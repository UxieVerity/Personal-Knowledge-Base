# 闭包与作用域链、执行上下文

> **结论：闭包 = 函数 + 它创建时的词法环境（Lexical Environment）的引用。** 函数内部声明的变量属于函数的作用域，函数**返回后**本应销毁——但**内部函数被返回/传递出去后，仍持有外层函数词法环境的引用**，于是外层变量「被带走、不销毁」，且**每次调用函数都创建一份独立的环境**。作用域链的查找规则是：**从当前词法环境出发，沿外部环境引用（outer）逐层向外，直到全局环境**。**`let/const` 是块级作用域（for 每轮迭代独立绑定），`var` 是函数级作用域（for 循环只创建一个变量）**——这是经典陷阱的根源。**闭包与 GC**：闭包环境里被引用的变量会**阻止回收**（有可达引用就不 GC），用后需主动断开；未被闭包引用的变量可以被回收（V8 已优化「无谓捕获」）。
>

## 1. 背景：JS 为什么要有闭包

- JS 函数是**一等公民**（可作为返回值、参数传递），且函数声明时**静态（词法）确定**它能看到哪些变量——不是看「在哪调用」，而是看「在哪定义」。
- 矛盾出现了：函数被当作值到处传，**定义它的作用域可能早已执行完毕**。如果外层变量随函数结束就销毁，那传出去的函数就"失忆"了。
- **闭包就是解决这个矛盾的机制**：把「函数」和「它出生时的环境」打包在一起，函数走到哪，环境跟到哪。

> 为什么这么设计：不是刻意发明"闭包"概念，而是「词法作用域 + 函数是一等公民」这两个 JS 基础设计**必然的推论**。任何语言只要同时具备这两点，就一定有闭包（Python、Ruby、Kotlin 全有）。

## 2. 核心机制：词法环境（Lexical Environment）

### 2.1 一次函数调用 = 一份词法环境

```js
function makeCounter() {
  let count = 0;              // ← 属于 makeCounter 本次调用的环境
  return function inc() {     // ← inc 的 [[Environment]] 指向这个环境
    count += 1;
    return count;
  };
}
```

| 概念 | 是什么 | 生命周期 |
| ---- | ---- | ---- |
| 词法环境 | 记录 `{ 变量名 → 值 }` 的容器 + 外部引用 outer | 函数每次调用**新建一份** |
| 环境记录 | 环境里的变量/函数声明 | 函数返回后若**仍被引用**则存活 |
| `[[Environment]]` | 函数对象内部指针，指向**它创建时**的环境 | 函数被创建时确定，**永不改变** |

### 2.2 实测：闭包确实「带走」了环境

> 🔗 代码见 [[闭包与作用域-验证脚本.js]] §A（闭包持有外层变量）/ §B（每次调用独立环境）

```
[A1] counter() = 1 | counter() = 2 | counter() = 3   ← makeCounter 早返回了，count 还能累加
[B1] c1() = 3 | c2() = 1                              ← 两次调用，两份独立 count，互不影响
```

- `[A]`：`makeCounter()` 执行完、栈帧弹出后，`count` 本应销毁；但返回的 `inc` 的 `[[Environment]]` 指着那份环境 → **count 存活，且可继续读写**。
- `[B]`：每次 `makeCounter()` 都**新建一份词法环境**，两个闭包各拿各的 → 互不干扰。**闭包不是"一份"，是"每次调用一份"。**

### 2.3 作用域链查找（闭包能"看见"什么）

```js
function outer() {
  const a = 1;
  function inner() {
    const b = 2;
    return a + b;   // 找 b：当前环境有 → 找 a：当前没有 → 沿 outer → 全局
  }
  return inner;
}
```

- 查找顺序：**当前环境 → 定义处的外层环境（outer）→ 再外层 → … → 全局环境**。
- 是**词法（定义处）决定**，不是调用处：`inner` 在哪调用，都不影响它看到的 `a`——它永远看定义时外层的 `a`。
- 关键：**作用域链在函数创建时就固定了**（`[[Environment]]`），运行时只是沿这条链查。

### 2.4 实测：词法作用域（定义处决定，不是调用处）

> 🔗 代码见 [[作用域与执行上下文-验证脚本.js]] §D（词法作用域 vs 动态作用域）

```
[D1] wrapper() = global        ← 返回 global 而非 local
[D2] 原因：JS 是词法作用域，函数能看到的变量由"定义位置"决定，与"调用位置"无关
```

```js
const who = 'global';
function showWho() { return who; }        // 定义在全局
function wrapper() {
  const who = 'local';
  return showWho();                       // 调用处在 wrapper，但 showWho 看定义处（全局）
}
wrapper();   // 'global'
```

- 这就是**词法作用域（Lexical Scoping）**：函数能访问的变量在**定义时**就确定了。
- 反例（动态作用域）语言（早期 Bash、Perl）：`wrapper()` 会返回 `local`——因为它看调用处。**JS 不是这样。**

### 2.5 实测：遮蔽（shadowing）

> 🔗 代码见 [[作用域与执行上下文-验证脚本.js]] §G（内层遮蔽外层）

```
[G1] outer 内 v = outer | inner 内 v = inner | 全局 v = outer
[G2] 遮蔽规则：查找从内向外，第一个命中的生效（inner > outer > global）
```

- 内层作用域声明与外层同名变量时，**内层遮蔽外层**，查找从内向外第一个命中即停。

## 2A. 执行上下文与调用栈（Execution Context & Call Stack）

### 2A.1 三个概念的关系

| 概念 | 是什么 | 类比 |
| ---- | ---- | ---- |
| **执行上下文**（EC） | 代码**执行时**的环境快照：变量环境 + 词法环境 + this + 函数引用 | 一次函数调用的"工作台" |
| **调用栈**（Call Stack） | 存放所有未完成执行上下文的**栈**（LIFO） | 函数调用的"调用记录堆叠" |
| **词法环境**（LE） | 代码**书写时**的变量归属结构（前面 2 节讲的） | 静态的"户口簿" |

- **词法环境是静态的**（代码写出来就有，决定"能看见谁"）；**执行上下文是动态的**（每次调用创建，决定"此刻在算谁"）。
- 每次函数调用：**创建新 EC → 压入调用栈 → 执行 → 出栈销毁**（栈顶永远是最新调用的）。

### 2A.2 实测：调用栈 LIFO 与先入后出

> 🔗 代码见 [[作用域与执行上下文-验证脚本.js]] §A（真实调用栈）/ §B（先入后出）

```
[A4] c() 最内层，完整栈: c → b → a → <anonymous>   ← 从下往上是压栈顺序（a 先入，c 最后入）
[B1] 执行顺序: A入 → B入 → C入 → C出                ← 最内层 C 最后入栈、最先生成结果（先入后出）
```

- 嵌套调用 `a() → b() → c()`：`a` 的 EC 先压栈，`c` 最后压栈 → **栈顶是 `c`**。
- `c` 执行完先出栈（`C出` 在最后输出），`a` 最后出——**先进后出（LIFO）**。

### 2A.3 实测：栈溢出（真实深度）

> 🔗 代码见 [[作用域与执行上下文-验证脚本.js]] §C（无限递归 → RangeError + 真实深度）

```
[C1] 无限递归 → RangeError | 崩溃深度 ≈ 12,510 层
[C2] 每个执行上下文都占内存，栈有上限 → 递归要写终止条件
```

- 每个 EC 都占内存（变量环境 + this + 调用记录），栈有上限（Node 本机约 **1.25 万层**）。
- 无限递归 → `RangeError: Maximum call stack size exceeded`。
- 面试延伸：**深递归 → 改迭代或尾调用优化**（V8 未完全实现 TCO，一般用循环/栈模拟）。

### 2A.4 执行上下文的三个阶段 + 提升（Hoisting）

> 🔗 代码见 [[作用域与执行上下文-验证脚本.js]] §E（var 提升）/ §F（let TDZ）

```
[E2] 执行到此时 x = undefined   ← var x 已提升，值为 undefined，未报错
[F1] let TDZ: 声明前访问 → ReferenceError: Cannot access 'y' before initialization
```

每个 EC 创建分三阶段：

| 阶段 | 发生什么 | var | let/const |
| ---- | ---- | ---- | ---- |
| **创建** | 扫描声明，var 提升并初始化为 `undefined`；let/const **提升但未初始化**（TDZ） | `x = undefined` | 处于**暂时性死区（TDZ）** |
| **执行** | 逐行执行，赋值生效；TDZ 内访问 let 变量 → `ReferenceError` | 赋值后才更新 | 声明行执行后脱离 TDZ |
| **销毁** | EC 出栈（被闭包引用的环境除外） | — | — |

> 面试一句话：**"`var` 提升到函数顶部并初始化为 `undefined`；`let/const` 也提升，但进入暂时性死区，声明前访问报 `ReferenceError`。这就是 `typeof x` 在 `let x` 前调用会报错、而 `var` 不会的原因。"**

> 为什么这么设计：TDZ 是 ES6 引入 `let/const` 时**故意**的严格化——把"声明前访问"从静默 `undefined` 变成显式报错，逼你写出声明在前的代码，避免 `var` 时代"用了才发现是 undefined"的隐性 bug。

## 3. 经典陷阱：for 循环 + 闭包（var vs let）

> 🔗 代码见 [[闭包与作用域-验证脚本.js]] §C（var 捕获同一变量 vs let 每轮新绑定）

```
[C1] var: fnsVar.map(f=>f()) = [ 3, 3, 3 ]   ← 3 个闭包全指向同一个 i（循环结束后 i=3）
[C2] let: fnsLet.map(f=>f()) = [ 0, 1, 2 ]   ← 每轮迭代独立绑定
```

| 版本 | 行为 | 原因 |
| ---- | ---- | ---- |
| `var i` | 全输出 3 | `var` 是**函数级作用域**，整个循环只有**一个** `i`，3 个闭包捕获同一变量，循环结束它=3 |
| `let j` | 输出 0,1,2 | `let` 是**块级作用域**，规范要求 **for 每轮迭代创建新的词法环境**，每轮闭包捕获各自那轮的 `j` |

> 面试回答模板：**"`var` 捕获的是同一个变量引用，`let` 捕获的是每轮迭代的新绑定。这是 `let` 的规范行为——`PerIterationBindings` 每轮新建环境。"**

## 4. 闭包与 GC（内存）

> 🔗 代码见 [[闭包与作用域-验证脚本.js]] §D（WeakRef + FinalizationRegistry 实测 GC），运行需 `node --expose-gc`

```
[D-gc] 无引用的 big 已被 GC 回收            ← 闭包没引用它 → 可回收
[D4]   强制 GC 后 holder() = 闭包持有着我    ← 闭包环境里还有 big → 阻止回收
```

- **闭包环境里被可达引用的变量，GC 不会回收**——因为词法环境仍被闭包对象引用着。
- **V8 的"无谓捕获"优化**：闭包只引用了 `tmp` 但外层有 `big` 时，`big` **不会**被整个环境连带持有（`[D-gc]` 证明它被回收了）。**不是所有外层变量都被闭包锁住，只有真正被引用的那些。**
- **内存泄漏真实场景**：
  - 事件监听器：`el.onclick = bigHandler` 且 handler 引用大对象 → 页面关闭前 `removeEventListener` 才能释放
  - `setInterval` 回调闭包引用大对象，但忘了 `clearInterval`
  - 全局变量挂大对象（`window.xxx`）永不回收

> 为什么这么设计：GC 只看**可达性**（引用图），不管"函数是否返回"——闭包环境是一个普通对象节点，被闭包引用着就是可达，就活。**这不是 bug，是"函数是一等公民"的代价**：你得到一个永远带记忆的函数，就得承担它可能拖住内存。

## 5. 闭包的三大用途

| 用途 | 例子 | 面试怎么讲 |
| ---- | ---- | ---- |
| **私有变量** | 计数器 / 模块内部状态，外部无法直接改 | "闭包模拟私有：`count` 只能通过返回的函数改，外部拿不到引用" |
| **柯里化 / 函数工厂** | `const add = x => y => x + y` | "把参数分次捕获，每次调用生成新闭包" |
| **模块化（IIFE 模式）** | `const mod = (() => { let n; return {get, set} })()` | "IIFE 执行一次，暴露的 API 闭包持有私有状态"——ES Module 出现前的主流封装 |

> 面试常考：**闭包的应用场景 = 私有变量 + 柯里化 + 模块化**，能各举一个例子即可。

## 6. 高频追问速答

| 问题 | 一句话答案 |
| ---- | ---- |
| 什么是闭包？ | 函数 + 创建时的词法环境引用，函数返回后仍能访问外层变量 |
| 闭包为什么能访问外层变量？ | 函数对象持有 `[[Environment]]` 指向创建时的环境，沿作用域链查找 |
| 闭包会造成内存泄漏吗？ | 会——被引用的变量阻止 GC；但 V8 只锁「真正被引用」的，用后主动断开（`= null` / 移除监听） |
| `var` 和 `let` 在循环里的区别？ | `var` 函数级一个变量全捕获；`let` 每轮迭代新环境 |
| 每次调用闭包函数都是同一份吗？ | 不是，**每次调用外层函数创建一份新环境**，闭包之间互不影响 |

## 7. 面试速记（30 秒版）

> **闭包 = 函数 + 它出生时环境的引用。** 函数是一等公民 + 词法作用域 → 必然有闭包。返回的函数持有 `[[Environment]]`，外层变量被"带走"存活。**每次调用创建独立环境**；`var` 捕获同一变量（for 陷阱），`let` 每轮新绑定。内存上：**只有被闭包真正引用的变量才阻止 GC**（V8 无谓捕获优化），用后 `= null` 或移除监听。三大用途：**私有变量 / 柯里化 / IIFE 模块化**。
