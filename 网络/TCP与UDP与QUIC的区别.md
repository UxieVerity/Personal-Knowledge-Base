# TCP 与 UDP 与 QUIC 的区别

> **结论：TCP 可靠有序但串行（有队头阻塞）、UDP 最快但不可靠（无连接）、QUIC 想兼得两者——在 UDP 上自建可靠传输 + 多路复用独立流，消除队头阻塞，成为 HTTP/3 的传输层。** 模型模拟 10 个包、5% 丢包：TCP **110ms**（丢 1 包全连接阻塞）→ UDP **10ms**（最快但会丢数据）→ QUIC **65ms**（只重传丢的那个流）。一句话：**UDP 是"尽力而为"，TCP 是"确保到达"，QUIC 是"确保到达且互不拖累"。**

## 1. 背景：三种协议各解决什么问题

网络传输层的两个极端：

- **UDP（用户数据报协议，1980）**：无连接、不可靠、无序。发出去不管，最快最轻。适合实时性 > 可靠性的场景（视频、语音、游戏）。
- **TCP（传输控制协议，1981）**：面向连接、可靠、有序。三次握手 + 确认重传 + 拥塞控制。适合准确性 > 速度的场景（HTTP、文件、邮件）。
- **QUIC（Quick UDP Internet Connections，2012+）**：Google 在 UDP 之上自建可靠传输，2018 标准化，成为 **HTTP/3** 的传输层。要「TCP 的可靠 + UDP 的速度 + 多路复用」。

## 2. 核心区别：一句话表

| 维度 | TCP | UDP | QUIC |
| ---- | --- | --- | ---- |
| 连接 | **面向连接**（三次握手） | **无连接**（直接发） | 面向连接（握手含 TLS1.3） |
| 可靠性 | ✅ 可靠（确认+重传） | ❌ 不可靠（尽力而为） | ✅ 可靠（独立流级重传） |
| 有序性 | ✅ 有序（按序号交付） | ❌ 无序 | ✅ 每流有序 |
| 队头阻塞 | ✅ **有**（一个包丢全等） | ❌ 无 | ❌ **无**（流独立） |
| 握手往返 | 1 RTT | **0 RTT** | 1 RTT（重连 0-RTT） |
| 传输单位 | 字节流（面向连接） | 数据报（面向报文） | 独立流（多路复用） |
| 头部开销 | 20 字节 | **8 字节** | 较大（含 TLS 状态） |
| 拥塞控制 | ✅ 内置（慢启动/拥塞避免） | ❌ 无 | ✅ 用户态实现（更灵活） |
| 典型应用 | HTTP、邮件、文件 | DNS、视频、语音、游戏 | **HTTP/3**、WebTransport |

## 3. 实测/模拟：行为差异

> 模型参数：RTT=50ms，10 个包，5% 丢包率，一次重传 50ms。**QUIC 为模型模拟**（Node 26 无内置 QUIC），TCP/UDP 部分有本机真实锚点。

| 场景 | TCP | UDP | QUIC |
| ---- | --- | --- | ---- |
| 握手往返 | 1 RTT | **0 RTT** | 1 RTT（重连 0-RTT） |
| 单请求延迟（无丢包） | 60ms | **10ms** | 60ms（重连同 UDP） |
| 5% 丢包下总耗时 | **110ms**（全连接阻塞） | 10ms（会丢数据） | **65ms**（只重传单流） |

- **真实锚点**：
  - **TCP**：HTTP/1.1 单连接串行 16 请求 = **762ms**（[[HTTP1vsHTTP2-验证脚本.js]] 实测）——队头阻塞的直接证据。
  - **UDP**：DNS 查询走 UDP 53，`localhost` 命中 **0.03ms**（[[DNS解析路径-验证脚本.js]] 实测）——无连接、极快。
  - **QUIC**：无本机实现，为模型模拟（诚实标注）。

## 4. 深入：为什么这样设计？（背后取舍）

### 4.1 为什么 TCP 有队头阻塞，UDP 没有

TCP 保证**有序交付**：接收方必须按序号组装，一个包丢了，后续所有包（无论属于哪个应用请求）都要**等在缓冲区里等重传**。这是可靠性（有序）换来的代价。UDP 不管顺序，丢包就丢，所以没有这个阻塞，但应用层得自己处理乱序/丢失。

### 4.2 QUIC 怎么做到「可靠 + 不阻塞」

QUIC 在 UDP 之上把连接拆成**多个独立流**，每个流独立编号、独立确认、独立重传。**一个流的包丢了，只重传那个流，其他流照常传输**——这就是「消除队头阻塞」。用可靠性换速度的取舍变了：TCP 是「一个丢、全体等」，QUIC 是「一个丢、单流等」。

### 4.3 为什么 QUIC 用 UDP 而不是改 TCP

改 TCP 需要**升级全球操作系统内核**（TCP 栈在内核），太慢。QUIC 在 **UDP 之上用用户态实现**可靠传输——不需要动内核，任何支持 UDP 的系统都能跑。代价是**用户态实现拥塞控制/重传更复杂**，且要过 NAT/中间设备的坑（部分网络限速/阻断 UDP）。

### 4.4 与上层协议的联动（面试重点）

- **HTTP/1.1 / HTTP/2** 走 **TCP** → 受 TCP 队头阻塞影响（H2 消除了应用层 HOL，但 TCP 层 HOL 还在）。
- **HTTP/3** 走 **QUIC（UDP）** → 队头阻塞彻底消除，这就是 H3 存在的意义。见 [[HTTP1和HTTP2、HTTP3 的区别]]。
- **DNS** 走 **UDP 53**（快、一次查询）→ 这是 UDP 最经典的应用。
- **TLS 1.3** 内置进 QUIC 握手 → 连接建立更快。见 [[TLS12和TLS13的区别]]。

## 5. 规避 / 实践

| 场景 | 该用哪个 | 原因 |
| ---- | -------- | ---- |
| Web 页面/API | TCP（HTTP/1.1/2）、QUIC（HTTP/3） | 需要可靠 + 快 |
| 视频/语音/直播 | **UDP**（WebRTC/SRT/RTMP over UDP） | 实时性 > 完整性，丢帧可接受 |
| 在线游戏 | **UDP**（或 QUIC） | 低延迟优先 |
| DNS 查询 | **UDP 53**（大响应 TCP 回退） | 单次查询，快 |
| 弱网/移动（跨洋） | **QUIC**（HTTP/3） | 独立流 + 0-RTT + 连接迁移 |
| 大文件下载 | TCP | 需要可靠有序（或用 QUIC 分块） |

```bash
# 看一个连接用的传输层协议（ss 显示 UDP/TCP）
ss -tunap | grep -E ":443|:53"
# tcp:  TCP   QUIC/UDP:  UDP
```

## 6. 面试速记

> **30 秒版**："TCP 可靠有序但有队头阻塞——一个包丢，后续全等；UDP 最快但不可靠、无连接，适合实时场景。QUIC 在 UDP 上自建可靠传输，把连接拆成独立流，丢包只重传单流，队头阻塞就没了，还内置 TLS1.3、0-RTT、连接迁移。所以 HTTP/3 用 QUIC 取代 TCP，就是想要 TCP 的可靠 + UDP 的速度。"
