# TCP FIN 和 RST：正常关闭 vs 异常断开

TCP 有两种断开方式：**FIN（四次挥手，优雅关闭）** 和 **RST（重置，粗暴断开）**。

## 1. FIN：优雅关闭（四次挥手）

FIN 的含义：**我这边不再发送数据了，但我还可以接收你发来的数据**（半关闭）。

完整四次挥手：

1. 客户端调用 `close()` → 内核发出 `FIN`，我不再发数据
2. 服务端回复 `ACK`，确认收到 FIN

> 到这里：客户端已经不能 send ()，但还能 recv () 接收服务端剩下的数据

3. 服务端也调用 `close()` → 内核发出 `FIN`，服务端也不再发送
4. 客户端回复 `ACK`，连接正式释放

> TIME‑WAIT 就是客户端收到对方 FIN 之后，等待一段时间，防止最后一个 ACK 丢包，对方重传 FIN。

特点：

- 有序、把缓冲区剩余数据尽量发送完毕
- 双方清楚 “连接要结束了”
- 属于**正常关闭流程**

---

## 2. RST：Reset 重置，暴力断开

RST = **直接废掉这条连接，丢弃缓冲区所有未发送 / 未接收数据，不做善后**，没有四次挥手。

什么场景会产生 RST：

1. **对方进程崩溃 / 被杀死，没调用 close** 进程直接退出，操作系统内核发现还有 TCP 连接，直接发 RST 把连接干掉，不走 FIN。
2. 向一个**不存在的端口发起 TCP 连接**，对方回复 RST。
3. 连接已经断掉，你还往这个已经失效的 socket 写数据，内核返回 RST。
4. 防火墙、中间设备主动切断连接，回复 RST。

表现：

- 收到 RST 之后：`recv()` 返回 -1；`send()` 直接抛出异常报错
- **没有半关闭，剩余数据全部丢掉**

> 区分记忆： FIN：礼貌说 “我说完了，再见”； RST：直接挂断电话，“挂掉，不谈了”。

---

## 3. 对比 UDP，感受差距

UDP **没有 FIN，没有 RST**。

- UDP 客户端不停发数据包，服务端进程挂掉了：
    - `sendto()` 返回成功，内核认为数据包已经交给网卡发出去了；
    - 只有对方操作系统回复 **ICMP 端口不可达**，本机内核才知道端口没人监听；
    - 但**防火墙经常把 ICMP 报文丢掉**，于是客户端完全蒙在鼓里，一直发送，完全不知道对方已经没了。

而 TCP：对方进程崩溃，会收到 RST，调用 send 立刻报错。

> QUIC 跑在 UDP 上，它自己在应用层模拟这个：
> 
> - 优雅关闭：发送 `CONNECTION_CLOSE` 帧（相当于 QUIC 版本的 FIN）
> - 异常断开：直接停止收发，超时判定连接死亡；QUIC 不会依赖 ICMP。

---

## 4. 一个非常经典的实验例子，方便理解

### TCP 场景

1. client 和 server 建立 TCP 连接
2. 直接 kill‑9 杀掉服务端进程（不是正常 close）
3. 服务端 OS 发出 RST 报文
4. 客户端再 send () → 直接报错 `Connection reset by peer`

### UDP 场景

1. client、server UDP 连通
2. kill‑9 杀掉 UDP 服务端进程
3. 客户端继续 sendto，调用返回成功，**不报错**
4. 如果防火墙不拦截 ICMP，下一次 recv 才可能感知；很多环境下完全感知不到。

---

## 5. 补充一个容易混淆：TIME‑WAIT vs CLOSE‑WAIT

- **TIME‑WAIT**：主动关闭那一方，发完最后 ACK 之后等待，防止丢包；是正常状态。
- **CLOSE‑WAIT**：被动关闭方收到 FIN，但应用程序**忘记调用 close ()**，一直占着连接，属于代码 bug，会泄露 socket。

> 比如服务端收到客户端 FIN，内核回 ACK，但业务代码一直不 close (fd)，连接就卡在 CLOSE_WAIT。

# 把前面整套链路串一遍小结（HTTP1/2/3）

1. **HTTP1.1**：多条 TCP，TCP 内核：三次握手、cwnd 慢启动、FIN/RST 断开；HTTP 层队头阻塞。
2. **HTTP/2**：单 TCP 多路复用，解决 HTTP 层队头阻塞；但 TCP 内核带来**传输层队头阻塞**，丢包整个连接卡住；断开还是 TCP 的 FIN/RST。
3. **HTTP/3 QUIC over UDP**：
    - UDP 内核：无握手、无 FIN/RST，只管发包；
    - QUIC 在 UDP 包里面**自己实现握手、重传、cwnd 拥塞控制、连接关闭帧**；
    - 多个 Stream 互相隔离，一个流丢包不影响别的流；
    - 连接迁移：手机切 Wi‑Fi/5G，IP 变了，依靠 ConnectionID 维持连接，TCP 做不到（TCP 靠 IP + 端口标识，IP 一变直接 RST 断开）。
