# HTTP/1.1 与 HTTP/2、HTTP/3 的区别

> **结论：HTTP/1.1 → HTTP/2 → HTTP/3 是「解决队头阻塞」的三步演进。** HTTP/2 用**二进制分帧 + 多路复用**在 1 条 TCP 连接上并行传输所有流，消除应用层 HOL（实测 16 资源：H1 串行 **762ms** → H1 六连 **154ms** → H2 单连多路复用 **60ms**，比 H1 六连还快 2.6×）；HTTP/3 改用 **QUIC（UDP）**，把每个流独立成自己的传输单元，**连 TCP 层 HOL 也消除**（丢包模拟：H2 共享连接 **90ms** vs H3 独立流 **46ms**，1.9×）。代价：H2 新增 TCP 层 HOL + 需 TLS/ALPN；H3 上 UDP、需 QUIC 支持。

> 可运行验证：[[HTTP1vsHTTP2-验证脚本.js]]（Node 起 HTTP/1.1 + HTTP/2(h2c) 服务器，实测 16 请求在 1 连接/6 连接/多路复用下的总耗时与完成序；第三段模拟丢包下 TCP 共享连接 vs QUIC 独立流的差异）

---

## 1. 背景：HTTP/1.1 的瓶颈

HTTP/1.1（1997）沿用了 1991 年 HTTP/1.0 的**文本协议**：每个请求一条报文，`\r\n` 分隔，且**一条 TCP 连接同时只能处理一个请求**（串行）。这带来几个致命问题：

1. **队头阻塞（Head-of-Line Blocking）**：连接上前一个请求没返回，后面的请求就得排队等。
2. **连接数爆炸**：为缓解串行，浏览器对每个域名最多开 **6 条**并行连接（现代 Chrome/Firefox），但并发上限仍低。
3. **头部冗余**：请求/响应头是明文文本，每次重复发送（Cookie、UA、Accept 等），浪费带宽。
4. **无法优先级**：多个资源同时请求时没有机制让关键资源（CSS/首屏图）先到。

## 2. 实测：三种并发模型对比

> 环境：本机 Node `http`（HTTP/1.1）与 `http2`（h2c 明文）服务器，`127.0.0.1` 回环；16 个资源并发请求，每个资源服务器端延迟 **40ms**。机器不同数值有差异，**相对倍率稳定**。

| 模型 | TCP 连接数 | 总耗时 | 完成序 |
| ---- | ---------- | ------ | ------ |
| HTTP/1.1 · 单连接（串行） | **1** | **761.6ms** | 严格 0→15（队头阻塞） |
| HTTP/1.1 · 6 连接（浏览器上限） | **6** | **153.9ms** | 乱序并行 |
| HTTP/2 · 多路复用 | **1** | **59.5ms** | 乱序并行 |
| HTTP/3 · QUIC 独立流（丢包模拟） | **1** | **46ms**（最慢流） | 丢包只拖慢单流 |

- **理论值对照**：串行 = 16×40 = **640ms**；6 连接 = ⌈16/6⌉×40 ≈ **120ms**；H2 全并行 ≈ **40ms**。实测与之吻合（含连接建立开销）。
- **第三段（H3 丢包模拟）**：8 个并行流，第 3 个流丢 1 个包（需 50ms 重传）。H2 共享 TCP 连接 → 全部 8 个流一起等重传（**90ms**）；H3 独立流 → 只有第 3 流多等（**46ms**），差距 **1.9×**。丢包越多差距越大。
- **关键读数**：
  - H1 单连接完成序是**严格递增 0,1,2,…15**——前一个没完成绝不开始下一个 = 队头阻塞的直接证据。
  - H2 **用 1 条连接**完成全部 16 个请求，耗时 59.5ms ≈ 单请求延迟，比 H1 的 6 条连接（153.9ms）还快 **2.6×**。
  - H2 完成序乱序——16 个流同时在一条连接上并发传输。

> 一句话：**HTTP/2 用 1 条连接做到比 HTTP/1.1 6 条连接还快，靠多路复用；HTTP/3 再把最后残留的 TCP 层 HOL 也用 QUIC 独立流拔掉。**

## 3. 核心区别：一句话表（三个版本横向对比）

| 维度    | HTTP/1.1                | HTTP/2                    | HTTP/3 (QUIC)                      |
| ----- | ----------------------- | ------------------------- | ---------------------------------- |
| 传输层   | TCP                     | TCP                       | **UDP（QUIC 封装）**                   |
| 数据格式  | **文本**（ASCII，`\r\n` 分隔） | **二进制分帧**                 | 二进制分帧（继承 H2）                       |
| 请求/响应 | 一条连接一次一个（串行）            | **多路复用**：1 连接 N 流         | 多路复用 + **流独立**                     |
| 队头阻塞  | ✅ 应用层 HOL               | ❌ 应用层；⚠️ 仍剩 **TCP 层 HOL** | ❌ **应用层 + TCP 层都消除**               |
| 连接数   | 每域名 ~6 条                | 每域名 **1 条**               | 每域名 **1 条**（连接可迁移）                 |
| 头部压缩  | ❌ 明文                    | ✅ **HPACK**               | ✅ **QPACK**（兼容 HPACK 语义）           |
| 握手    | TCP                     | TCP + **TLS/ALPN**        | **QUIC 握手（TLS1.3 内置）**：1-RTT/0-RTT |
| 连接迁移  | ❌                       | ❌                         | ✅ **Connection ID**（WiFi↔4G 不断）    |
| 流优先级  | ❌                       | ✅ 权重/依赖                   | ✅ 继承 H2 + 更细                       |
| 服务器推送 | ❌                       | ✅ `PUSH_PROMISE`（少用）      | ❌ 移除（H3 废除推送）                      |
| 兼容性   | 通用                      | 需协商，失败回退 H1               | 需协商，失败回退 H2/H1                     |

## 4. 深入：为什么这样设计？（背后取舍）

### 4.1 为什么要二进制分帧

文本协议靠分隔符切分报文，**无法区分"哪个字节属于哪个请求"**——这是 H1 不能在一连接上并行传输的根因。HTTP/2 把数据切成**二进制帧**，每帧带 `Stream ID`（属于哪个流）+ 长度 + 标志位，接收端靠 ID 重组。代价是**人类不可读**（wireshark 需解码），换来的是多路复用的可能。

### 4.2 为什么队头阻塞没有完全消失

HTTP/2 消除了**应用层** HOL（不再互相排队），但所有流共享同一条 **TCP** 连接。TCP 保证有序交付，**一个包丢了，后续所有包（属于任何流）都要等重传**——这就是 **TCP 层队头阻塞**。HTTP/3（QUIC over UDP）把流独立成多个连接单元，才彻底解决。取舍：**多路复用的收益 > 单连接丢包放大风险**（局域网/无丢包时 H2 全面占优；高丢包网络 H3 才显优势）。

### 4.3 为什么头部压缩用 HPACK

H1 每次请求重复发送完整明文头（Cookie 常 1KB+），16 个资源就是 16 份重复。HPACK 维护**静态表**（61 个常见头）+ **动态表**（本次会话见过的头只传索引），Huffman 编码压缩。代价是**有状态**（两端都要维护表）→ 需要在连接上协商，这也是为什么 H2 依赖连接会话。

### 4.4 为什么还是需要多条连接（现实）

- H2 一条连接理论上够，但**服务器推送/流优先级**处理不好反而拖慢；且**高丢包网络**下单连接风险集中。
- 现实优化：H2 通常仍保留少量连接（如 Chrome 默认同域名 1 条，但跨域名仍各自建立），且 **域分片（domain sharding）** 在 H2 下反而有害。

### 4.5 HTTP/3 为什么用 QUIC（UDP）——彻底解决 TCP 层 HOL

HTTP/2 消除了应用层 HOL，但所有流共享 1 条 TCP 连接。**TCP 保证有序交付：一个包丢了，后续所有包（不管属于哪个流）都要等重传**——这就是 TCP 层队头阻塞。HTTP/3 换掉传输层：

- **QUIC（Quick UDP Internet Connections）**：在 **UDP** 之上自建可靠传输，把「连接」拆成**多个独立流**，每流独立编号、独立确认、独立重传。**一个流丢包重传，不影响其他流**。
- 实测模拟（8 流、第 3 流丢 1 包）：H2 共享连接全部一起等重传 **90ms** vs H3 独立流只有单流慢 **46ms**，**1.9×**；丢包越多差距越大。
- **握手更快**：QUIC 内置 TLS 1.3，握手合并到 1 次往返（**1-RTT**，重连 **0-RTT**），比 H2「TCP+TLS」两步快。
- **连接迁移**：QUIC 用 **Connection ID** 标识连接而非 IP+端口 → 手机从 WiFi 切 4G，连接不断。
- **QPACK**：H3 头部压缩改用 QPACK（兼容 HPACK 语义，但针对「流乱序」做了优化——因为 QUIC 各流可能乱序到达）。
- **移除服务器推送**：实践中推送容易过度、抢占带宽，H3 直接废除，用 `preload`/`103 Early Hints` 替代。

> 取舍：QUIC 在**用户态**实现拥塞控制/重传（绕过操作系统 TCP 栈），更灵活但更复杂；上 UDP 意味着**要过 NAT/中间设备的坑**（部分网络对 UDP 限速/阻断）。所以 H3 通常**协商失败自动回退 H2/H1**，保证兼容。

## 5. 规避 / 实践

| 问题 | 手段 | 对应协议 |
| ---- | ---- | -------- |
| H1 队头阻塞 | 升级 **HTTP/2**、`domain sharding`（临时缓解） | H2 |
| H2 仍有 TCP 层 HOL | 升级 **HTTP/3 (QUIC)** | H3 |
| 高丢包/弱网（移动、跨洋） | **HTTP/3** 独立流 + 0-RTT + 连接迁移 | H3 |
| 手机切换网络连接中断 | **HTTP/3 Connection ID** 迁移 | H3 |
| 头部冗余 | H2 自带 HPACK，无需手动 | H2 |
| 首屏关键资源优先 | H2 **流优先级**；H1 用 `<link rel="preload">` | H2/H1 |
| 连接建立慢（TLS 握手） | HTTP/2 + `keep-alive` 长连接复用；HTTP/3 0-RTT | H2/H3 |
| 服务器推送滥用 | 谨慎使用 `PUSH_PROMISE`，多数场景用 preload 替代 | H2 |
| H3 被中间设备阻断 | 自动回退 H2/H1（`Alt-Svc` 协商） | H3→H2/H1 |

```nginx
# 服务器启用 HTTP/2 与 HTTP/3（Nginx，需 TLS）
listen 443 ssl http2;
listen 443 quic reuseport;   # HTTP/3 (QUIC)
add_header Alt-Svc 'h3=":443"; ma=86400';  # 告诉客户端支持 h3
```

```http
# 调试：看响应用的协议版本（DevTools Network → Protocol 列）
HTTP/3 200   ← h3 | HTTP/2 200 ← h2 | HTTP/1.1 200
```

## 6. 面试速记

> **30 秒版**："HTTP/2 核心是二进制分帧 + 多路复用，1 条 TCP 连接并行跑所有请求，解决 H1 的应用层队头阻塞；头部 HPACK 压缩。实测 16 资源 H2 一条连接 60ms 比 H1 六条 154ms 还快 2.6×。但 TCP 层队头阻塞还在——一个包丢、整条连接的所有流都等。HTTP/3 改用 QUIC(UDP)，把流拆成独立单元，丢包只拖慢单流（模拟 1.9×），还内置 TLS1.3 握手更快、连接可迁移。"
