# 从浏览器输入网址到页面完整展示全过程

> **结论：输入网址到页面展示是一条「前置逻辑 + 网络请求链 + 浏览器渲染链」串成的流水线。真正向服务器发起「最终资源」请求之前，还有两道前置——① 缓存查找（命中新鲜副本 → 0 网络请求，直接本地短路）、② 重定向跟随（3xx 自动跳 Location，回到缓存/请求循环再走一遍）。网络链的终点是 TTFB（首字节），渲染链的起点是 HTML 到达——两段的分界线是 `responseStart`。** 实测中 `slow.css`（放在 `<head>` 的渲染阻塞样式）把 FCP 从 28ms 拖到 532ms（**≈19×**），把 DOMContentLoaded 从 12ms 拖到 526ms（**≈44×**）——它不只阻塞首次渲染，还阻塞了 `<head>` 之后的脚本执行。

> 可运行验证：[[导航时序全过程-demo.html]]（本地 HTTP 服务器给 `slow.css`/`slow.png` 注入延迟，逐段拆解 Navigation Timing + Paint Timing，含瀑布图）；[[重定向与缓存-验证脚本.js]]（本地 HTTP 服务器 + 浏览器式缓存客户端，实测 301 跟随、缓存命中 0 请求、no-cache→304、no-store 全量）

## 1. 背景：一条流水线，两段链路

从输入 URL 到页面展示，本质是**两条链路串接**，前面还有一道**前置逻辑**：

```
[前置逻辑(发请求前)]              [网络请求链]                                   [浏览器渲染链]
输入URL → ①缓存查找 → ②DNS → ③TCP → ④TLS → ⑤HTTP请求 → ⑥HTTP响应 → 解析HTML → CSSOM → 渲染树 → 布局 → 绘制 → 合成 → 屏幕
   │  命中→0网络请求            ↑ 收到 3xx → 跟随 Location，回到①/⑤ 循环 │
   └→ 直接用本地副本             └───── TTFB 分界线 ─────┘
                                   responseStart = HTML 第一个字节到达
```

- **前置逻辑的性能特征在「省」**：缓存命中直接短路，省掉整个网络链（0 请求）；重定向每跳一次 = 多一个完整 RTT，是纯开销。
- **网络链的性能瓶颈在「延迟」**：DNS、TCP、TLS、服务器处理、网络 RTT，决定 TTFB。
- **渲染链的性能瓶颈在「阻塞」**：HTML/CSS/JS 的解析顺序、渲染阻塞资源，决定 FCP/LCP。
- 两条链几乎**互不影响**：网络再快，渲染阻塞资源照样推迟首屏；渲染再快，网络慢 TTFB 也下不去。

## 2. 前置处理：输入 → 导航意图

用户在地址栏输入内容后，浏览器先做「意图判断」，然后才发起导航：

1. **判断是搜索词还是 URL**：含空格或不是合法 URL → 走搜索（默认搜索引擎）；是合法 URL 或域名 → 直接导航。
2. **自动补全协议**：输入 `example.com` 无协议时，现代浏览器默认补 `https://`（不再是 `http://`）。
3. **查本地 DNS 缓存**：先查**浏览器自身缓存**，命中即短路（hosts、系统都不再查，直接拿 IP，跳过网络 DNS 查询）；miss 后读**系统 `hosts` 文件**（静态配置、最高优先级，命中即止）；再往下才到系统解析层。⚠️ 浏览器实现有差异：**Chrome/Edge 默认自带 async DNS 解析器，绕过系统 DNS 缓存、直连配置的 DNS 服务器**；**Firefox 才走系统 `getaddrinfo`（用系统 DNS 缓存）**。优先级 **hosts > 系统缓存 > 网络查询**——但浏览器缓存命中会暂时掩盖 hosts 改动（改 hosts 后需清浏览器缓存才生效）。可运行验证：[[DNS解析路径-验证脚本.js]]
4. **同一站点复用连接**：如果是同源二次访问，TCP/TLS 连接可能被复用（keep-alive），跳过握手。

> ⚠️ 只有「输入框回车/点击链接」才叫导航（navigation）。JS 改 `location.href` 也叫导航，但 `fetch`/XHR 请求**不是导航**——它们不触发页面解析渲染。

## 3. 重定向与缓存：真正发起 HTTP 请求前的两道前置逻辑

> **结论：在浏览器真正向服务器发起「最终资源」的 HTTP 请求之前，有两条前置逻辑——① 重定向跟随（3xx 自动跳转 Location），② 本地缓存查找（命中新鲜副本 → 0 网络请求）。** 缓存是**先于网络**的：命中就不用建连接、不发请求。重定向是**响应回来后的循环**：收到 3xx 就回到缓存/请求循环再走一遍。**304 不是重定向**——它是「缓存校验通过，复用本地副本」的信号，不产生新请求。

```
输入 URL → 导航意图
   ↓
┌─ 前置逻辑（真正发请求前）─────────────────────────┐
│  ① 缓存查找：命中新鲜？→ 直接用本地副本，0 网络请求    │
│     miss / 过期 ↓                               │
│  ② DNS → TCP → TLS → 发送 HTTP 请求 → 收到响应     │
│     · 响应 3xx（301/302/…）→ 跟随 Location ──→ 回到① │
│     · 响应 304 → 缓存校验通过 → 用本地副本           │
│     · 响应 200 → 写入缓存 → 进入渲染链              │
└──────────────────────────────────────────────────┘
```

### 3.1 重定向：浏览器自动跟随 3xx

- **机制**：服务器返回 `3xx + Location`，浏览器自动对 `Location` 再发起一次导航（重新走缓存→DNS→连接）。业务 JS 通常无感知，`fetch` 默认 `redirect: "follow"` 也是自动跟随；设 `redirect: "manual"` 才能拿到 3xx 本身。
- **状态码语义（面试高频）**：

| 状态码 | 语义 | 默认可缓存 | 是否保留方法/请求体 |
| --- | --- | --- | --- |
| **301** | 永久重定向 | ✅ 可缓存 | POST 可能被改成 GET |
| **302** | 临时重定向 | ❌（除非显式缓存头） | POST 可能被改成 GET（历史遗留） |
| **303** | See Other | ❌ | 强制改成 GET |
| **307** | 临时重定向 | ❌ | ✅ 保留方法 + 请求体（POST 仍是 POST） |
| **308** | 永久重定向 | ✅ 可缓存 | ✅ 保留方法 + 请求体 |

- **301 vs 308 / 302 vs 307 的核心区别 = 方法保留**：307/308 是「POST 提交后跳转」的正确选择，301/302 会丢请求体。
- **重定向是纯开销**：每跳一次 = 一次完整请求-响应 = 多一个 RTT。链式重定向（/a→/b→/c）逐级翻倍延迟，是 TTFB 高的隐藏原因。
- **有上限**：浏览器限制重定向次数（Chrome 约 20 跳），防死循环（/a→/b→/a）。
- **跨域重定向丢敏感头**：跳转到不同源时，浏览器会丢弃 `Authorization` 等敏感头（防凭据泄露到第三方）。

### 3.2 缓存：先于网络的本地副本

- **查找顺序**：Service Worker（Cache API）→ 内存缓存（最快）→ 磁盘缓存（持久）→ 网络。
- **命中 = 0 网络请求**：直接从本地读，无 DNS/TCP/TLS/网络往返（实测见 §3.3）。
- **新鲜度判定（强缓存）**：
  - `Cache-Control: max-age=N`：从存储起 N 秒内直接命中；
  - `Expires`：HTTP/1.0 的绝对过期时间，基本被 `max-age` 替代；
  - **无任何缓存头 → 启发式缓存**：浏览器按 `(Date − Last-Modified) × 10%` 估一个新鲜期——「没配缓存却被缓存了」多半是这个。
- **过期后的协商缓存（条件请求）**：不直接弃用，带校验器问服务器：
  - `ETag / If-None-Match`：内容哈希（强校验）；
  - `Last-Modified / If-Modified-Since`：时间戳（弱校验，精度到秒）；
  - 服务器回 **304 Not Modified** → 无响应体，本地副本继续用（省带宽）；
  - 服务器回 **200** → 内容真变了，全量下载并替换。

- **Cache-Control 指令速记**：

| 指令 | 含义 | 面试一句话 |
| --- | --- | --- |
| `no-store` | 不存任何副本 | 每次全量下载，最严格 |
| `no-cache` | 可存副本，但每次用前必须先校验 | **≠ 不缓存**：省响应体、不省请求 |
| `private` | 仅浏览器缓存，共享缓存(CDN)不存 | 针对用户数据 |
| `public` | 可被 CDN/代理共享缓存 | 静态资源常用 |
| `max-age=0` | 立即过期，每次校验 | 语义 ≈ `no-cache` |
| `must-revalidate` | 过期后必须校验，禁止用过期副本 | 关掉 stale-while-revalidate |

- **⚠️ 304 不是重定向**：没有 `Location`，不产生新请求链；它是「服务器说『你没变』」的缓存校验响应，只出现在条件请求之后。

> 可运行验证：[[重定向与缓存-验证脚本.js]] —— 本地 HTTP 服务器 + 浏览器式缓存客户端，实测 301 跟随、新鲜命中 0 请求、no-cache→304、no-store 全量、max-age=0→304、If-Modified-Since→304。

### 3.3 实测：重定向与缓存（Node 本地服务器）

环境：Node 26 本地 HTTP 服务器 + 模拟浏览器缓存客户端（内存缓存 + 新鲜度判定 + 条件请求）。

**① 301 自动跟随**：`GET /old` → 服务器回 `301 Location:/landing` → 浏览器自动再请求 `/landing` → 最终 `200`。业务侧只见最终 200，中间多 1 次往返。

**② 新鲜缓存命中 = 0 网络请求**：`/new`（`Cache-Control: max-age=60`）第一次访问写缓存；第二次访问直接命中内存缓存，**服务器完全没收到请求**。

**③ no-cache + ETag（每次都校验，但 304 省响应体）**：

| 访问 | 服务器响应 | 响应体 |
| --- | --- | --- |
| 第 1 次 | 200（全量） | 100B |
| 第 2 次 | 304（带 If-None-Match 校验） | **0B** |
| 第 3 次 | 304 | **0B** |

**④ no-store（永不缓存）**：第 1、2 次都是完整 200、各 100B，本地不留副本。

**⑤ max-age=0 + ETag**：立即过期 → 条件请求 → 304 复用本地，省 80B。

**⑥ If-Modified-Since（时间戳校验）**：语义同 ETag，省 90B。

**汇总**（本实验全流程）：真实网络请求 **12** 次；缓存命中/复用（未全量下载）**5** 次；网络下载响应体 **537B**。若完全不缓存，响应体总量约 **967B**（省约 44%），且 `/new` 第 2 次那 1 次网络往返被完全省掉。

> 结论：**缓存的价值 = 「重复访问时把网络请求数降为 0（新鲜命中），或把全量下载降为 304 空响应体（协商命中）」**。重定向的价值 = 站点迁移时旧地址不失效，但对性能是纯开销，能少则少。

## 4. DNS 解析（域名 → IP）

浏览器拿域名，本地缓存优先、逐级向上查询：

```
[客户端] 浏览器缓存 → hosts → 系统解析层（Chrome 绕过系统缓存直连 DNS / Firefox 用系统缓存）
[网络侧] 路由器缓存 → 本地 DNS（运营商/公共 DNS）
                                              ↓ 查不到
                          根域名服务器 → 顶级域名服务器（.com）→ 权威域名服务器
                                              ↓
                                   拿到目标 IP，并逐级缓存
```

- 查询方式：**迭代查询**（本地 DNS 依次向上问，自己聚合答案）；客户端到本地 DNS 通常是递归查询。
- 缓存分级：浏览器、OS、路由器、本地 DNS 各级都有 TTL 缓存。**命中缓存则 DNS 耗时≈0**（实测见下）。⚠️ 浏览器缓存与系统缓存是**两套平行存储、非串行**——Chrome/Edge 自带解析器**绕过**系统缓存，Firefox 走系统 `getaddrinfo`（见 §2.3）。
- 一个域名解析完，浏览器还会做 **HSTS 检查 / HTTP 升级**（若该站点在 HSTS 预加载列表，强制 HTTPS）。

### 实测：DNS 耗时

> Chrome headless + 本地服务器（`127.0.0.1` 无需 DNS），`domainLookupStart≈domainLookupEnd`，DNS 段 **0ms**——因为本地回环地址命中系统缓存。真实公网域名的 DNS 耗时通常在 **10~100ms**，取决于缓存与解析路径深度。

### 直接输入 IP：跳过 DNS 解析

> **结论：输入 IP 地址时，浏览器完全跳过 DNS 解析——IP 本身就是地址，无需查缓存、也无需任何网络 DNS 查询，直接把该 IP 用于 TCP 连接。** 但代价是**没有 SNI**，HTTPS 虚拟主机（一个 IP 挂多个域名）和证书 SAN 校验会失败，所以实际中很少直接输 IP 访问 HTTPS 站点。

- 实测（`dns.lookup`，本地机器）：`127.0.0.1` / `192.168.1.1` 直接返回自身 **0.15~0.47ms**（不发起任何查询）；`www.baidu.com` 走真实解析 **6.94ms**。IP 与域名差一个数量级。
- **跳过的不只是 DNS，还有域名携带的额外能力**：
  - **SNI（Server Name Indication）**：HTTP/2/TLS 依赖客户端在握手时上报域名，服务器据此选虚拟主机。输 IP 没有 SNI → **无法路由到正确的虚拟站点**。
  - **证书校验**：TLS 证书的 SAN 字段通常只含域名、不含 IP → 输 IP 访问 HTTPS 常报「证书不匹配」。
  - **HTTP/2**：H2 协商（ALPN）不依赖域名，但许多站点/场景仍以域名为前提；实际中 IP 直连多以 HTTP/1.1 为主。
- 浏览器仍可能做 **reverse DNS（反查 IP→域名）**，但这是日志/安全用途、**不阻塞导航**，不是「解析 IP」。
- **面试速记**：输 IP 跳过 DNS，但丢 SNI/证书匹配 → 虚拟主机和 HTTPS 用不了 → 实际很少直接输 IP；且域名命中缓存时 DNS 也≈0，跳过 DNS 省的时间在真实导航里并不明显。

> 可运行验证：[[DNS解析路径-验证脚本.js]] —— `lookup('127.0.0.1')` 直接返回自身、0ms；`lookup('www.baidu.com')` 走真实解析。

### 为什么挂 VPN 才能访问外网？（GFW 与 DNS 的关系）

> **结论：访问不到外网不是因为「运营商 DNS 没有外网缓存」，而是因为连接层被 GFW 封锁**——DNS 解析大多能成功，卡在 TCP 连接（IP 封锁）和 TLS/SNI 检测。挂 VPN 是把流量加密走隧道从境外节点出口，绕过 IP/SNI 封锁，不是「借用境外 DNS 缓存」。

本地实测（`dns.resolve4` + TCP 连接测试）：

| 域名 | DNS 解析 | TCP:443 连接 | 说明 |
| ---- | -------- | ------------ | ---- |
| `www.baidu.com` | ✅ 180.101.49.44 | ✅ 通 | 正常 |
| `www.github.com` | ✅ 20.205.243.166 | ✅ 通 | 正常 |
| `www.google.com` | ✅ 185.45.5.35 | ❌ 不通/超时 | **能解析、连不上** |
| `www.youtube.com` | ✅ 104.244.42.197 | ❌ 不通/超时 | **能解析、连不上** |
| `www.facebook.com` | ✅ 69.171.235.22 | ❌ 不通/超时 | **能解析、连不上** |

- **关键：被墙域名照样能解析出 IP** → 证明「访问不到」与 DNS 解析/缓存无关，卡在连接层。
- **DNS 缓存只影响「快不快」，不影响「能不能访问」**：任何地区的递归 DNS 都能解析全球域名（它不管"该不该被墙"）；本地没缓存顶多多几十 ms 去上级查，不会导致访问不到。
- **"访问不到"真正卡在哪（由浅到深）**：
  1. **DNS 解析**：大多能通（上面已证明）。
  2. **TCP 连接（IP 封锁）**：被墙站点 IP 直接不可达 → 超时（Google/YouTube/Facebook 即此例）。
  3. **TLS/SNI 检测**：少数 IP 能连，但 ClientHello 里的 SNI 被识别 → RST 重置。这就是「IP 能 ping 通但浏览器打不开」的原因。
- **VPN 真正做了什么**：
  - 把所有流量（含 DNS 查询）**加密封装进隧道**，经境外节点出口 → GFW 看不到你访问的域名，也无法按 IP/SNI 阻断。
  - DNS 在隧道内/出口解析，解析出的是真实全球可达 IP。
  - 是**绕过封锁/检测**，不是「借用境外 DNS 缓存」——没 VPN 时就算手动指定香港 DNS，流量仍直连、IP 仍被墙，照样访问不了。
- **与「直接输 IP」的联动**：输 IP 连 SNI 都没有，被墙站点直接裸奔 IP 挨封，更容易失败。
- **面试速记**：访问不了外网 = DNS 能解析但连不上（IP/SNI 被墙）→ 不是缓存问题 → VPN = 隧道加密 + 境外出口绕过封锁，不是借用境外 DNS 缓存。

> 可运行验证：[[DNS解析路径-验证脚本.js]] —— `dns.resolve4` + TCP 连接测试，复现「能解析、连不通」。

## 5. TCP 三次握手（建立可靠连接）

浏览器拿到 IP（域名解析所得，或输入 IP 直接得到），发起 TCP 连接（HTTP/1.1 每个新导航默认一次；HTTP/2 多路复用同一连接）：

```
① Client ── SYN ─────────────▶ Server    （请求同步，seq=x）
② Client ◀── SYN+ACK ────────── Server    （确认+请求同步，ack=x+1, seq=y）
③ Client ── ACK ─────────────▶ Server    （确认，ack=y+1）→ 连接建立
```

- 前两次握手消耗 **1 个 RTT**，第三次纯本地确认，不再等网络。
- 对 HTTP 请求而言，TCP 握手期间**不能发数据**——这是 HTTP/1.1 慢的主要来源之一。
- 优化：**HTTP/3 (QUIC)** 把「TLS + 连接建立」合并成 **0-RTT/1-RTT**，显著降低握手成本。

[[TCP 三次握手（建立连接）+ 四次挥手（断开连接）]]
[[TCP 初始序列号 ISN（Initial Sequence Number）]]
#### 标准教科书说法：TCP 建立连接耗时 **1 RTT**

> RTT 定义：**从发送报文，到收到对端对此报文的 ACK 的时间**。

- Client 发出 `SYN`；
- 收到 `SYN+ACK`，这个 `SYN+ACK` 就是对 Client SYN 的 ACK。 👉 **从发 SYN 到收到 SYN+ACK，这一段，正好是 1 个完整 RTT** ✅

> 重点：**第三次握手的 ACK，是 Client 发给 Server，Client 不需要等待这个 ACK 的确认！** TCP 不要求对 “ACK 报文” 再回复 ACK。 客户端收到`SYN+ACK`那一刻，**客户端侧连接已经进入 ESTABLISHED**，可以直接发业务数据了。 第三次的 ACK 只是单向发给服务端，服务端收到之后服务端才变为 ESTABLISHED。 这个 ACK 报文是**异步发出去，客户端不需要等待它回来**，不计入握手 RTT。

如果把服务器收到 ACK 的时间也算入的话那就是1.5个RTT


## 6. TLS 握手（HTTPS 专属）
[[TLS12和TLS13的区别]]

> HTTPS = HTTP over TLS over TCP。HTTP 明文访问**没有这一步**。

```
① ClientHello ──支持的加密套件、TLS版本、随机数
② ServerHello ──选定套件、服务器随机数 + 证书链
③ 客户端验证证书（信任链、域名、有效期）→ 生成预主密钥
④ 密钥交换（RSA 或 ECDHE）→ 双方派生会话密钥
⑤ Finished 互相确认 → 后续数据对称加密传输
```

- TLS 1.3 握手只需 **1-RTT**（比 1.2 少一次往返），首次访问比 HTTP 多 **2 个 RTT 左右**。
- 连接复用（keep-alive）时二次访问**跳过握手**。

### 实测：TLS 耗时

> 本地 HTTP 服务器无 TLS，`secureConnectionStart=0` → **本实验 TLS 段不存在（null）**。真实 HTTPS 站点 TLS 握手约占 1 个额外 RTT（TLS1.3），是「为什么上 HTTPS 要配 HTTP/2 + 连接复用」的原因之一。

## 7. 发送 HTTP 请求 → 服务器处理 → 返回响应

1. 浏览器组装请求报文（**请求行 + 请求头 + 请求体**），如 `GET /index.html HTTP/1.1`、`Host`、`Cookie`、`User-Agent`、`Accept` 等。
2. 服务器（Nginx/Apache）接收 → 转发给后端（PHP/Java/Node）处理业务 → 组装响应（**状态行 + 响应头 + 响应体**）。
3. HTML 作为响应体，通过 TCP 流式返回浏览器。
4. **响应回来后的分支**：若是 `3xx` → 回到 §3 的前置逻辑跟随重定向；若是 `304` → 用 §3 的缓存副本；若是 `200` → 写入缓存（按 §3 的缓存头），进入渲染链。

> 关键节点：`requestStart`（发请求）→ `responseStart`（**收到第一个字节，TTFB 结束点**）→ `responseEnd`（HTML 下载完成）。

## 8. TCP 四次挥手（可选）

- HTTP/1.1 默认 **keep-alive 长连接**，导航后连接通常**不立即断开**，供后续资源请求复用。
- 只有显式关闭（服务器 `Connection: close` / 超时 / 客户端关闭）才执行四次挥手：
  ```
  ① Client ── FIN ──▶ Server
  ② Client ◀── ACK ──── Server
  ③ Client ◀── FIN ──── Server   （服务器关闭它那一侧）
  ④ Client ── ACK ──▶ Server
  ```
- 对本主题而言：**挥手发生在页面渲染之后**，不影响首屏。

## 9. 渲染链：HTML → DOM → CSSOM → 渲染树 → 布局 → 绘制 → 合成

HTML 到达后，浏览器进入渲染管线（严格按序，见 [[Update Rendering 阶段详解]]）：

```
HTML字节流 → 字符 → Token → 节点 → DOM树（边下载边解析）
                                  └→ 遇 <link>css → CSSOM
DOM + CSSOM → 渲染树(Render Tree，剔除 display:none)
           → 布局 Layout(几何尺寸/位置，即回流 Reflow)
           → 绘制 Paint(颜色/背景/文字 → 图层)
           → 合成 Composite(GPU 合成分层 → 屏幕)
```

### 关键：解析时的阻塞语义（实测重点）

| 资源/位置 | 是否阻塞 DOM 解析 | 是否阻塞渲染(FCP) | 说明 |
| --------- | ----------------- | ----------------- | ---- |
| `<link>` CSS 在 `<head>` | ❌ 不阻塞解析 | ✅ **阻塞**（render-blocking） | 首屏前必须拿到 CSSOM |
| 同步 `<script>`（无 defer/async） | ✅ **阻塞解析** | ✅ | 可能改 DOM，必须等它执行完 |
| `<script async>` | ✅ 阻塞（下载不阻塞，执行时阻塞） | 视情况 | 下载并行，执行仍抢解析 |
| `<script defer>` | ❌ 不阻塞解析 | ✅ 阻塞在 DOMContentLoaded 前 | 解析完、DOMContentLoaded 前按序执行 |
| `<img>` 图片 | ❌ 不阻塞解析 | ❌（但可能成为 LCP） | 解码渲染完才上报 LCP |

> **CSS 与 JS 的交互坑**：`<head>` 里的 CSS 会**阻塞其后同步 `<script>` 的执行**（规范：脚本要等前置样式表就绪）。实测中 `slow.css` 延迟 350ms，把 `domInteractive` 也推到 500ms+，就是这个机制。

### 实测：慢 CSS / 慢图片 对首屏的影响（Chrome headless，3 次采样）

环境：本地 HTTP 服务器，`slow.css` 延迟 **350ms**，`slow.png` 延迟 **600ms**；Chrome 151 headless；机器不同数值有差异，**相对倍率稳定**。

**① 有渲染阻塞 CSS 的标准页 vs 无阻塞基线页**

| 指标 | 基线页(无 slow.css) | 标准页(含 slow.css) | 差距 |
| ---- | ------------------- | ------------------- | ---- |
| FCP 首次内容绘制 | 28ms | 532ms | **≈19×** |
| DOMContentLoaded | 12ms | 526ms | **≈44×** |
| load | 12ms | 651ms | **≈53×** |

**② 标准页逐阶段耗时（3 次采样中位数）**

| 阶段 | 耗时 | 占首屏比例 | 说明 |
| ---- | ---- | ---------- | ---- |
| DNS | 0ms | — | 本地回环命中缓存 |
| TCP | 0ms | — | 本地服务器，握手瞬间完成 |
| TLS | — | — | HTTP 无此段 |
| TTFB（请求→首字节） | ~6ms | 1% | 服务器本机处理，无真实网络 RTT |
| 下载 HTML | ~1ms | <1% | 文档极小 |
| **HTML解析→DOMInteractive** | **~500ms** | **77%** | 被 `slow.css` 阻塞的脚本等待占大头 |
| FP / FCP | ~532ms | — | 首帧渲染 |
| LCP | ~656ms | — | 最大内容（slow.png 600ms 后到达） |

> 结论：**这个页面首屏 77% 的时间耗在「解析被渲染阻塞 CSS 拖住」**——CSS 不阻塞解析本身，但阻塞其后脚本执行，连带推迟 `domInteractive`。图片 600ms 延迟**不阻塞**解析（`DCL` 不因它推迟），但会成为 LCP 的组成部分。

> 可运行验证：[[导航时序全过程-demo.html]] —— 打开后瀑布图可见 `domParse` 段（红紫）横跨大半时间轴，`slow.css` 资源条（start≈17ms）与 LCP（蓝，~650ms）形成对比。

## 10. 关键时间节点（Performance 指标）

| 指标 | 全称 | 含义 | 本实验(标准页) |
| ---- | ---- | ---- | -------------- |
| **TTFB** | Time To First Byte | 发请求到收到第一个字节 | ~6ms |
| **FP** | First Paint | 第一次绘制像素 | 532ms |
| **FCP** | First Contentful Paint | 第一个内容(文字/图片/画布)渲染 | 532ms |
| **LCP** | Largest Contentful Paint | 最大内容块渲染，核心体验指标 | 656ms |
| DCL | DOMContentLoaded | DOM 解析完 + 阻塞脚本执行完 | 526ms |
| load | Load | 所有同步资源加载完 | 651ms |

> LCP 是**动态更新**的：最大内容可能变（图片后到会替换文字）。以「最后一次上报」为准。规范见 W3C Long Tasks / Largest Contentful Paint。

## 11. 为什么这么设计？（背后取舍）

- **缓存先于网络**：本地读取是 μs 级，网络是几十 ms 级 RTT——「速度 > 新鲜度」，所以才有新鲜期和过期后的协商校验，用「最终一致性」换「极速命中」。
- **no-cache 不是「不缓存」**：历史命名混乱。它要的是「每次确认」而不是「每次全量」，省响应体、不省请求。取舍：**一致性 > 省流量**。
- **301 可缓存、302 不缓存**：301 是「永久」语义，浏览器敢大胆缓存免去重复解析；302 是「临时」，缓存会错误地长期指向过期位置。取舍：**正确性 > 便利**。
- **重定向设上限**：防死循环（/a→/b→/a）。取舍：**健壮性 > 无限信任服务器**。
- **CSS 阻塞渲染**：首屏必须保证样式一致（避免 FOUC 无样式闪烁）。浏览器宁可在 CSSOM 就绪前不画，也不愿画了再闪。取舍：**首屏正确性 > 首屏速度**。
- **JS 阻塞解析**：脚本可能 `document.write`/改 DOM，解析器无法预知，只能停下等它执行完。取舍：**确定性 > 并行性**。这也是 `defer`/`async`/`module` 存在的意义——把「确定性」主动让渡给开发者。
- **图片不阻塞解析**：图片与 DOM 结构无关，浏览器只需留出占位。取舍：**并行下载 > 渲染完整性**；代价是图片晚到会触发布局抖动（CLS），由 `width/height` 占位解决。
- **为什么有 TTFB 分界线**：网络与渲染是两个独立子系统，TTFB 衡量「后端 + 网络」，FCP/LCP 衡量「前端渲染」。面试分层答，能体现系统思维。

## 12. 规避 / 实践

| 问题 | 手段 | 对应阶段 |
| ---- | ---- | -------- |
| TTFB 高 | CDN、HTTP/2/3、服务端缓存、边缘计算 | 网络链 |
| 重定向拖慢首屏 | 减少/合并重定向（避免链式）、CDN 上直接配目标 | 前置逻辑 |
| 静态资源反复下载 | `Cache-Control: max-age` 长缓存 + hash 文件名（内容变→URL 变→自然失效） | 前置逻辑 |
| 304 频繁（每次都要校验） | 长缓存 + `immutable`，或把可变的塞进 URL | 前置逻辑 |
| 敏感页被缓存 | `no-store` | 前置逻辑 |
| 首屏被 CSS 拖 | 关键 CSS 内联 + `media` 拆分非关键样式、`<link rel="preload">` | 渲染链 |
| 首屏被 JS 拖 | `defer` 放 body 底部、`async` 独立脚本、`<script type="module">` | 渲染链 |
| 图片成为 LCP 瓶颈 | `loading="lazy"` 首屏外的图、`fetchpriority="high"` 首屏图、`width/height` 防 CLS | 渲染链 |
| 重复连接握手 | keep-alive 连接复用、HTTP/2 多路复用、`dns-prefetch`/`preconnect` | 网络链 |
