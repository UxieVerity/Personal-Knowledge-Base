# 播放器缓冲策略

> **结论：缓冲策略的本质是「一个水位目标 + 两个动作」——**buffered 长度低于水位就等（保流畅），高于水位就丢旧数据/追帧（保延迟和内存）**。点播追求「大 buffer 防卡顿」，直播追求「小 buffer 保延迟」——两个目标互相拉扯，水位就是定价。实测数据基础：appendBuffer 毫秒级、buffered 即时可查（[[MSE最小播放器-验证demo]] §3），策略层全是纯前端逻辑，浏览器不帮你管——`<video>` 自带的黑盒水位（固定 ~20s）不可定制，这就是自研⑤同步层的存在理由。**

> 可运行验证：水位判定逻辑的所有输入来自 [[MSE核心机制]] §2.3（buffered 只读区间）与 [[MSE最小播放器-验证demo]]（buffered 实时读数面板）；卡顿判据的实测见本篇 §3。

## 1. 背景：缓冲解决什么矛盾

下载速度 ≠ 消费速度：

```
码率 4Mbps，下载 6Mbps → buffer 涨（每秒存 0.25MB）
码率 4Mbps，下载 2Mbps → buffer 跌（每秒耗 0.25MB，耗尽=卡顿）
```

buffer 的作用是「以空间换时间」：攒一段存量，扛住短时下载波动。但 buffer 不是越大越好：

| buffer 过大 | buffer 过小 |
| --- | --- |
| 首开慢（要先攒） | 频繁卡顿 |
| 延迟高（直播致命） | 弱网体验差 |
| 内存占用大 | — |
| 直播回看丢失多（eviction） | — |

## 2. 定义/原理：水位模型

```
bufferedLen = buffered.end(current区间) - currentTime   ← 当前存量（秒）

                    ┌──────────┐
  目标水位 target ──→│          │  ← 策略围绕它做增减
                    └──────────┘
低于 lowWater  → 等待/降档（保播放）
高于 highWater → 主动丢旧(remove)/追帧/暂停下载（保延迟与内存）
```

| 参数 | 点播典型 | 直播典型 | 作用 |
| --- | --- | --- | --- |
| 初始起播水位 | 3~5s | 1~2s | 首开 vs 流畅 |
| 目标水位 | 20~60s | 3~5s | 稳态存量 |
| 低水位 | 2s | 1s | 触发等待/降档 |
| 保留窗口（直播） | — | 5~10s | `sb.remove()` 的依据 |

**追帧（直播专属）**：存量超过目标 = 延迟超标 → `playbackRate = 1.1~1.5` 把 currentTime 快速推回水位内（1.5× 播 10s 追回 ~3.3s）。下限：Chrome 的 playbackRate 最低 0.0625、最高 16，但 >2× 的音调处理需要保真模式（preservesPitch），追帧一般用 1.1~1.5× 保听感。

## 3. 实测

### 3.1 卡顿判据的实测区分（两种卡顿）

> 🔗 数据源：`video.buffered` + `getVideoPlaybackQuality()`，读数方法见 [[MSE最小播放器-验证demo]] 面板。

| 卡顿类型 | buffered 表现 | droppedVideoFrames | 判定 |
| --- | --- | --- | --- |
| **带宽型**（下载跟不上） | 存量耗尽（currentTime 贴住 buffered.end） | 正常 | 治理：ABR 降档/换 CDN |
| **性能型**（解码/渲染跟不上） | 存量充足（buffered 远超 currentTime） | **持续增长** | 治理：降分辨率/关滤镜/查解码通道 |

**排查卡顿先分这两类**——带宽型去优化网络层（loader/ABR），性能型去优化解码渲染层（decode/render）。混着治是播放器调试最常见的弯路。

### 3.2 水位参数对首开/卡顿的量化关系（实测基准）

appendBuffer 毫秒级（[[MSE最小播放器-验证demo]] §3）说明「喂数据」不是瓶颈，首开时间的真实构成为：

```
首帧时间 ≈ 建立连接 + 等首个分片(含 I 帧) + 起播水位攒够时间
```

起播水位从 5s 降到 1s，首开直接省 4s——代价是 1s 存量扛不住任何下载抖动，起播后 30s 内卡顿概率上升。**工业实践：低起播水位 + 起播后快速补水位（激进预取）**，两头都占。见 [[首开时间优化]] 的完整拆解。

### 3.3 eviction 与主动 remove 的分工（实测）

- 浏览器自动 eviction：容量压力下**从最旧静默删段**（无报错事件），见 [[MSE核心机制]] §3.3。
- 主动 `sb.remove(start, end)`：掐关键帧边界、可预知的删除——直播保留窗口管理用这个。

**实测结论**：依赖浏览器 eviction 的直播播放器会出现「回看拖拽到已删区间」的异常（buffered 起点漂移不可控），主动管理是唯一可靠方案。

## 4. 为什么这么设计？（背后取舍）

**为什么浏览器不把水位参数开放？**
- 水位策略和产品形态强绑定：点播站要大水位，直播要小水位，会议要极小水位。浏览器 `<video>` 只能取折中（内部固定策略）。MSE 给 `buffered`/`remove()`/`playbackRate` 这三个原子件就是「策略开放」的边界——**黑盒给设施，白盒给策略**。

**为什么「攒够水位才起播」而不是「到帧就播」？**
- 起播后前几秒是卡顿高发期（下载刚建立、波动最大）。攒水位 = 用首开时间买「起播成功率」。工业上的折中是**水位自适应**：网络快（RTT 低）少攒、网络慢多攒——和 TCP 慢启动「探测后定速率」同构。

**为什么直播水位低反而还要「丢旧」？**
- 直播消费点是「现在」，存量代表延迟。存量涨 = 你落后于主播 = 需要追帧或丢旧回到近实时。点播存量是资产，直播存量是负债——**同一个 buffer，两种语义**。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 点播 | 大水位（20s+）+ 起播自适应 + eviction 放给浏览器 |
| 直播 | 小水位（3~5s）+ 超水位追帧 1.1~1.5× + 主动 remove 保留窗口 |
| 卡顿排查 | 先看 buffered 与 dropped 分清带宽型/性能型（§3.1 表） |
| 弱网 | 低水位立即降档（ABR）优先于等待，见 [[ABR自适应码率]] |
| 首开 | 起播水位自适应 + 起播后激进补水位，见 [[首开时间优化]] |

## 6. 面试速记

> **30 秒版**："缓冲策略=水位模型：buffered 长度低于低水位就等待或降档，超过目标水位就追帧或丢旧。点播水位大（存量是资产），直播水位小（存量是延迟负债），超水位用 1.1~1.5 倍速追回。排查卡顿先分两类：buffered 耗尽是带宽型治网络，buffered 充足但 dropped 增长是性能型治解码。浏览器黑盒水位不可定制，MSE 的 buffered/remove/playbackRate 就是策略开放的边界——自研播放器的缓冲层全部价值在这三个原子件上组合。"
