# 直播CDN分发链路

> **结论：直播 CDN 链路 = 推流 → 源站 → (转码/录制) → 边缘节点 → 观众，卡顿分布的规律是「离观众越近的环节，卡顿占比越大」——**播放端到边缘的「最后一公里」通常占卡顿原因的 60%+**，所以播放器观测（buffered/下载速率/节点切换）比服务端监控更能定位真实卡顿。1000 人观看 = 码率 × 并发的带宽（4Mbps × 1000 = 4Gbps），靠的就是「一份内容缓存到 N 个边缘」的复制经济学——**直播的成本模型 = 带宽 × 并发，这就是 ABR 降档 1Mbps 能省 75% 成本的原因（[[ABR自适应码率]]）。**

> 可运行验证：播放端观测手段见 [[MSE最小播放器-验证demo]] 面板（buffered/下载速率）；网络层探测脚本复用 [[DNS解析路径-验证脚本.js]]（就近接入的第一环）与 [[CDN与压缩-验证脚本.js]]（CDN 命中验证）。

## 1. 背景：为什么直播必须 CDN

```
不经 CDN： 源站上行带宽 = 码率 × 观众数（全部涌向源站）→ 源站带宽/连接数爆掉
走 CDN：   源站上行 = 码率 × 1（每边缘节点回源一份）
           观众下行 = 从最近的边缘节点取（地理就近 + 负载分散）
```

| 环节 | 角色 | 关键指标 |
| --- | --- | --- |
| 推流端 | RTMP/WebRTC 上行 | 推流稳定性、GOP/B帧参数 |
| 源站（origin） | 收流、鉴权、转封装 | 首开时的回源延迟 |
| 中间层（可选） | 转码（多码率 ladder）、录制、截图 | 转码延迟加入链路 |
| 边缘节点（edge） | 就近分发 | **命中命中率、回源次数** |
| 观众端 | 拉流播放 | 下载速率、buffered |

**直播 CDN 与静态 CDN 的核心差异**：内容是「活的」——分片过期即弃（直播窗口外无缓存价值）、必须支持流式透传（FLV）或高频刷新的索引（HLS m3u8）、回源是持续的流（不是一次性对象拉取）。

## 2. 定义/原理：链路各段的延迟与卡顿来源

### 2.1 延迟账（以 HTTP-FLV 为例）

```
端到端延迟 = 推流端缓冲(0.1s) + 上行传输(0.1s) + 源站处理(0.1s)
           + 边缘透传(0.1~0.5s) + 播放端水位(1~3s) ≈ 2~5s
```

### 2.2 卡顿归因分布（工业经验值）

| 卡顿原因 | 占比（经验） | 播放端可观测信号 |
| --- | --- | --- |
| **观众侧网络（最后一公里）** | **60%+** | buffered 停滞 + 下载速率波动（WiFi/4G 切换） |
| 边缘节点问题（过载/跨区） | 10~20% | 同区域批量卡顿、节点 IP 变化 |
| 回源/源站问题 | 5~10% | 全量卡顿（所有边缘同时） |
| 播放器 bug | 5~10% | 与网络无关的规律性卡顿 |

**「先看是不是普遍卡（全量 vs 个例）再定位段」**——普遍卡查源站/转码，个例卡查观众网络/边缘调度。

### 2.3 首开与就近接入

```
首开路径：观众 → DNS 调度（就近边缘 IP）→ 边缘命中？
  命中 → 直接拉流（快）
  未命中 → 边缘回源（逐级或直连源站）→ 首开时间 + 回源 RTT
```

DNS 调度是就近接入的第一环（实测见 [[云服务商DNS-验证脚本.js]] 的解析路径差异）；直播特有的问题是**新流首播时全网边缘都没缓存**——首次回源延迟直接打在第一个观众的脸上（冷启动）。

## 3. 实测

### 3.1 播放端卡顿定位的实测信号

> 🔗 观测工具：demo 面板（[[MSE最小播放器-验证demo]]）+ DevTools Network：

| 信号组合 | 诊断 | 动作 |
| --- | --- | --- |
| buffered 停滞 + 下载速率 < 码率 | 带宽不足（最后一公里） | ABR 降档 / 提示网络 |
| 下载速率正常但突发归零 | 边缘/链路抖动 | 重连换节点 |
| 下载速率正常 + droppedVideoFrames 涨 | 性能型卡顿（非网络） | 降分辨率/查解码 |
| 首包 TTFB 高（>1s） | 边缘未命中回源 / 调度偏远 | 换调度策略/预热 |

**播放端每天产出的这些信号就是 CDN 质量的地面真相**——服务端监控看的是聚合，播放端看的是每个用户的实际体验。

### 3.2 带宽×并发的成本实测账

> 🔗 [[码率帧率分辨率与带宽]] §2.1/§3.1 实测码率：

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| 1000 人看 1080p@5M | 5Mbps × 1000 | 5 Gbps（≈ 每月数十 TB 流量） |
| 全员 ABR 降到 720p@2.5M | 2.5Mbps × 1000 | 2.5 Gbps（**-50%**） |
| 全员 480p@1M | 1Mbps × 1000 | 1 Gbps（**-80%**） |

**ABR 的经济意义**：观众端自动降档 = 平台带宽成本自动下降——弱网时降档既是体验优化也是成本优化，一体两面。

### 3.3 CDN 命中的验证方法（复用静态 CDN 实测链）

```
# 响应头判断命中（直播分片/静态资源通用）
curl -sI https://cdn.example.com/seg_100.ts | grep -i "x-cache"
# X-Cache: HIT  → 边缘命中
# X-Cache: MISS → 回源（首播冷启动常见）
```

直播特有：分片 URL 带 session/防盗链参数 → **相同内容不同 URL = 缓存失效**——调度与防盗链设计必须与缓存键对齐（工业踩坑高发区）。

## 4. 为什么这么设计？（背后取舍）

**为什么边缘节点「缓存」而不是「全量转推」？**
- 转推（每个边缘都有一条源到边缘的流）= 上行带宽 × 边缘数；缓存/回源 = 只有观众到达时才回源拉流。**爆款少、长尾多的直播分布下，按需回源的总带宽远低于全网转推**——树状分发（源→中间→边缘）就是这么长出来的。

**为什么播放端观测比服务端监控更真？**
- 服务端只看得到「我发出的」，观众看到的是「我收到的」——中间隔着最后一公里（观众 WiFi/4G）这段服务端完全盲区。**体验数据的采集点必须在体验发生的地方**（RUM 思想），播放器上报（卡顿率/首开/码率分布）就是直播平台的 QoE 数据源。

**为什么转码放在源站侧而不是边缘？**
- 转码是 CPU 重活（一路 1080p 占数核），放边缘 = 每个边缘都配转码集群（利用率低）；放源站集中转一次、各边缘分「现成的多档流」——**计算集中、分发分散**，与「缓存命中率优先」的 CDN 经济学一致。

## 5. 规避 / 实践

| 问题 | 手段 |
| --- | --- |
| 首开慢（冷流） | 边缘预热（推流即向全网边缘推一份）+ 就近调度校准 |
| 卡顿率高 | 先分「个例/普遍」→ 播放端上报分段归因（§3.1 表） |
| 带宽成本高 | ABR ladder 下探（低档）+ 按区域限档 |
| 跨区调度错 | DNS 调度实测校准（[[云服务商DNS-验证脚本.js]] 思路） |
| 防盗链杀缓存 | 缓存键与鉴权参数分离（path 鉴权而非 query 鉴权） |

## 6. 面试速记

> **30 秒版**："直播 CDN 链路：推流→源站（转码集中）→边缘节点（分发分散）→观众，靠『一份内容缓存到 N 边缘』把 1000 人观看的 4Gbps 上行压成源站一份。卡顿分布 60% 在最后一公里——观众自己的网络，所以播放端观测（buffered/下载速率/dropped）比服务端监控更真，先分个例还是普遍再定位段。ABR 降档既是体验优化也是成本优化：全员从 5M 降到 1M 带宽省 80%。直播 CDN 和静态 CDN 的区别是内容是活的：分片过期即弃、回源是持续流、防盗链参数会杀缓存键。"
