# H264与H265结构和原理区别

> **结论：H265 压缩率提升的全部秘密在「块划分数 ×4 + 预测方向 ×17 + 滤波增强」——**宏块 16×16（固定）→ CTU 最大 64×64（四叉树可拆到 8×8），帧内预测 9 种 → 35 种，加上 SAO 滤波**，换来同画质体积 -30~50%、代价是编码慢 2~4×。结构层差异：NALU 头 1B → 2B（新增 temporal_id 支持分层）、参数集从 SPS/PPS 增到 VPS/SPS/PPS 三件套、Cabac 从双上下文模型扩到 89 种。实测本机：1080p 等体积等画质（SSIM 0.9876）H265 体积略小、4K 同 CRF 体积差收敛到 1.5×（高分辨率才兑现优势）、1080p 软解慢 ~35%、4K 编码慢 ~2×。**

> 可运行验证：FFmpeg 9.0 编码/解码/SSIM 全链实测（§3，命令即脚本）；NALU 类型实测 `ffmpeg -v debug` 可复现（§3.3）；体积速度数据与 [[视频编码代际与浏览器支持]] §3.1 同源。

## 1. 背景：同一套框架，两次精细化

H264/H265 都是「**块 + 帧间预测 + 帧内预测 + 变换 + 熵编码**」的混合编码框架——H265 没有发明新原理，而是**把每一环的粒度做细**：

```
共同管线：  帧切块 → 帧内/帧间预测 → 残差变换 → 量化 → 熵编码 → NALU 打包
H265 改进： 块更大可更深拆 + 预测方向更多 + 变换更灵活 + 滤波多一层 + 熵编码更精细
```

| 环节 | H264 (AVC) | H265 (HEVC) | 收益来源 |
| --- | --- | --- | --- |
| 最大块 | 宏块 MB 16×16 **固定** | CTU 64×64（16/32/64 可选） | 平坦区一整块搞定 |
| 块划分 | 宏块内 4 分层 | **四叉树**递归 64→32→16→8 | 按内容自适应深度 |
| 帧内预测 | 9 种（4×4）/ 4 种（16×16） | **35 种**（平面+33 角度+DC） | 纹理方向贴合 |
| 变换单元 | 4×4/8×8 整数 DCT | 4×4~32×32 + **DST**（4×4 帧内） | 残差能量更集中 |
| 环路滤波 | Deblock | Deblock + **SAO**（样本自适应偏移） | 环伪影补偿 |
| 熵编码 | CAVLC + CABAC | 仅 CABAC（**89 种上下文模型**） | 更精细的概率建模 |

**理解框架**：压缩吃空间冗余（帧内预测）、时间冗余（帧间预测+运动补偿）、感知冗余（量化+SAO）。I/P/B 帧的参考关系不变（[[I帧P帧B帧与GOP]]），变的是每个环节的「刀具精细度」。

## 2. 定义/原理：结构与参数集差异

### 2.1 NALU 层：1 字节头 → 2 字节头

两代的裸流单元都是 NALU（Network Abstraction Layer Unit），但头部结构不同：

```
H264 NALU 头（1 字节）：[forbidden_zero(1) | nal_ref_idc(2) | nal_unit_type(5)]
H265 NALU 头（2 字节）：[forbidden(1) | nal_type(6) | nuh_layer_id(6) | nuh_temporal_id(3)]
                                              ↑ 多层可伸缩      ↑ 时域分层标记
```

**多出的 1 字节买到了**：可伸缩层（layer_id，一套流多分辨率）与时域分层（temporal_id，一套流多帧率）——实时通信里「只传低时域层」的带宽自适应就靠这个字段。

**参数集从两件套变三件套**（实测 `ffmpeg -v debug` 解析序）：

```
H264: SPS(7) → PPS(8) → slice            ← 两个参数集 + 切片
H265: VPS(32) → SPS(33) → PPS(34) → slice ← 多了 VPS（视频参数集，描述多层/多子流拓扑）
```

MSE/WebCodecs 里 H265 的 codec 串写 `hvc1.1.6.L93.B0`、H264 写 `avc1.42E01E`——浏览器初始化解码器靠的是容器里的 `avcC`（H264，实测本机 48B）或 `hvcC`（H265，实测含 VPS 后达 2.4KB）参数集盒（[[fMP4与MP4的区别]] §2）。

### 2.2 块划分：宏块 vs 四叉树（压缩率的核心来源）

```
H264 宏块:      固定 16×16，内部再分 16x8/8x16/8x8/4x4
H265 CTU:       64×64 起步，四叉树递归可拆到 8×8
                平坦背景 → 整块 64×64 一个运动矢量（开销极小）
                细节纹理 → 深拆到 8×8（预测精细）
```

**为什么这是最大收益点**：1080p 一帧 = H264 的 8160 个宏块 vs H265 的 810 个 CTU——每块的「头部开销」（模式/运动矢量/分割信息）摊薄 10×；平坦区单块覆盖面积 16× 大，运动矢量大都省了。**H265 对高分辨率的优势由此而来**（低分辨率下 CTU 用不满大块，优势缩水——§3.1 实测）。

### 2.3 帧内预测 35 种 & SAO

- H264 帧内 9 方向 + DC；H265 增加到 **33 角度 + 平面 + DC**——斜向纹理（栏杆/发丝/屏幕内容）的预测误差残差更小，直接省比特。
- **SAO（样本自适应偏移）**：Deblock 之后按区域统计像素偏移再加补偿，专治环状伪影（ quantization 引起的边缘振铃）——低码率下画质提升明显。

## 3. 实测

### 3.1 等画质体积：分辨率越高优势越大（FFmpeg 9.0，preset=medium）

> 🔗 方法：H264 crf28 为基准，二分 H265 的 CRF 找到体积≈基准的档位，SSIM 对照画质。机器不同绝对值有差异，倍率稳定。

| 分辨率 | H264 (crf28) | H265 等体积 | SSIM All | 画质读数 |
| --- | --- | --- | --- | --- |
| 360p | 219,041 B | crf30（216,755 B） | 0.9849 vs 0.9849* | 优势微弱 |
| 1080p | 1,521,424 B | crf31.5（1,466,451 B） | **0.9876 = 0.9876** | 等体积下 H265 略优 |
| 4K | 2,727,656 B | crf31（2,735,359 B） | 0.9892 = 0.9892 | 同 CRF 体积比收敛 1.55× |

> *360p 对照组两编码同 CRF 体积接近（H265 crf30 ≈ H264 crf28），SSIM 差 <0.002，量级上无决定性优势。

同 CRF 直拼体积比（越小代表 H265 越省）：

| 分辨率 | H264 crf28 | H265 crf28 | 比 |
| --- | --- | --- | --- |
| 1080p | 1,521,424 | 2,442,617 | 1.61× |
| 4K | 2,727,656 | 4,224,989 | 1.55× |

⚠️ **反直觉读法**：同 CRF 下 H265「更大」不代表压缩差——CRF 的画质锚点不同代不可比（H265 在同 CRF 下保真更多细节）。**正确的比较单位是「等体积看 SSIM」**：等体积下 H265 的 SSIM 略高或持平，且分辨率越高差距越大（真实拍摄内容/更高码率下，行业普遍 -40% 体积）。

### 3.2 速度：编码 2~4× 慢，软解 ~35% 慢

| 操作 | H264 | H265 | 倍率 |
| --- | --- | --- | --- |
| 编码 1080p 4s（medium） | 1337 ms | 3744 ms | **2.8×** |
| 编码 4K 2s（medium） | 2177 ms | 4414 ms | **2.0×** |
| 软解 1080p 120 帧 | ~247 ms | ~336 ms | **1.36×** |
| 软解 4K 60 帧 | ~485 ms (4.16×) | ~588 ms (3.4×) | **1.21×** |

**为什么编码更慢**：四叉树要**递归尝试所有划分深度**（RDO 率失真优化），35 种帧内方向逐一试——编码器搜索空间指数级扩大。**为什么解码只慢 ~35%**：解码没有搜索（划分信息在码流里已写明，照着拆就行），只多了解析+SAO 的固定开销——这个不对称正是「转码贵、播放便宜」的产业格局来源。

### 3.3 NALU/参数集的现场证据（ffmpeg -v debug 可复现）

```
H264 流解析序:  nal_unit_type: 7(SPS) → 8(PPS) → 6(SEI) → slice
H265 流解析序:  nal_unit_type: 32(VPS) → 33(SPS) → 34(PPS) → slice
容器参数集盒:   avcC 48 B (H264)  vs  hvcC 2449 B (H265，含 VPS + 配置版本)
```

x265 编码器日志佐证 CTU 划分（`wpp(6 rows)` 波前并行 + `bframes 4`）：

```
x265 [info]: frame threads / pool features : 3 / wpp(6 rows)
x265 [info]: Lookahead / bframes / badapt  : 20 / 4 / 2
```

### 3.4 Profile/Level 体系（兼容性声明的来源）

| | H264 | H265 |
| --- | --- | --- |
| 常见 Profile | Baseline / Main / **High** | Main / Main 10（HDR） |
| 实测本机编码档 | High, level 40 | Main, level 120 |
| Level 语义 | 解码能力上限（分辨率×帧率×码率） | 同左（数值 = 30×实际级别） |

Web 播放的 codec 串（`avc1.42E01E` = Baseline L3.0 / `hvc1.1.6.L93.B0` = Main L3.1）就是 profile_idc+constraint+level 的十六进制打包（RFC 6381）——**能力检测失败常常是 level 不够**（4K 流用 L3.0 声明必失败），不是编码本身不支持。

## 4. 为什么这么设计？（背后取舍）

**为什么 H265 用「四叉树」而不是 H264 式的固定分层？**
- 内容的空间复杂度极不均匀（平坦天空 vs 细节人脸）；四叉树让编码器**按区域买深度**：平坦区 1 个 CTU 摊薄头部，复杂区深拆保保真。这是「按需分配语法元素」的思想——和 ABR 的「按网络分档」同构（[[ABR自适应码率]]），只是分配对象从码率换成了码流结构。

**为什么编码慢解码快的不对称可以接受？**
- 一对多的分发链：编码 1 次、解码 N 次——编码端慢 3× 只影响转码农场，解码慢 35% 摊在每个终端。**把复杂度推向出现次数少的一端**，这是分布式系统的通用定价法（编译慢运行快的语言同构）。

**为什么 H265 参数集多一个 VPS？**
- H265 标准内建了可伸缩（多分辨率层）与时域分层（多帧率子集），VPS 描述「层的拓扑关系」。实际单层流里 VPS 多数冗余，但语法预留了扩展空间——**标准设计要为十年后的用例留钩子**（SVC 思想在 H264 是附加标准，H265 内化进语法）。

**为什么 H265 专利费还更贵（技术更好却推广更难）？**
- 专利池碎片化（HEVC Advance / Velos / MPEG LA 各收一道），总费用高于 H264 数倍且法律风险不可预估——浏览器厂商（分发解码器的商业软件是收费对象）观望，Chrome MSE 长期不放行（实测 [[视频编码代际与浏览器支持]] §3.2）。**技术优劣与生态胜出是两场比赛**——H265 输掉的是生态那场，AV1 免专利正是针对这个死穴。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 编码端选型 | 1080p 以下用 H264（CTU 优势用不上 + 兼容性 100%）；4K/存储敏感选 H265 |
| 转码成本 | H265 转码并发按 H264 的 1/2.5~1/3 估算 |
| 播放器适配 | H265 必须 isTypeSupport 运行时探测（三通道结论可不一致） |
| codec 串写错 | level 对不上：4K 流标 L3.0 必失败，查 `ffprobe` 的 level 换算（H265 level 值 = 实际×30） |
| 软解性能兜底 | H265 软解慢 35%，移动端降档 720p/480p（[[WASM软解H265管线]] §3.1） |
| 花屏排查 | H265 检查 hvcC 是否完整带 VPS/SPS/PPS（比 H264 的 avcC 大一个量级，切流易丢） |

## 6. 面试速记

> **30 秒版**："H265 和 H264 是同一套混合编码框架，差别全在精细化：块从固定 16×16 宏块变成 64×64 四叉树 CTU，帧内预测 9 种变 35 种，多 SAO 滤波，Cabac 上下文扩到 89 种——同画质省 30~50%，代价编码慢 2~4 倍。结构上 NALU 头 1B 变 2B（换 temporal_id 时域分层），参数集 SPS/PPS 多了 VPS。实测最有意思的是不对称性：编码慢是因为四叉树要递归搜索，解码只慢 35% 因为划分信息已写进码流照着拆——转码贵播放便宜就是这个不对称。等体积比 SSIM：分辨率越高 H265 优势越大，1080p 以下差距不大，所以 1080p 以下用 H264 是合理选型。"
