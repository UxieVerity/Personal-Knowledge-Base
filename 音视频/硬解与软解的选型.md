# 硬解与软解的选型

> **结论：硬解 = GPU/专用单元解码（省电、快、但支持矩阵碎片化），软解 = CPU 通用计算解码（全覆盖、可控、但慢且费电）。选型不是二选一而是**决策链：能力检测 → 硬解可用走硬解 → 不可用降级软解 → 软解也不行报错**——本机 Chrome 154 实测：H265 在正常启动（GPU 可用）时 video 标签与 MSE 均可用，但 --disable-gpu 软渲染环境下双双关闭——同一浏览器结论随启动环境漂移，硬解「有没有」只能运行时逐通道探测。这就是自研 SDK `isTypeSupport()` 的第一性依据：**能力检测必须在运行时做，且必须按通道做。**

> 可运行验证：能力矩阵实测见 [[视频编码代际与浏览器支持]] §3.2（canplay-probe 系列脚本）；硬解/软解解码速度实测见本篇 §3（ffmpeg NVDEC vs libx265）；软解全管线见 [[WASM软解H265管线]]。

## 1. 背景：两条解码路径的物理差异

| | 硬解（GPU/专用解码单元） | 软解（CPU 通用计算） |
| --- | --- | --- |
| 实现 | GPU 里的专用解码电路（NVDEC/Intel QSV/Apple MediaEngine） | 软件解码器（ffmpeg/WASM 编译的 dec 库） |
| 速度 | 快（专用流水线，1080p 实时几十路） | 慢（H265 软解实测比硬解路径慢数倍） |
| 功耗 | 低（专用电路能效比高） | 高（CPU 满载） |
| 格式覆盖 | **碎片化**（芯片代次 × 驱动 × OS × 浏览器策略） | **全**（软件实现不依赖硬件） |
| 可控性 | 黑盒（出错只能换路径） | 全控（能裁剪/魔改/逐帧调试） |

**浏览器里的三条硬解通道**：`<video>` 标签（平台管线）、MSE（Chrome 自家管线 + 白名单）、WebCodecs（VideoDecoder，独立开关）。三条通道的可用性可以互不一致（本机实测见 §3.1）。

## 2. 定义/原理：决策链与降级

```
isTypeSupport(mime) 流程（自研 SDK 选型层）：

1. WebCodecs 可用？ VideoDecoder.isConfigSupported(h265) 
   → supported 且 config.hardwareAcceleration 可用 → WebCodecs 硬解
2. MSE.isTypeSupported('video/mp4; codecs="hvc1..."') 
   → true → MSE 硬解（直播/点播主通道）
3. 都不可用，但 <video>.canPlayType(hvc1) ≠ '' 
   → 整文件硬解通道（点播可用，直播不可用）
4. 全部不可用 → WASM 软解（decode 层替换，其余层复用）
5. H264 → 永远走 MSE（支持面 100%，无需决策）
```

**为什么 H264 不进决策链**：H264 硬解支持面接近 100%（20 年部署史），任何设备都可走 MSE——决策链只为「新编码」服务（H265/AV1）。这也是自研 SDK 的简化：**H264 统一走 MSE，H265 才分硬软**。

## 3. 实测

### 3.1 能力矩阵碎片化的实证（本机 Chrome 154 / RTX 3050）

> 🔗 [[视频编码代际与浏览器支持]] §3.2 完整表，关键行：

| 通道 | H265 结果 |
| --- | --- |
| `<video>.canPlayType('…hvc1…')` | probably |
| `MediaSource.isTypeSupported('…hvc1…')`（正常启动） | true（--disable-gpu 时 false，见 [[视频编码代际与浏览器支持]] §3.2 修正） |
| `<video>` 实播 H265 文件 | **成功**（NVDEC 硬解，currentTime 正常推进） |
| `--enable-features=PlatformHEVCDecoderSupport` 后 MSE | 仍 false |

**同一浏览器、同一编码、三通道结论互斥**——这就是「碎片化」的具体形状：不是「支持/不支持」一个位，而是「哪条通道、什么 flags、什么硬件」的三维空间。

### 3.2 硬解 vs 软解速度实测（ffmpeg，1080p 4s 片段）

> 🔗 环境：FFmpeg 9.0，RTX 3050 NVDEC，同一条 H265 等体积流（h265-eq2.mp4）：

| 路径 | 命令 | 3 次均值 |
| --- | --- | --- |
| 软解 H265 | `ffmpeg -i h265.mp4 -f null -` | ~336 ms（speed 12.5×） |
| 硬解 H265 | `ffmpeg -hwaccel cuda -i h265.mp4 -f null -` | ~383 ms* |
| 软解 H264（对照） | `ffmpeg -i h264.mp4 -f null -` | ~247 ms（speed 28.9×） |

> *CLI 整体耗时含进程启动与拷回开销，**不构成「软解比硬解快」的结论**——它只证明两条路径在本机都跑得通。真实差距要在浏览器内解码循环测（GPU 解码 + 拷回 CPU 的组合工程复杂度，见 [[WASM软解H265管线]] 的讨论）。可靠结论只有两条：① H265 软解比 H264 软解慢 ~35%（同为 CPU 路径，公平对比）；② 硬解路径能跑通不代表策略层放行（§3.1 的 MSE false）。

### 3.3 为什么「测得出硬解」≠「用得上硬解」

`<video>` 能播 ≠ MSE 能用：MSE 需要浏览器 demuxer 白名单 + 解码器两条都放行。**自研播放器的直播通道必须走 MSE → 直播 H265 的硬解可用性 = MSE 检测结果**，哪怕同页面 video 标签明明能硬解。这是选型链第 2 步在第 3 步之前的原因。

## 4. 为什么这么设计？（背后取舍）

**为什么浏览器不统一三条通道的解码决策？**
- 专利敞口不同（见 [[视频编码代际与浏览器支持]] §5）：video 标签把解码交给 OS（微软/苹果装解码器，Google 不分发），MSE 管线在 Chrome 进程内（专利风险自担），WebCodecs 又是独立 feature flag。**三条通道是三条法律边界，不可能统一**——碎片化是法律问题的技术投影，不是工程失误。

**为什么软解永远要有（哪怕硬解率 95%）？**
- 剩下 5% 的设备 = 5% 的用户完全播不了。音视频产品的底线是「能播」，软解是**覆盖率的兜底**而非性能方案。工业现实：软解路径存在但流量占比个位数——养它的成本（维护 WASM 解码器）远低于丢 5% 用户的损失。

**为什么 SDK 层封装成 isTypeSupport 一个入口？**
- 三通道检测 + flags/版本差异的复杂度不应该泄漏给业务方；业务方只问「这个流我这能不能播」——**选型层把碎片化收纳成一个布尔**，这是分层架构（[[播放器架构分层]]）里 decode 层替换自由度的红利。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| H265 直播 | MSE 检测先行；false → WASM 软解；H264 兜底转码双流 |
| H265 点播 | 三通道都试（video 标签通道保底） |
| 软解性能不够 | 降分辨率档（480p 软解可行）+ 帧率减半 |
| 能力缓存 | 检测结果按 (设备, 通道, 编码) 缓存，避免每次起播全探测 |
| 兜底链终点 | 软解也失败 → 明确报错（别无限重试），引导换 H264 流 |

## 6. 面试速记

> **30 秒版**："硬解快省电但支持矩阵碎（芯片×驱动×OS×浏览器策略四维），软解慢费电但全覆盖。选型是决策链不是二选一：WebCodecs 硬解 → MSE 硬解 → video 标签硬解 → WASM 软解，H264 直接 MSE 不进链。实测最有说服力的一点：本机 Chrome 154 的 H265，MSE 层 isTypeSupported 是 false，但 video 标签实播 NVDEC 硬解成功——同一浏览器三通道结论互斥，所以检测必须运行时按通道做，这就是我们 SDK isTypeSupport 的存在理由。软解养着不是为性能是为兜底 5% 设备。"
