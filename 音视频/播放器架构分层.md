# 播放器架构分层

> **结论：任何播放器（video 标签内部、flv.js、hls.js、自研 SDK）都是同一条五层流水线：**拉流(loader) → 解复用(demux) → 解码(decode) → 渲染(render) → 同步(sync)**，层间只传「带时间戳的数据」。分层的意义：每层可独立替换（换协议只动 loader，换解码只动 decode）——自研 SDK 的 isTypeSupport 选型就是只动 decode 层（硬解 MSE / WASM 软解），flv.js 就是只动 loader+demux 层（FLV→fMP4 转、其余复用 MSE）。能按层讲清楚「哪层是你自己写的」，播放器面试的上限就在这里。**

> 可运行验证：[[MSE最小播放器-验证demo]]（①②③⑤层的完整最小实现）；[[WASM软解H265管线]]（③层换软解的完整管线）；时序类结论由各层笔记的实测支撑。

## 1. 背景：video 标签把五层全包了，什么时候需要拆开

```
<video src="x.mp4"> 内部：
  网络栈 → 内建 demuxer → 内建/平台解码器 → 合成器
```

黑盒五层全包 = 任何一层不满足需求就整条链废掉。播放器工程的一切工作，本质是**按需替换某一层，其余复用浏览器/既有库**：

| 需求 | 替换的层 | 方案 |
| --- | --- | --- |
| 播 FLV 直播流 | loader + demux | fetch FLV → JS 转 fMP4 → MSE（flv.js） |
| 播 H265（浏览器 MSE 不放行） | decode | WASM 软解 + WebGL 渲染（自研 SDK） |
| 帧级处理（截帧/AI） | decode 输出出口 | WebCodecs |
| 自定义缓冲/追帧策略 | sync + buffer 管理 | MSE 上自建策略层 |
| 全部都要 | 五层全自研 | 商业 SDK（如自研播放引擎） |

## 2. 定义/原理：五层职责与数据流

```
┌─────────────────────────────────────────────────────┐
│ ⑤ 同步层 (sync)  主时钟 + 音画同步 + 缓冲策略 + 状态机   │
├─────────────────────────────────────────────────────┤
│ ④ 渲染层 (render) 视频:video/WebGL ←YUV; 音频:WebAudio │
├─────────────────────────────────────────────────────┤
│ ③ 解码层 (decode) 硬解(video/MSE内部/WebCodecs) 软解(WASM)│
├─────────────────────────────────────────────────────┤
│ ② 解复用层 (demux) fMP4/FLV/TS → 压缩帧+参数集+时间戳    │
├─────────────────────────────────────────────────────┤
│ ① 拉流层 (loader)  HTTP/WS/WebRTC → 字节流（可多路复用）  │
└─────────────────────────────────────────────────────┘
数据流自下而上；控制流（buffered/seeks/码率决策）自上而下
```

| 层 | 输入 → 输出 | 关键问题 | 对应笔记 |
| --- | --- | --- | --- |
| ① loader | URL → 字节分片 | 长连接/断线重连/并发预取 | [[HTTP-FLV协议原理]] |
| ② demux | 字节 → (压缩帧, PTS, SPS/PPS) | 容器解析、关键帧定位、多轨道分流 | [[fMP4与MP4的区别]] |
| ③ decode | 压缩帧 → VideoFrame/YUV | 硬解可用性/性能/延迟 | [[硬解与软解的选型]] |
| ④ render | YUV/PCM → 画面/声音 | WebGL 上屏、AudioContext 队列 | [[YUV格式与WebGL渲染]] |
| ⑤ sync | 各层状态 → 播控决策 | 主时钟、追帧、水位、状态机 | [[音画同步策略]] |

**层间契约是「带时间戳的数据」**——这是五层能独立替换的原因：demux 给 decode 的是 `(EncodedChunk, pts)`，decode 给 render 的是 `(VideoFrame, pts)`，时间戳是唯一的跨层语言。

## 3. 实测：各层的实测证据链（本库已有）

五层的每层行为都有实测笔记背书：

| 层 | 实测结论 | 出处 |
| --- | --- | --- |
| ① 拉流 | file:// 无法 fetch 本地媒体，必须 http；分片拉取粒度决定首开 | [[MSE最小播放器-验证demo]] §4 |
| ② demux | mimeType codec 写全才过（audio OT 0x40 实测报错）；fMP4 分片自包含寻址 | [[fMP4与MP4的区别]] §3.2 |
| ③ decode | H265 硬解三层探测面结论可不一致；H265 软解比 H264 慢 ~35% | [[视频编码代际与浏览器支持]] §3.1/3.2 |
| ④ render | AudioContext 硬件钟 2 秒漂移 <2ms；suspended 冻结 | [[WebAudio与音画同步时钟]] §3 |
| ⑤ sync | appendBuffer 毫秒级完成、buffered 即时可查（策略数据源） | [[MSE最小播放器-验证demo]] §3 |

### 3.1 最小播放器的分层映射

[[MSE最小播放器-验证demo]] 的 70 行代码，逐行对应五层：

```js
fetch(url)                    // ① loader
// （fMP4 场景浏览器内置 demux）   // ② demux（省略 = 复用浏览器）
MediaSource + appendBuffer    // ③ decode（复用浏览器解码）
<video> 元素                   // ④ render（复用浏览器渲染）
video.play() / currentTime    // ⑤ sync（仅最小版；自研版在本层重写）
```

**自研 SDK 的增量 = 把②③④⑤从「复用浏览器」变成「自己实现」**，而不是重写这 70 行骨架。这就是为什么「自研播放器」的合理第一课是先吃透 MSE 最小实现。

## 4. 为什么这么设计？（背后取舍）

**为什么五层而不是三层（网络/解码/播放）？**
- 粒度按「独立演进速度」划分：协议（loader）换代最快（HLS→FLV→WebRTC）、容器（demux）次之（TS→fMP4）、解码（decode）受制于硬件/专利、渲染与同步最稳定。**层边界画在「变化速率差异最大」的地方**，替换成本才最小——和前端把 UI 层/状态层/数据层分开是同一个理由。

**为什么时间戳是层间唯一契约而不是「帧对象」？**
- 跨层传递「富对象」会把层耦合死（decode 层被迫理解渲染层的需求）；只传 `(数据, pts)`，每层对数据做任意变换（软解/超分/加密），时间戳保持不变——**数据流单向、标注随行**，流水线才可组装。这也是 MPEG-TS 的 PTS/DTS 设计沿用 30 年的原因。

**为什么 sync 层是自研播放器的核心价值层？**
- ①~④层浏览器/开源方案已经很好（MSE/WebCodecs/WebGL 都是成熟件），**缓冲水位、追帧、ABR、音画容差这些策略浏览器黑盒里都有但不可定制**——商业播放器的差异化几乎全部在⑤层。这也是面试问「你们播放器难点在哪」的答案锚点（不是解码，是时序策略）。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 新播放器立项 | 先跑通 MSE 最小链路（复用②③④），确认需求缺口再决定自研哪层 |
| 换协议 | 只改 loader 层，demux 以下不动（接口：字节分片） |
| 性能问题 | 先定位层：卡顿→⑤水位策略；花屏→②分片边界；黑屏→③解码初始化 |
| 团队分工 | loader/demux 一组（IO/协议），decode/render 一组（性能/图形），sync 一组（策略/业务） |
| 简历表述 | 按「替换了哪几层、为什么」组织，而不是「实现了播放器」一笔带过 |

## 6. 面试速记

> **30 秒版**："播放器五层：拉流→解复用→解码→渲染→同步，层间只传带时间戳的数据所以每层可独立替换——flv.js 替换①②，我们 SDK 替换③（硬解不行就 WASM 软解），商业播放器的主战场是⑤同步策略层因为①~④浏览器都有成熟件。每层的关键问题不同：②的分片边界、③的硬解可用性、④的硬件时钟、⑤的水位与容差，我库里每层都有实测笔记。video 标签就是五层全包的黑盒，自研 = 按需重开某一层。"
