# ABR自适应码率

> **结论：ABR = 「实时估带宽 + 在码率档位表里选一个不卡的档」——**估带宽（throughput 法：最近 N 个分片的 字节/耗时）→ 选档（≤ 带宽的 70~80%，留余量）→ 切档（掐关键帧边界无缝换流）→ 防抖（hysteresis：升档要求带宽持续富余，降档立即可行）**。升难降易是核心设计：降档错了只是画质差点，升档错了就卡顿——不对称惩罚决定不对称策略。实测依据：码率-体积矩阵见 [[码率帧率分辨率与带宽]] §3，切档的分片对齐机制见 [[fMP4与MP4的区别]] §3。**

> 可运行验证：多码率 ladder 的生成与切换 demo 可复用 [[MSE最小播放器-验证demo]]（换 url 即换档）；带宽估计的原始数据来自 fetch 分片的 Response 头与耗时（§2.1 代码）。

## 1. 背景：为什么码率要自适应

带宽不是常数（WiFi 干扰、4G 边缘、共享链路），码率是常数 → 固定码率必然「不卡就糊」二选一：

- 固定 5M：带宽 5M+ 时画质浪费，带宽 2M 时卡死。
- ABR：带宽 6M 播 5M 档，掉到 3M 自动切 2.5M 档，恢复再升——**每一刻都播当前网络能承受的最高画质**。

工业基础：一源多档（ABR ladder）。转码端出：1080p@5M / 720p@2.5M / 480p@1M（可选 360p@0.6M），**各档 GOP 对齐**（同一时刻的关键帧时间点一致），切换才能无缝（[[码率帧率分辨率与带宽]] §5）。

## 2. 定义/原理：三个模块

### 2.1 带宽估计（throughput 法）

```js
// 每完成一个分片下载就更新估计
const bits = chunk.byteLength * 8;
const seconds = (chunkEndTs - chunkStartTs) / 1000;   // 含排队/传输全程
bw = bits / seconds;                                   // 本片吞吐 bps
// 平滑：指数移动平均（EMA），近期权重高
estBw = alpha * bw + (1 - alpha) * estBw;              // alpha≈0.2
// 或 harmonic mean of last N（hls.js 默认对 N=2~3 片取调和平均，压毛刺）
```

**为什么要平滑**：单片的吞吐毛刺大（TCP 慢启动、GC 停顿、WiFi 波动）。EMA/调和平均压掉毛刺，代价是响应变慢——这个「响应速度 vs 稳定」的权衡就是 ABR 调参的全部手感。

### 2.2 选档决策

```
目标 = estBw × 安全系数(0.7~0.8) 内的最高档
额外约束：
  buffer 水位高   → 允许试升档（有余粮）
  buffer 水位低   → 强制降档（保命优先于画质）
  首片（冷启动）  → 从中低档起播（快速首帧，见 [[首开时间优化]]）
```

### 2.3 切档执行（MSE 通道）

```
1. 新档分片与旧档在关键帧边界对齐（ladder 对齐保证）
2. appendBuffer 新档分片（等 updateend）
3. 播放头自然跨越旧/新分片交界 → 画面无感切换
   （旧数据不必清除：两档可以在 SourceBuffer 里短暂共存，播放头线性前进）
```

**无缝切换的两个前提**：分片时间戳连续（同一时轴）、关键帧对齐——这就是 HLS/DASH 的 ladder 规范要求，也是「切档黑屏一下」类 bug 的排查起点（时间轴没对齐）。

## 3. 实测

### 3.1 档位表的真实数据（码率-画质实测矩阵）

> 🔗 [[码率帧率分辨率与带宽]] §3.1：分辨率是体积主导因子（480p→1080p 体积 ×4.54），帧率影响小（15→60fps 仅 ×1.55）。**所以 ABR ladder 降档先降分辨率再降帧率**——同样省一半带宽，降分辨率画质损失更小。

| 档 | 码率 | 与 1080p 的带宽比 | 适用带宽（×1.4 余量） |
| --- | --- | --- | --- |
| 1080p@30 | 5 Mbps | 1× | ≥7 Mbps |
| 720p@30 | 2.5 Mbps | 0.5× | ≥3.5 Mbps |
| 480p@30 | 1 Mbps | 0.2× | ≥1.4 Mbps |
| 360p@30 | 0.6 Mbps | 0.12× | ≥0.84 Mbps |

### 3.2 切档时机的实测判据（buffer 联动）

buffer 水位（[[MSE最小播放器-验证demo]] 实测：buffered 即时可查）是比带宽估计更「诚实」的信号——带宽估计看的是过去，buffer 看的是未来还能撑几秒：

| buffer 存量 | 策略 |
| --- | --- |
| > 20s | 富余 → 允许升档试探 |
| 5~20s | 稳态 → 维持当前档 |
| 2~5s | 预警 → 冻结升档 |
| < 2s | 告急 → 立即降档（不等带宽估计确认） |

**工业实现（hls.js 同型）**：buffer 紧急度直接进入选档函数，权重随存量非线性上升——「卡顿损失 > 画质收益」被硬编码进决策。

### 3.3 hysteresis 防抖的必要性（思想实验 → 工业参数）

带宽在两档边界（如 3.2 Mbps，720p 档需 3.5M、480p 档 1.4M 安全线内）波动时，无迟滞策略会在档间振荡（每切一次都有解码器重配开销 + 画质跳变）。hls.js 的做法：

- **升档条件**：估计带宽 > 目标档 × 1.1 且 buffer > 某水位，且持续若干分片。
- **降档条件**：buffer 告急或带宽 < 当前档 × 0.9，**立即执行**。

## 4. 为什么这么设计？（背后取舍）

**为什么安全系数 0.7~0.8 而不是拉满带宽？**
- 带宽估计永远滞后于真实网络（你用的是上一个分片的吞吐）。留 20~30% 余量 = 承认「估计是滞后的」，给网络波动留缓冲。拉满 = 单片波动直接转化为卡顿——**估计器的误差方差决定了必须的余量**。

**为什么升难降易（不对称 hysteresis）？**
- 损失不对称：降档损失画质（可恢复、可感知度低），升档失败导致卡顿（不可逆、体验断崖）。**风险不对称 → 决策不对称**，与 TCP 拥塞控制「加法增、乘法减（AIMD）」完全同构——都因「失败代价不对称」。

**为什么切档在关键帧边界（而不是任意时间）？**
- 见 [[Seek实现与关键帧对齐]] §5：解码器只能从 IDR 重启。新档分片从 IDR 起才可解；ladder 对齐让新旧档在同一时刻都有 IDR——**编码层的随机访问约束决定了切换粒度**。

**为什么冷启动从中低档起？**
- 首片下载决定首开时间（见 [[首开时间优化]]）：低档分片小（1Mbps 档 1s 片 ≈ 125KB vs 5M 档 625KB），快速拿到 = 快速起播；起播后 buffer 积累、估计收敛，再逐步升档。**先用体验下限换首帧时间，再爬坡**——TCP 慢启动的播放器版。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| ladder 设计 | 4 档左右、GOP 对齐、先降分辨率再降帧率 |
| 估计毛刺 | EMA α≈0.2 或最近 2~3 片调和平均 |
| 切档黑屏 | 查 ladder 关键帧对齐 + 分片时间戳连续性 |
| 弱网反复降档 | 保底档（360p）+ 卡顿计数触发的「稳定模式」 |
| 冷启动 | 中低档起播 + 起播后每 N 片试探升档 |

## 6. 面试速记

> **30 秒版**："ABR 三模块：带宽估计用最近分片吞吐做 EMA 平滑，选档取估计带宽 ×0.7~0.8 内最高档并叠加 buffer 紧急度，切档靠 ladder 关键帧对齐在 MSE 里无缝换流。核心是不对称 hysteresis：升档要带宽持续富余 buffer 够，降档 buffer 告急立即执行——因为升档失败卡顿不可逆，降档只是画质差点，风险不对称决策就不对称，和 TCP 的 AIMD 同构。冷启动中低档起播再爬坡，就是慢启动的播放器版。"
