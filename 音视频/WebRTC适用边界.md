# WebRTC适用边界

> **结论：WebRTC = 「强实时、小规模、可接受高单路成本」的专用通道——**会议/连麦/竞拍用它（延迟 <1s 是产品功能），万人直播不用它（SFU 逐路转发成本不可接受）**。成本模型是分水岭：CDN 直播「一份内容 N 人取」（带宽计费），WebRTC「一人一份个性化流」（路数计费，数倍~数十倍）。混合架构是工业终态：主播连麦走 WebRTC、混流后的主画面走 CDN 分发——**腾讯云/声网的产品形态就是这条边界的直接工程化**。技术上也一样：Opus/VP8 必选集、DTLS-SRTP、jitter buffer 全是为实时定制的，拿它做分发是杀鸡用牛刀还不划算。**

> 可运行验证：端到端延迟与卡顿行为的实测对比见 [[直播协议延迟对比]] §3；Opus/编解码必选集实测 [[SDP与ICE穿透]] §3.1；采集/建连链路 [[getUserMedia采集]] + [[RTCPeerConnection流程]]。

## 1. 背景：WebRTC 的设计目标决定了它是什么

WebRTC 的每个组件都为「**最低延迟的双向实时通信**」优化：

| 组件 | 为实时做的定制 | 分发场景下的代价 |
| --- | --- | --- |
| UDP/SRTP | 无队头阻塞、容忍丢包 | 无 CDN 缓存可能 |
| Opus 可变码率 | 跟网络抖动实时调（6k~510k） | 每路流内容不同（无法复用） |
| jitter buffer | 100~300ms 动态缓冲 | 每观众独立 buffer 状态 |
| SFU 转发 | 每人按需订阅轨（大小流/SVC） | **服务器带宽 ∝ 观众数** |

**结论先行**：WebRTC 的「每路个性化」与 CDN 的「一份多取」在分发模型上对立——选型本质是问「延迟值不值这个钱」。

## 2. 定义/原理：适用与不适用的判定线

### 2.1 适用（延迟=产品功能）

| 场景 | 延迟要求 | WebRTC 的角色 |
| --- | --- | --- |
| 视频会议 | <300ms | 主通道（SFU 全员互传） |
| 连麦（直播互动） | <500ms | 主播-连麦者之间 |
| 竞拍/抢答/云监考 | <1s | 信号级实时 |
| 云游戏/远程控制 | <100ms | 输入+画面双实时 |
| Web 端 SIP 通话 | — | 媒体面标准答案 |

### 2.2 不适用（延迟是锦上添花）

| 场景 | 为什么不用 | 替代 |
| --- | --- | --- |
| 万人直播观看 | SFU 成本 ∝ 观众数，不可接受 | CDN 协议（HLS/FLV），见 [[直播协议延迟对比]] |
| 点播 | 无实时性需求 | MSE 播放器 |
| 大规模弱互动活动 | 数万人规模成本爆炸 | CDN + 混流延后若干秒 |

### 2.3 混合架构（工业终态）

```
主播 A ─┐
主播 B ─┴─ WebRTC(MSFU) ─→ RTC 房间（互看，<500ms）
              │
              └→ 混流服务器（合成单画面+音频）
                     └→ CDN（HLS/FLV）→ 观众万人（延迟 3~10s，无所谓）
```

**两个世界各干各的活**：互动者之间用 WebRTC 保实时；观众看混流结果走 CDN 保规模。观众侧的「连麦延迟感知」= 混流+分发延迟（5s 级），产品上用 UI 掩盖（如「连麦画面稍后出现」的转场）。

## 3. 实测

### 3.1 端到端延迟的量级实测（协议对照）

> 🔗 各协议链路组成实测汇总（[[HLS协议原理]] §3.2 / [[HTTP-FLV协议原理]] §2.3 / 本篇）：

| 协议 | 端到端延迟 | 主要构成 |
| --- | --- | --- |
| WebRTC | **0.2~1s** | jitter buffer(0.1~0.3s) + 传输(0.05~0.1s) + 编解码(0.1s) |
| HTTP-FLV | 2~5s | 服务端缓冲 + CDN 透传 + 播放水位 |
| HLS | 10~20s | 分片 × 片数 + 轮询间隔 |

WebRTC 的延迟构成里**没有「分发」概念**（点对点/SFU 直达），下限由 jitter buffer 决定——再往下压就是花屏换延迟（jitter buffer <100ms 后丢包直接上屏）。

### 3.2 成本模型的量化对比

1000 人观看 1Mbps 直播 1 小时：

| 方案 | 服务器/带宽成本 | 计费单位 |
| --- | --- | --- |
| CDN（HLS/FLV） | 1GB × 1000 = 1TB 流量 | GB（约几美元~十几美元/百GB） |
| WebRTC SFU | 1Mbps × 1000 路 × 3600s ≈ 450GB **过 SFU** + SFU 集群算力 | 分钟路数（典型 $0.001~0.004/分钟/路） |
| 差距 | — | **CDN 便宜约 5~20×**（规模越大差距越大） |

再加**回源结构差异**：CDN 边缘可缓存（源站压力与观众数无关），SFU 逐路转发（源/中心压力与观众数线性）——**规模越大，WebRTC 的成本曲线越陡**。

### 3.3 WebRTC 播放观看流的「能但不该」

技术上 `RTCPeerConnection` 可以接收广播流（只 recv 不 send），实测可行但：

| 维度 | 实测/事实 |
| --- | --- |
| 服务端 | 每观众一条 PeerConnection × 全量媒体（无缓存） |
| 连接建立 | 每观众独立 offer/answer + ICE + DTLS（~1~2s，CDN 命中是 0） |
| 弱网 | 每路独立拥塞控制（万人 = 万人突发） |

**结论**：万人观看用 WebRTC = 把 CDN 用「逐人专线」的方式重做一遍——工程可行、商业自杀。

## 4. 为什么这么设计？（背后取舍）

**为什么 WebRTC 不做「可缓存」的设计？**
- 缓存的前提是「同一份内容」；实时通信每路流的码率/丢包响应/优先级都按**该接收者的网络**定制（SVC 分层、simulcast 多小流按需订阅）。个性化的极致 = 不可复用的极致——**目标函数从「分发效率」换成了「实时质量」**。

**为什么 SFU（选择性转发）而不是 MCU（混流转发）？**
- MCU 混流 = 服务端全量解码再编码（贵、延迟+数百 ms、画质降级）；SFU 只转发不转码（便宜、延迟低），代价是客户端要处理多流（simulcast 选层）。**SFU 用客户端复杂度换服务端成本**——浏览器端有硬解冗余，服务器端却是成本大头，这笔账很自然。

**为什么「混流出 CDN」的延迟差（连麦者 vs 观众差 5s）能被产品接受？**
- 观众与连麦者**没有直接互动**——观众看到的「主播连麦」只要时间序一致（都延迟 5s），叙事是完整的。**延迟敏感度取决于「谁在和谁互动」而非绝对数字**——产品层的设计（转场/提示）消化了架构层的延迟差。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 直播+连麦 | WebRTC 房间 + 混流出 CDN（混合架构） |
| 需要类 WebRTC 延迟但万人规模 | 评估 LL-HLS/LL-DASH（2~5s）或 RTC 直播产品（贵） |
| 成本优化 | simulcast 按需订阅、TURN 用量告警、小流优先 |
| 弱互动大活动 | 延迟容忍声明（产品页写明 5~10s）+ CDN 全力 |
| 技术选型沟通 | 用「延迟-规模-成本三角」对齐产品/老板（[[直播协议延迟对比]] §4 底图） |

## 6. 面试速记

> **30 秒版**："WebRTC 的适用边界由成本模型决定：它为每路接收者定制流（变码率、simulcast 订阅、独立 jitter buffer），所以不可缓存、SFU 逐路转发、成本随观众数线性涨——万人直播用它是商业自杀，CDN 便宜 5-20 倍。反过来会议连麦竞拍必须用它，延迟 <1s 是产品功能。工业终态是混合架构：连麦者之间 WebRTC 保实时，混流出 CDN 给万人观众，两边的 5s 延迟差用产品转场掩盖——因为观众和连麦者之间没有直接互动，延迟敏感度取决于谁在和谁互动。"
