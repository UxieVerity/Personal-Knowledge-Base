# 首开时间优化

> **结论：首帧时间 = 连接建立 + 等首个含关键帧的分片 + demux/解码初始化 + 攒起播水位——四段各有专项手段：**连接（TLS1.3/QUIC 复用已有）、等分片（短 GOP + 低档起播 + 边缘预连接）、解码初始化（提前 configure/预热）、水位（低起播水位 + 起播后激进补）**。实测依据：TLS 握手差一个 RTT 实测 22~40ms（[[TLS12和TLS13的区别]]）、appendBuffer 毫秒级不是瓶颈（[[MSE最小播放器-验证demo]] §3）、等 IDR 是 GOP 长度的上限（[[I帧P帧B帧与GOP]] §3.2）。**「低水位起播 + 起播后快补」是两头兼顾的工业答案**。**

> 可运行验证：各段耗时都可用 Navigation Timing 思路 + demo 面板实测（TLS 数据 [[TLS12vsTLS13-验证脚本.js]]；append 数据 [[MSE最小播放器-验证脚本.js]]）。

## 1. 背景：首开时间是一条乘法链

用户点「播放」到第一帧画面：

```
T首帧 = T连接 + T首分片 + T解码就绪 + T起播水位
        (RTT×1~3)  (GOP 等待)    (decode 初始化)  (0~5s 策略值)
```

**乘法链的优化原则：最长的那段优先**。典型直播 FLV 场景的量级：

| 段 | 典型 | 主要决定因素 |
| --- | --- | --- |
| T连接 | 100~300ms（冷）/ ~0（复用） | DNS+TCP+TLS 往返 |
| T首分片 | 1~10s | **GOP 长度** + 边缘节点命中 |
| T解码就绪 | 50~200ms | 解码器初始化（软解更慢） |
| T起播水位 | 0~5s | **策略参数**（起播水位） |

## 2. 定义/原理：四段的手段清单

### 2.1 T连接：复用与前置

| 手段 | 收益 | 出处 |
| --- | --- | --- |
| TLS1.3（省 1 RTT） | 实测 22~40ms | [[TLS12和TLS13的区别]] §3 |
| 会话复用/连接预热（页面加载时就建连接） | ~100ms+ | [[网络层优化]] |
| HTTP/2 多路复用（首片与 m3u8 并行） | 串行→并行 | [[HTTP1和HTTP2、HTTP3 的区别]] |
| 边缘节点就近 | RTT 本身下降 | [[直播CDN分发链路]] |

### 2.2 T首分片：短 GOP + 低档起播

- **推流端短 GOP**（1~2s）：新观众最长等一个 GOP 才遇到 IDR（[[I帧P帧B帧与GOP]] §5）——首分片等待的上限就是 GOP。
- **低档起播**：1s 分片 360p ≈ 75KB vs 1080p ≈ 625KB，下载时间差 8×，弱网下更显著（[[ABR自适应码率]] §5 冷启动）。
- **首分片必含 IDR**：推流端保证每个分片从关键帧开始（分片对齐 GOP），否则播放端要再等一个分片。

### 2.3 T解码就绪：预热与预配置

- MSE：`addSourceBuffer` 早于 fetch 完成（并行做）；
- WebCodecs/WASM：decoder.configure / WASM 实例化在拉流同时进行（[[WASM软解H265管线]] 的启动序列）；
- AudioContext：`resume()` 提前到手势时机（[[WebAudio与音画同步时钟]] §3.2 的启动顺序）。

### 2.4 T起播水位：低水位 + 快补

| 策略 | 首开 | 卡顿风险 |
| --- | --- | --- |
| 固定高水位 5s | 慢 5s | 低 |
| 固定低水位 1s | 快 | 起播期高 |
| **自适应：低水位起播 + 起播后激进预取补到稳态水位** | 快 | 低（复水快） |

## 3. 实测

### 3.1 各段实测数据汇总（本库已有）

| 论断 | 实测值 | 出处 |
| --- | --- | --- |
| TLS1.3 省 1 RTT | 同站 22~40ms（B站/抖音/淘宝） | [[TLS12和TLS13的区别]] §3 |
| 分片 append 不是瓶颈 | 587KB 分片 append 3.9ms | [[MSE最小播放器-验证demo]] §3 |
| GOP 决定首帧等待上限 | GOP 1s vs 10s 的关键帧密度实测 | [[I帧P帧B帧与GOP]] §3.2 |
| 低档分片小 5× | 1080p@5M vs 360p@0.6M | [[码率帧率分辨率与带宽]] §2.2 |
| AudioContext 冻结陷阱 | suspended 时 currentTime 不走 | [[WebAudio与音画同步时钟]] §3.2 |

### 3.2 首开打点（怎么量出来）

生产打点（首帧 = video 第一次 timeupdate 且 currentTime>0 或 `requestVideoFrameCallback` 首次回调）：

```
t0 = 点击播放
t1 = 首分片响应头到达           → 网络+边缘耗时
t2 = 首分片 appendBuffer updateend → demux 就绪
t3 = 首帧上屏（rVFC/首帧渲染回调）  → 真实首帧
分段 = t1-t0(连接+首包) / t2-t1(下载) / t3-t2(解码+渲染)
```

**没有分段打点的首开优化都是盲调**——先量再治，用数据定位最长的段。

### 3.3 起播水位与卡顿率的权衡实测（工业经验值）

| 起播水位 | 首帧增量 | 起播后 30s 卡顿率（弱网经验） |
| --- | --- | --- |
| 1s | 基准（最快） | 高 |
| 2~3s | +1~2s | 显著下降 |
| 5s | +4s | 降幅趋平（收益饱和） |

2~3s 是收益拐点——「自适应水位」的初始值就从这里取，弱网往上加。

## 4. 为什么这么设计？（背后取舍）

**为什么「低水位起播」敢把卡顿风险置后？**
- 起播后立刻激进预取，水位几秒内补到稳态——**只在最脆弱的窗口借债，随后立刻还**。比固定高水位省下整段首开，比固定低水位多一层保护。这是「延迟还债」策略（预取/预连接/预热全部同构）。

**为什么 GOP 短了压缩率变差还要短？**
- 首开和直播接入是「用户存在」的前提（首帧 10s 用户早走了），压缩率 10% 的差距是「成本问题」——**体验问题优先于成本问题**，除非成本失控（见 [[I帧P帧B帧与GOP]] §5 的定价逻辑）。

**为什么解码预热重要（明明只有 50~200ms）？**
- 乘法链上每段都省才叠加出「秒开」；且软解场景（WASM 实例化+编译）可达数百 ms，是最容易被忽略的隐藏段——**长尾段的优化收益 = 不可省**。

## 5. 规避 / 实践

| 段 | 手段 |
| --- | --- |
| 连接 | TLS1.3 + 连接预热（详情页就预连 CDN） + H2/H3 |
| 首分片 | 短 GOP（1~2s）+ 分片含 IDR + 低档起播 |
| 解码就绪 | configure/实例化/resume 全部并行于拉流 |
| 起播水位 | 自适应 2~3s 起播 + 起播后快补到稳态水位 |
| 观测 | 四段打点（t0/t1/t2/t3），先量再治 |

## 6. 面试速记

> **30 秒版**："首帧时间四段：连接、等首个含关键帧的分片、解码就绪、攒起播水位。逐段手段：TLS1.3 实测省 22~40ms、连接预热；GOP 缩到 1~2s 让等 IDR 上限变小、低档起播分片小 8 倍；decoder configure 和 AudioContext resume 全部并行于拉流；起播水位用『低水位起播+起播后快补』两头兼顾，2~3s 是卡顿率收益拐点。appendBuffer 实测毫秒级所以从来不是瓶颈。先分段打点再优化——没有分段数据的首开优化都是盲调。"
