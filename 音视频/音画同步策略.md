# 音画同步策略

> **结论：以音频主时钟为主轴，视频当从属——**视频帧 pts 落后主时钟就丢帧（跳过），超前就等（重复上屏或晚触发渲染）**，容差阈值外才动作（典型 ±40ms 内不动，人眼无感）。为什么音频当主轴：人耳对断音的容忍（~20ms）远低于人眼对画面停顿（~100ms），音频硬件时钟又天然单调连续（实测 [[WebAudio与音画同步时钟]] §3：2 秒漂移 <2ms）。同步动作只有三个：**丢帧、等帧、追帧（倍速）**——所有商业播放器都在这三个动作的组合上做文章。**

> 可运行验证：主时钟机制实测见 [[WebAudio与音画同步时钟]]（本篇的地基）；MSE 通道 pts 来源与 buffered 联动见 [[MSE最小播放器-验证demo]]。

## 1. 背景：音画为什么会不同步

音频和视频是两条独立管线（各自的 decode/render/buffer），速度永远有微小差异：

| 漂移源 | 典型量级 |
| --- | --- |
| 音频设备时钟 vs 视频解码时钟晶振偏差 | 每分钟几十 ms 级累积 |
| 解码耗时抖动（性能型卡顿） | 单帧 10~50ms |
| 网络分片到达不均 | 秒级（水位波动） |
| Seek/切流后锚点不同步 | 显式错位 |

**不同步不可消除，只能持续校正**——同步策略 = 「测量偏差 → 超阈值时用最小动作拉回」的闭环控制。

## 2. 定义/原理：主从模型与三个动作

```
masterClock = audioCtx.currentTime - anchor      （音频主轴，连续单调）
videoPts    = 当前待渲染帧的显示时间戳

diff = videoPts - masterClock
  |diff| ≤ 40ms    → 正常上屏（不动）
  diff > 40ms      → 视频超前 → 等帧（这一帧多挂一拍/延迟触发渲染）
  diff < -40ms     → 视频落后 → 丢帧（跳过若干帧追上主时钟）
持续落后且水位足   → 追帧（playbackRate 1.1~1.5，见 [[播放器缓冲策略]]）
```

| 动作 | 触发 | 代价 | 适用 |
| --- | --- | --- | --- |
| 等帧（重复上屏） | 视频超前 | 画面微顿 | 小超前（点播） |
| 丢帧（跳上屏） | 视频落后 | 画面跳变 | 小落后 |
| 追帧（倍速） | 持续落后 + 水位足 | 音调/听感变化 | 直播延迟回稳 |

**为什么 ±40ms**：人眼对音口型偏差的感知阈值经验值 ~80ms，40ms 留一半余量；小于阈值动反而引入「振荡」（两轴互相追）。**控制器加死区（dead zone）是控制论的标准做法**。

## 3. 实测

### 3.1 主时钟的资格实测（为什么不是 video/墙钟）

> 🔗 [[WebAudio与音画同步时钟]] §3 全套数据：AudioContext.currentTime 2 秒与墙钟偏差 <2ms、严格单调、suspended 冻结；video.currentTime 在 waiting/seek 时跳变；墙钟与媒体状态脱钩。**同步控制器的输入必须连续单调，三个候选只有音频钟合格。**

### 3.2 丢帧检测的实测口径（浏览器自带的读数）

```js
const q = video.getVideoPlaybackQuality();
q.droppedVideoFrames;   // 渲染层丢帧累计（浏览器判定「来不及」的帧）
```

| 现象 | droppedVideoFrames | buffered | 判定 |
| --- | --- | --- | --- |
| 画面跳但声音顺 | 增长 | 充足 | 解码/渲染性能不足 → 视频落后 → 同步层在丢帧（正常工作） |
| 画面跳且声音断 | 增长 | 耗尽 | 带宽型 → 主时钟本身停了（不是同步问题） |

**同步策略正常工作时丢帧是「合理代价」**（跳帧保口型）；buffered 耗尽导致的音画同停属于缓冲问题（[[播放器缓冲策略]] §3.1），两层问题要分开治理。

### 3.3 Seek 后的锚点重建（实测语义）

Seek 时主时钟必须显式重建（`anchor = audioCtx.currentTime - seekTarget`），否则 diff 计算出巨大偏差触发「疯狂丢帧」。对照 [[Seek实现与关键帧对齐]] §2.2 的步骤 4（currentTime 设精确位置）——**锚点重建与数据面重启是 Seek 的两半，缺一即不同步**。

## 4. 为什么这么设计？（背后取舍）

**为什么音频永远当主轴（而不是视频）？**
- 三条物理事实：①人耳容忍度 < 人眼（20ms vs 100ms）；②音频设备有硬件级稳定节拍（缺样本=爆音，声卡不允许「等一等」）；③音频数据量小（~96k vs ~4000k），队列行为最可预测。**让约束最严格、行为最可预测的一轴做基准，另一轴付出弹性**——分布式时钟同步的通用解法（NTP 里选最稳的源做 stratum 0 是同构）。

**为什么有死区而不是每帧都校正？**
- 连续微调 = 抖动叠加（两个时钟互相追 = 振荡）；死区内不动 = 让微小漂移自然累积到阈值再一次拉回。**控制频率与控制成本的权衡**，和 React 批处理更新、TCP 拥塞控制的迟滞是同构设计。

**为什么直播的同步阈值更松、且允许倍速？**
- 直播的主时钟锚定的是「直播边缘」（主播当前时刻）而非音视频相对同步——延迟超标时**宁可音调微变也要追回边缘**（见 [[直播低延迟与追帧]]）。点播则严格保听感（不用倍速）。**同一个同步器，锚点语义不同 → 策略参数完全不同**。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 通用点播 | 音频主轴 + ±40ms 死区 + 落后丢帧/超前等帧 |
| 直播 | 锚定直播边缘 + 宽死区 + 超标追帧 1.1~1.5× |
| 无声视频 | 建静音 AudioContext 当主轴（否则退化为墙钟，卡顿感知失真） |
| 多音轨/切换 | 切轨后重建锚点；CrossOrigin 的音频走 WebAudio 前先测 CORS |
| 排查不同步 | 先看主时钟是否冻结（ctx suspended）→ 再看锚点是否重置 → 最后才是阈值参数 |

## 6. 面试速记

> **30 秒版**："音画同步=音频主时钟+视频从属的闭环控制：diff=视频pts−AudioContext.currentTime，±40ms 死区内不动，视频落后丢帧、超前等帧、持续落后且水位足就 1.1~1.5 倍速追。音频当主轴因为人耳容忍 20ms 人眼 100ms，且硬件钟单调连续实测 2 秒漂移小于 2ms。三个工程细节：死区防振荡（两钟互追）、Seek 要显式重建锚点（否则疯狂丢帧）、无声视频也要建静音 AudioContext 做主轴。点播锚相对同步、直播锚直播边缘，锚点语义不同策略就不同。"
