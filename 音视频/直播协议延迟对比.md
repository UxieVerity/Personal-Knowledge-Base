# 直播协议延迟对比

> **结论：延迟即选型——**HLS 10s+（分发规模最大）/ HTTP-FLV 2~5s（国内直播平衡解）/ WebRTC <1s（强互动专用）**，三档分别对应「看什么」的三种产品形态：观看型（点播感）、互动型（弹幕节奏）、参与型（连麦/竞拍）。延迟从哪来决定了下限在哪：HLS 的分片轮询机制下限 ~2s（LL-HLS）、FLV 的流式传输下限 ~1s、WebRTC 的实时传输下限 ~200ms——**每往低走一档，分发成本和实现复杂度跳一个台阶**。选型问题的正确问法不是「哪个协议最好」而是「产品要什么延迟、预算养得起哪一档」。**

> 可运行验证：HLS 分片/轮询机制实测 [[HLS协议原理]] §3；FLV 流式结构实测 [[HTTP-FLV协议原理]] §3；WebRTC 延迟实测见 [[WebRTC适用边界]] §3；TCP/QUIC 底座对照 [[TCP与UDP与QUIC的区别]]。

## 1. 背景：延迟的下限由协议机制决定

| 协议 | 传输形态 | 延迟机制下限 | 实际典型 |
| --- | --- | --- | --- |
| **HLS** | 切片 + HTTP 轮询 | 分片时长 × 片数（≈2s） | **10~20s**（LL-HLS 2~5s） |
| **HTTP-FLV** | HTTP 长连接流式 | 播放水位（≈1s） | **2~5s** |
| **WebRTC** | UDP + SRTP 实时 | jitter buffer（≈100~300ms） | **<1s** |

三条机制曲线（延迟 vs 规模/成本）：

```
延迟 ←
 1s ┤              ● WebRTC（专用 SFU 集群，1 观众 1 带宽成本）
    │
 3s ┤      ● HTTP-FLV（CDN 透传长连接，中等成本）
    │
10s ┤ ● HLS（静态分片 CDN 缓存，成本最低、规模最大）
    └──────────────────────────→ 分发规模/并发上限
```

**这张图是所有直播选型讨论的唯一底图**——延迟、成本、规模三者在此协议层就完成了定价，播放器工程只能在这条曲线上微调（[[直播低延迟与追帧]]）。

## 2. 定义/原理：三协议的机制细节

### 2.1 为什么各卡在各自的下限

| 协议 | 下限卡在哪 | 压下限的手段 |
| --- | --- | --- |
| HLS | 分片是「分发+解码」最小单元，客户端要周期刷 m3u8 | 短分片 + 阻塞刷新（LL-HLS），但越短 CDN 缓存效率越差 |
| HTTP-FLV | TCP 队头阻塞（丢包等待）+ 播放水位 | 水位压到 1s 以下开始高频卡顿 |
| WebRTC | jitter buffer 要攒乱序包 | buffer 压到 <100ms 开始花屏/丢帧 |

**每条协议的极限体验都是「在卡顿悬崖边上排队」**——下限不是数字是悬崖位置。

### 2.2 传输层差异（对照网络笔记）

| | HLS/FLV | WebRTC |
| --- | --- | --- |
| 传输层 | TCP（HTTP） | **UDP**（SRTP）+ RTP/RTCP |
| 可靠性 | 完全可靠（重传） | 可容忍丢失（FEC/PLC/丢帧） |
| 队头阻塞 | **有**（TCP 字节流语义） | 无（UDP 报文独立） |
| 拥塞控制 | TCP 自带 | GCC/BBR 变码率联动（Opus 6k~510k 无缝调） |

WebRTC 的低延迟一半来自 UDP 无队头阻塞 + 容忍丢包（花一帧好过等 200ms 重传）——**可靠性与延迟的取舍做在了传输层**，见 [[TCP与UDP与QUIC的区别]]（QUIC 试图在两者之间找位置：可靠但流间无队头阻塞）。

### 3.2 CDN 行为差异（同一家云厂商，两套产品）

| 维度 | HLS/FLV（直播 CDN） | WebRTC（RTC 网络） |
| --- | --- | --- |
| 单位 | 带宽（GB 流量） | 并发分钟路数 |
| 转发形态 | 边缘缓存/透传 | SFU 逐观众转发（不可缓存） |
| 1000 人观看成本 | 码率 × 流量（GB 计费） | 1000 路 × 分钟费（数倍～数十倍） |

**「WebRTC 贵」贵在逐路转发**：SFU 把每条流复制 1000 份，没有 CDN 缓存可用——这就是为什么连麦要 WebRTC、万人直播用 CDN 协议，两者的成本模型不可互换（[[WebRTC适用边界]] §4 的成本细账）。

### 3.3 选型决策树（工程实操）

```
延迟需求？
├─ ≥10s 可接受 → HLS（海外/iOS 一等公民，CDN 成本最低）
├─ 2~5s（弹幕节奏）→ HTTP-FLV（国内） / LL-HLS（海外）
├─ <1s（连麦/竞拍/抢答）→ WebRTC（RTC 网络，按路数买）
└─ 混合形态（万人看 + 连麦）→ 主流 CDN 协议分发 + 连麦走 RTC 混流
   （典型架构：主播连麦走 RTC，混流出 CDN 流给观众——腾讯云/声网的标准产品形态）
```

## 4. 为什么这么设计？（背后取舍）

**为什么没有「既低延迟又 CDN 便宜」的协议？**
- 低延迟 = 消费端要「现做现吃」（不能攒），CDN 便宜 = 内容可缓存复用（越攒越省）——**两个目标在「缓存深度」上直接对撞**。LL-HLS/LL-DASH 的本质是把缓存深度往零压，代价是 CDN 缓存命中率下降、回源压力上升。这是物理性的权衡，不是工程没做好。

**为什么 WebRTC 不用 CDN？**
- CDN 的前提是「一份内容服务 N 人」（缓存复制）；WebRTC 的实时性要求每路接收独立 pacing/拥塞控制（N 份个性化流）——**「一份对 N 人」与「一人一份」是分发模型的对立**。QUIC/MoQ（Media over QUIC）正在探索中间形态，但工业现状仍是两套网络。

**为什么国内 FLV 活得比海外久？**
- 海外：HLS+CDN 生态成熟、苹果生态强制 HLS、延迟敏感场景直接 WebRTC。国内：秀场/游戏直播的互动延迟需求早于 LL-HLS 成熟、CDN 厂商提供 FLV 透传、RTMP 推流端统一——**生态路径决定协议存续，技术优劣只是其中一票**。

## 5. 规避 / 实践

| 场景 | 选型 |
| --- | --- |
| 海外点播/准直播 | HLS（ladder 齐全） |
| 国内直播（弹幕互动） | HTTP-FLV 主流 + HLS 兜底（iOS 老设备） |
| 连麦/强互动 | WebRTC + 混流出 CDN |
| 跨境直播 | 协议层统一 HLS（跨境 CDN 覆盖决定） |
| 观察新方向 | LL-HLS、MoQ（QUIC 上的媒体传输）——关注但不押注 |

## 6. 面试速记

> **30 秒版**："直播协议就是延迟-成本-规模的三方定价：HLS 10s+ 但静态分片 CDN 缓存成本最低；FLV 2-5s 流式透传；WebRTC <1s 但 SFU 逐路转发按路数计费贵数十倍。下限由机制决定：HLS 卡在分片轮询、FLV 卡在 TCP 队头阻塞和水位、WebRTC 卡在 jitter buffer——每条协议的极限都是在卡顿悬崖边排队。低延迟和 CDN 便宜在缓存深度上对撞是物理权衡。选型先问产品要什么延迟：观看型 HLS、互动型 FLV、参与型 WebRTC，万人连麦就是 RTC 混流出 CDN 的混合架构。"
