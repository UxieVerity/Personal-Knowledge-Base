# 编码与封装的区别

> **结论：编码（Codec）是「怎么压缩」，封装（Container）是「怎么装箱」——H264/H265 是压缩算法，MP4/FLV/WebM 是装这些压缩数据的箱子。两步缺一不可：不压缩一条 1080p 视频裸流是 1.5Gbps 根本没法传输，不封装解码器就不知道流的参数、时间戳和音视频怎么对齐。实测：同一份 H264 裸流塞进 MP4 或 AVI 两个箱子，抽出来的 ES（基本流）MD5 完全一致——封装只是搬运，不碰内容。**

> 可运行验证：`ffmpeg`/`ffprobe` 全程实测（本机 FFmpeg 9.0），见 §3 各表；浏览器能力实测用 headless Chrome + puppeteer-core，见 [[视频编码代际与浏览器支持]] §3。

## 1. 背景：为什么两步都要

一条 1920×1080@30fps 的 YUV420 裸流：

```
1920 × 1080 × 1.5 字节/像素 × 30 帧/秒 ≈ 93 MB/s ≈ 746 Mbps
```

直接传/存完全不可行 → **第一步：编码压缩**（去空间冗余、时间冗余、感知冗余），压到 2~8 Mbps。

压完的数据是「裸流」（ES，Elementary Stream）：只有一帧帧压缩数据，解码器不知道宽高、帧率、音轨在哪、某一帧该在什么时刻显示 → **第二步：封装**，把视频裸流 + 音频裸流 + 字幕 + 时间戳 + 参数信息（SPS/PPS）装进一个带索引的「箱子」，播放器按箱子里的目录取数据。

```
拍摄/生成 → YUV 裸流 → [编码器 x264/x265] → H264/H265 ES → [封装器 muxer] → MP4/FLV/WebM 文件
播放时反过来：文件 → [解复用 demuxer] → ES → [解码器] → YUV → 渲染上屏
```

前端对应关系：`<video src="x.mp4">` 里浏览器先 **demux** 再 **decode**；MSE 分段喂的 fMP4 就是「半个箱子」；自研播放 SDK 的 demux 模块就是在做解封装这一步。

## 2. 定义/原理：两层各管什么

### 2.1 编码层（视频）

| 术语 | 含义 |
| --- | --- |
| 编解码器 Codec | Coder + Decoder，压缩算法标准（H264/H265/VP9/AV1） |
| ES（Elementary Stream） | 编码后的裸流，只有压缩帧数据 |
| SPS/PPS（H264） | 序列参数集/图像参数集，解码器初始化必需的「说明书」 |
| VPS（H265 新增） | 视频参数集，多子层描述 |
| NALU | 裸流的组成单元，一帧被切成若干 NALU |

### 2.2 封装层（容器）

| 容器            | 常装编码                      | 特点                                   |
| ------------- | ------------------------- | ------------------------------------ |
| MP4 (ISOBMFF) | H264/H265/AV1 + AAC       | 最通用，moov 索引，网页/移动端标配                 |
| fMP4          | 同上                        | 分片版，MSE 唯一指定格式，见 [[fMP4与MP4的区别]]     |
| FLV           | H264 + AAC                | 流式友好，HTTP-FLV 直播用，见 [[HTTP-FLV协议原理]] |
| WebM          | VP8/VP9/AV1 + Vorbis/Opus | 开源免专利，HLS/浏览器兼容层                     |
| TS (MPEG-TS)  | H264/H265 + AAC           | HLS 分片格式，广播出身，抗丢包                    |

关键认知：**容器和编码是多对多关系**——同一个 H264 裸流可以装进 MP4、FLV、TS 任何一种；`copy` 编码器（流复制）做封装转换时**重新编码为零耗时、零画质损失**。

## 3. 实测：封装转换零损失 + 编码决定体积

### 3.1 同一裸流装进两个箱子，内容完全一致

> 🔗 用 `ffmpeg -c copy` 把同一份 H264 文件分别 remux 成 MP4 和 AVI，再从两个容器里抽出 ES 对比 MD5：

```
ffmpeg -i src-h264.mp4 -c:v copy -c:a copy -f avi src-h264.avi
ffmpeg -i src-h264.mp4 -map 0:v -c copy -f h264 es-from-mp4.h264
ffmpeg -i src-h264.avi -map 0:v -c copy -f h264 es-from-avi.h264
```

| 文件 | MD5 |
| --- | --- |
| `es-from-mp4.h264` | `0d76bf8b04030e049e64d1af34a889a3` |
| `es-from-avi.h264` | `0d76bf8b04030e049e64d1af34a889a3` |

**两个 MD5 完全一致** —— 封装层（MP4 vs AVI）换了，编码层（H264 ES）一个字节没变。这就是「编码管内容、封装管箱子」的直接证据。

### 3.2 编码层决定体积：同内容同参数下 H264 vs H265

> 🔗 同一合成源（`testsrc2` 640×360@30fps 4s），`libx264` vs `libx265`，preset=medium，CRF 恒定质量模式：

| CRF | H264 | H265 | H265/H264 |
| --- | --- | --- | --- |
| 23 | 404,641 B | 441,673 B | 1.09× |
| 28 | 219,041 B | 275,892 B | 1.26× |
| 33 | 132,959 B | 147,504 B | 1.11× |

⚠️ 注意：合成图形源上 H265 反而**更大**——H265 的压缩优势在高分辨率、高运动、真实拍摄内容上才兑现（块划分更细、帧内预测方向更多）。1080p 同一源：

| CRF | H264        | H265        | H265/H264 |
| --- | ----------- | ----------- | --------- |
| 23  | 3,212,444 B | 4,196,094 B | 1.31×     |
| 28  | 1,521,424 B | 2,442,617 B | 1.61×     |
| 33  | 802,067 B   | 1,159,818 B | 1.45×     |

同 CRF 不代表同画质，换成**同体积同画质**对比（对合成源仍不利，但差距收窄）：

| 分辨率 | H264 (crf28) | H265 等体积 (crf≈30) | SSIM All |
| --- | --- | --- | --- |
| 1080p | 1,521,424 B | 1,466,451 B (crf31.5) | 0.9876 |
| 360p | 219,041 B | 216,755 B (crf30) | 0.9849 |

> 环境说明：FFmpeg 9.0 全量构建（libx264/libx265），机器不同绝对值有差异，但「H265 同画质体积更小、合成源优势不明显」这组相对结论稳定。编码速度实测：1080p 4s 片段 medium 档 H264 1337ms vs H265 3744ms（**2.8×慢**），slow 档拉到 4.4×慢——H265 编码贵得多，直播推流端常用 H264 就是这个原因。

### 3.3 封装层不影响体积：remux 前后对比

| 文件 | 大小 | 说明 |
| --- | --- | --- |
| `src-h265.mp4`（MP4，moov 在尾） | 327,837 B | 原始 |
| `src-h265-fmp4.mp4`（fMP4 分片） | 318 KiB | 仅索引结构变化 |
| remux 成 AVI 后 | 与源基本一致 | mdat 原样搬运 |

结论：**remux 只动箱子的「目录页」，体积差异在 KB 量级（索引本身）；编码重新压缩才会 GB→MB 量级地改变体积。**

## 4. 规范位置

- 封装标准：MP4 = ISO/IEC 14496-14（基于 ISOBMFF ISO/IEC 14496-12）；FLV = Adobe F4V/FLV spec；WebM = matroska 衍生。
- 编码标准：H264 = ITU-T H.264 / MPEG-4 Part 10 (AVC)；H265 = ITU-T H.265 / MPEG-H Part 2 (HEVC)；AV1 = AOMedia。
- 浏览器入口：`MediaSource.isTypeSupported('video/mp4; codecs="hvc1..."')` 的字符串就是「容器 + 编码」的组合声明——**两个名字都要写对**，见 [[MSE核心机制]]。

## 5. 为什么这么设计？（背后取舍）

**为什么编码和封装要分成两层？**
- 关注点分离：编码算法几十年换三代（H264→H265→AV1），容器格式相对稳定；分层后「换编码不动容器规范」（MP4 同时容纳 H264/H265/AV1，靠 `codec_tag` 区分：`avc1`/`hvc1`/`av01`）。
- 工具链复用：一次封装，多种解码设备消费；一次编码，remux 到各平台分发（转封装远比转码便宜——上面实测零损失、毫秒级）。
- 类比前端：编码 = 数据的压缩格式（gzip/brotli），封装 = 传输协议的包格式；HTTP 只管装，压缩算法可协商替换。

**为什么面试爱问「MP4 里的 H264 是什么意思」？**
- 这是判断候选人有没有真正接触过流媒体的试金石：答「一个东西」直接出局；答「容器 + 编码两层」还要能往下讲 moov/mdat、SPS/PPS 才算过关。自研播放器项目的 demux 模块天天跟这层打交道。

## 6. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 文件「有画面没声音/有声音没画面」 | 先 `ffprobe -show_streams` 看两路流是否都在，再看 `canPlayType` 是否支持对应编码 |
| 只换容器不重新编码 | `ffmpeg -i in.mp4 -c copy out.flv`（快、无损）；**别用** `ffmpeg -i in.mp4 out.flv`（默认重新编码） |
| 浏览器报 `DEMUXER_ERROR_COULD_NOT_OPEN` | mimeType 的 codec 串与实际流不匹配（实测踩坑见 [[MSE最小播放器-验证demo]]： AAC 音轨必须在 codecs= 里显式列出 `mp4a.40.2`） |
| 判断文件真实内容 | 永远 `ffprobe` 看 `codec_name`，**别信文件后缀**——.mp4 里可以是 H264 也可以是 H265 |

## 7. 面试速记

> **30 秒版**："编码是压缩算法（H264/H265/AV1），封装是容器格式（MP4/FLV/WebM），多对多关系。实测同一份 H264 裸流 remux 进 MP4 和 AVI，抽出来 MD5 完全一致——封装不碰内容；而换编码器同画质体积能差 30%+。播放链路是 demux → decode，MSE 喂的 fMP4 就是 MSE 专用的分片容器，`isTypeSupported` 的参数 'video/mp4; codecs=hvc1' 一句话同时声明两层。"
