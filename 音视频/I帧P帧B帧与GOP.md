# I帧P帧B帧与GOP

> **结论：I 帧是「能独立解出来的帧」（关键帧），P 帧参考前一帧只存差异，B 帧前后双向参考压得最狠但要等后面的帧——**所以 B 帧引入重排序延迟，直播首开必须等 I 帧，Seek 必须落到 I 帧**。实测同一 4s 片段（x264 默认）：120 帧里 I=1、P=47、B=72，B 帧最多；GOP 从 30 拉到 300（10s），同画质体积从 596,775 B 降到 538,568 B（-9.7%）——GOP 越长压缩率越高、但 Seek/切流/首开越伤，这就是直播 GOP 短、点播 GOP 长的原因。**

> 可运行验证：`ffprobe` 逐帧统计 + GOP 对比编码（§3 实测，ffmpeg 命令即验证脚本）；帧序重排用 `ffprobe -show_entries packet=pts_time,dts_time` 直接观察。

## 1. 背景：压缩为什么需要「帧的分类」

视频压缩吃三口：空间冗余（一帧内相邻像素像）、时间冗余（相邻帧几乎一样）、感知冗余（人眼不敏感的细节）。I/P/B 帧就是时间冗余的三种利用姿势：

```
I 帧：不看别人，自己完整画出来        （大）
P 帧：看前面一帧，只画差异            （中）
B 帧：前后都看，差异最小              （小）
```

I 帧是解码的「锚点」：没有 I 帧，后面所有参考它的 P/B 帧全部解不出来。**一组完整的帧序列（I 开头到下一个 I 前）= 一个 GOP（Group of Pictures）。**

## 2. 定义/原理：三种帧 + GOP

### 2.1 I/P/B 帧对比

| 帧型 | 参考关系 | 压缩率 | 解码延迟 | 丢了的后果 |
| --- | --- | --- | --- | --- |
| I（Intra） | 无参考 | 低 | 零 | 该 GOP 全废 |
| P（Predicted） | 前向参考（前面的 I/P） | 中 | 零 | 后续 P 链全废 |
| B（Bidirectional） | 双向参考（前后 I/P） | **最高** | **要等后面的参考帧 → 需重排序** | 局部影响小 |

### 2.2 B 帧为什么有延迟：解码顺序 ≠ 显示顺序

B 帧参考「未来」的帧，所以编码器输出顺序是重排的。实测（本机 h264-crf28.mp4，`ffprobe` 看 packet 层）：

```
packet: pts=0.000  dts=-0.067  [K]     ← I 帧，dts 被压成负数提前送
packet: pts=0.033  dts=-0.033          ← 前面被 B 帧占了
packet: pts=0.067  dts= 0.000
...
ffmpeg 解析报告: Setting codecpar->delay to 2 for stream st: 0   ← 重排缓冲 2 帧
```

**pts（显示时间戳）≠ dts（解码时间戳），差值就是重排延迟**。播放器必须缓存 dts 早于 pts 的帧按 pts 重排后再渲染——这就是解码器 jitter buffer 的来源。B 帧越多，`delay` 越大，端到端延迟越高：**实时通信（WebRTC）默认不用 B 帧**，直播编码器也常 `-bf 0` 关 B 帧换首开延迟。

### 2.3 GOP：压缩率与灵活性的天平

| GOP 长短 | 压缩率 | 首开 | Seek | 切换直播流/丢包恢复 |
| --- | --- | --- | --- | --- |
| 长（如 10s） | **高**（I 帧摊薄） | 慢（等下一个 I） | 粗、慢 | 恢复慢 |
| 短（如 1~2s） | 低（I 帧变多） | **快** | 细、快 | 恢复快 |

直播场景（观众随时加入、随时切进）必须**短 GOP**（通常 1~2s，即 2×fps），且**编码器第一帧必须是 IDR**，否则新观众要等最长一个 GOP 才能出画面。

> IDR vs 非 IDR I 帧：IDR（Instantaneous Decoder Refresh）是「断代」的 I 帧——它之后的帧不允许参考它之前的帧；非 IDR I 帧允许跨参考（开放 GOP）。直播切流要求 IDR。

## 3. 实测

### 3.1 帧型分布（ffmpeg 实测）

> 🔗 源：testsrc2 1080p@30fps 4s，libx264 crf28 默认参数：

```
ffprobe -show_frames -show_entries frame=pict_type -of csv h264-crf28.mp4 | 统计
→ I: 1   P: 47   B: 72   （共 120 帧）
```

**I 帧只占 0.8%，B 帧占 60%** —— 压缩率主要靠 B 帧贡献，这就是 B 帧延迟换体积的直接证据。x264 默认只有第一个 I 帧（点播文件），keyframe interval 由编码器自适应。

### 3.2 GOP 长短 vs 体积（同画质）

> 🔗 同一 10s 640×360 源，只改 `-g`（GOP 尺寸）：

| GOP | 体积 (B) | 相对 GOP=30 |
| --- | --- | --- |
| 30（1s，直播典型） | 596,775 | 基准 |
| 120（4s） | 551,518 | **-7.6%** |
| 300（10s，点播典型） | 538,568 | **-9.7%** |

关键帧位置实测（`ffprobe -show_entries packet=flags`）：

```
gop-30.mp4:  I @0s, 1s, 2s, 3s ...   （每 1s 一个 IDR）
gop-120.mp4: I @0s, 4s, 8s
gop-300.mp4: I @0s                   （10s 里只有片头一个）
```

### 3.3 GOP 与 Seek 粒度的联动

Seek 到 t=4.5s 时（`-ss 4.5` 输入端 seek），`gop-300.mp4` 必须从 t=0 的唯一 I 帧开始解，一帧帧往前**快进解码 ~135 帧**才到目标；`gop-30.mp4` 只需从 t=4s 的 I 帧解 15 帧。**这就是「Seek 后黑屏转圈」和「Seek 粒度是关键帧间隔」的机制根源**，详见 [[Seek实现与关键帧对齐]]。

### 3.4 帧序重排的量化证据

```
第一帧: pts=0.000, dts=-0.066667   （dts < pts → 有重排缓冲）
ffmpeg 日志: codecpar->delay = 2    （解码器需缓存 2 帧再按 pts 输出）
```

## 4. 规范位置

- H.264 spec：slice types I/P/B；IDR NAL unit type 5；`num_reorder_frames`（SPS VUI）声明重排深度。
- ffmpeg 编码参数：`-g`（GOP 长度）、`-bf`（B 帧数）、`-x264opts keyint=xx:min-keyint=xx`（直播关键帧间隔）。
- 浏览器侧：MSE 的 `appendBuffer` 分段必须从 keyframe 边界开始（`sourceBuffer.mode="segments"` 的分段依据），WebCodecs 的 `VideoDecoder.decode(chunk, {keyFrame})` 同理。

## 5. 为什么这么设计？（背后取舍）

**为什么不是「每帧都 I」或「全靠 B 帧压到底」？**
- 全 I：压缩率崩（实测 I-only 编码体积约 3~10×），等于每帧一张 JPEG。
- 全 B/无限参考：一个丢包污染无限远（误差传播），且延迟不可控。GOP + IDR 就是**用周期性锚点限定误差传播的最大半径**——错误最多传播一个 GOP。
- 这和 TCP 里「周期性全量快照 + 增量同步」是同构设计：用锚点换恢复能力。

**为什么直播 GOP 短、点播 GOP 长？**
- 直播的核心指标是首开和切流（观众从任意时刻进来），点播的核心指标是体积和画质（用户能等 1s）。**GOP 长度本质上是在「锚点密度 = 恢复能力/随机访问粒度」和「压缩率」之间定价**，不同场景的定价不同。

**为什么 B 帧实时场景不用？**
- B 帧的收益（体积）对实时场景不重要（带宽便宜），代价（重排延迟 + 解码缓冲）是实时场景最贵的资源。WebRTC 默认 `-bf 0`；RTC 场景低延迟 > 画质效率。

## 6. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 直播推流 | `-g 60 -bf 0`（30fps 下 2s GOP、关 B 帧）；第一帧强制 IDR |
| 点播转码 | GOP 2~5s、保留 B 帧（省带宽） |
| Seek 实现 | 目标时间 → 对齐到 ≤ 目标的关键帧 → 从该 IDR 开始 appendBuffer（见 [[Seek实现与关键帧对齐]]） |
| 直播首开 | 进流先缓冲到下一个 IDR；推流端 GOP 决定了这个等待上限（见 [[首开时间优化]]） |
| 排查花屏 | 90% 是 GOP 内丢帧/乱序：检查是否从 IDR 完整开始、P/B 参考链是否断 |

## 7. 面试速记

> **30 秒版**："I 帧独立解码是锚点，P 帧前向参考，B 帧双向参考压缩率最高但要重排——pts/dts 分离和 delay=2 就是实测证据。GOP 是两个 I 帧之间的周期，越长压缩率越高但首开/Seek/容错越伤：实测 GOP 1s→10s 体积降 9.7%，但 10s GOP 的文件 Seek 到中间要从片头快进解 135 帧。所以直播用 1~2s 短 GOP + 关 B 帧，点播用长 GOP 保 B 帧，Seek 必须关键帧对齐。"
