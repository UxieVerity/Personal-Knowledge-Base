# 码率帧率分辨率与带宽

> **结论：码率 = 每秒的视频数据量，帧率 = 每秒画多少张，分辨率 = 每张多大。三者乘积关系约束画质，但编码器是「恒定质量（CRF）」还是「恒定码率（CBR）」决定了谁说了算。带宽估算口诀：**1080p@4Mbps ≈ 每秒 0.5MB ≈ 30 分钟 900MB**——面试让你「估算一个直播间带宽」就用这条链。实测同一内容 480p→1080p 体积 ×4.5、15fps→60fps 只 ×1.55：**分辨率对体积是平方级贡献，帧率是线性贡献**——降分辨率是省带宽第一杠杆。**

> 可运行验证：ffmpeg 同源编码矩阵（§3 实测，命令即脚本）；浏览器侧配合 [[WebAudio与音画同步时钟]] 的播放时钟实测。

## 1. 背景：三个「率」各管什么

| 概念 | 单位 | 含义 | 类比 |
| --- | --- | --- | --- |
| 分辨率 (Resolution) | 像素 (W×H) | 每帧画面多大 | 每页纸多大 |
| 帧率 (Frame Rate / fps) | fps | 每秒画多少帧 | 每秒翻几页 |
| 码率 (Bitrate) | bps | 每秒数据量多少 | 每秒墨水消耗 |

三者关系被编码器模式绑定：

- **CRF（恒定质量）**：画质说了算 → 码率浮动。内容越复杂码率越高。
- **CBR（恒定码率）**：码率说了算 → 画质浮动。带宽恒定但画面复杂时会糊。
- **VBR（可变码率）**：折中，给复杂段落多、简单段落少。

**带宽问题的本质：码率 ≤ 网络能稳定供给的吞吐**。码率 4Mbps 的流跑在 2Mbps 的链路上必然卡顿——ABR（自适应码率）就是按这个约束实时换档的（见 [[ABR自适应码率]]）。

## 2. 定义/原理：怎么估算

### 2.1 带宽估算链（面试必背）

```
未压缩码率 = 宽 × 高 × 1.5(B/pixel, YUV420) × fps × 8 bit
1080p@30:  1920×1080×1.5×30×8 ≈ 746 Mbps
压缩后 ≈ 未压缩 / 压缩比(约100~300×) → 2.5~8 Mbps
```

**直播带宽账**（面试常问「你们直播间并发 N 人要多少带宽」）：

```
单观众下行 = 流码率（4Mbps ≈ 0.5 MB/s）
服务端总带宽 = 码率 × 并发观众数（CDN 分摊）
例：1000 人 × 4Mbps = 4 Gbps —— 这就是必须 CDN 分发的原因（见 [[直播CDN分发链路]]）
```

### 2.2 分辨率/帧率/码率的推荐对照（H264 现实值）

| 分辨率@帧率 | 典型码率 | ≈ 每分钟流量 |
| --- | --- | --- |
| 480p@30 | 1~1.5 Mbps | 9 MB |
| 720p@30 | 2.5~4 Mbps | 22 MB |
| 1080p@30 | 4~6 Mbps | 40 MB |
| 1080p@60 | 6~9 Mbps | 56 MB |
| 4K@30 (H265) | 12~20 Mbps | 120 MB |

## 3. 实测

### 3.1 分辨率 vs 帧率的体积贡献（同源同 CRF）

> 🔗 FFmpeg 9.0，testsrc2 合成源，libx264 crf28，每次只改一个变量（10s/4s 片段按比例归一后对比）。机器不同绝对值有差异，**倍率稳定**。

分辨率维度（30fps 恒定）：

| 分辨率 | 像素倍率 | 体积 (B) | 体积倍率 |
| --- | --- | --- | --- |
| 854×480 | 0.35× | 334,841 | 基准 |
| 1280×720 | 1× | 768,133 | **2.29×** |
| 1920×1080 | 2.25× | 1,521,424 | **4.54×** |

体积倍率 ≈ 像素倍率的 ~0.8 次幂（4.54 ≈ 2.25^0.85），**近似随像素数线性增长**（合成纹理简单，真实内容会因运动复杂度略低于线性）。

帧率维度（720p 恒定）：

| 帧率 | 帧数倍率 | 体积 (B) | 体积倍率 |
| --- | --- | --- | --- |
| 15 fps | 0.5× | 614,292 | 基准 |
| 30 fps | 1× | 768,133 | **1.25×** |
| 60 fps | 2× | 954,365 | **1.55×** |

**帧率翻倍体积只涨 55%**——时间冗余被 P/B 帧吃掉了大半。对比之下**分辨率是体积的主导因子**。

### 3.2 码率-画质的实测换算

同一 1080p 源压到相同目标码率 1500k：

| 编码 | 实测码率 | 备注 |
| --- | --- | --- |
| H264 -b:v 1500k | 1621 kbps | CBR 目标下实际浮动 |
| H265 -b:v 1500k | 1467 kbps | 同码率下 H265 画质更高（SSIM 相同源对照 0.984 vs 0.983） |

**读法**：相同码率下新一代编码画质更好；换算成「省带宽」就是 H265/AV1 用 70% 的码率达到 H264 的画质——CDN 成本敏感的大厂推 AV1 的动力。

### 3.3 浏览器播放时的对应读数

播放 4Mbps 的流时，Chrome DevTools → Network 面板拉到的持续下行速率 ≈ 码率（+ 容器开销 ~1%）；`video.getVideoPlaybackQuality().droppedVideoFrames` 增长而带宽正常 → 卡顿源是**解码/渲染跟不上帧率**，不是带宽——排查卡顿先分清「带宽型卡顿（buffered 增长停滞）」还是「性能型卡顿（buffered 充足但 dropped 增长）」，见 [[播放器缓冲策略]]。

## 4. 为什么这么设计？（背后取舍）

**为什么编码器不把「无限码率」给到所有场景？**
- 带宽是共享资源、存储是真实成本。编码器的本质工作是在「码率预算」内把感知损失最小化——CRF/CBR 只是预算方式不同。**没有免费的画质，只有预算内最优的画质。**

**为什么降分辨率比降帧率更有效？**
- 实测：分辨率 2.25× → 体积 4.54×（近乎线性于像素数），帧率 2× → 体积仅 1.55×（时间冗余兜底）。且人眼对「分辨率不足」的容忍度高于「卡顿/不连贯」——所以弱网 ABR 先降分辨率、保帧率（见 [[ABR自适应码率]] 的切档策略）。

**为什么直播平台「清晰度」切换不重连？**
- 多码率转码（ABR ladder）+ 每档独立的 fMP4/TS 分片，切换 = 换拉流地址的对齐分片（需对齐到关键帧边界）。这就是 HLS/DASH 的核心设计，见 [[HLS协议原理]]。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 弱网优化 | ABR 降档顺序：先降分辨率（4K→1080p）再降帧率（60→30）最后降码率（CBR 限流） |
| 带宽预估 | 码率 × 1.05（容器开销）× 并发数 + 峰值余量 20% |
| 移动端省流 | 默认 480p/720p + WiFi 下自动升档 |
| 排查卡顿 | DevTools 看 buffered 是否停滞（带宽型）vs droppedVideoFrames（性能型） |
| 转码出片 | 一源多档 ladder：如 1080p@5M / 720p@2.5M / 480p@1M，GOP 对齐便于无缝切换 |

## 6. 面试速记

> **30 秒版**："分辨率、帧率、码率是画质三角，编码器模式决定谁说了算：CRF 恒质量码率浮动，CBR 恒码率画质浮动。实测同源编码：分辨率 480p→1080p 体积 ×4.5（近像素数线性），帧率 15→60 只 ×1.55（时间冗余兜底），所以降分辨率是省带宽第一杠杆。带宽估算：1080p@4Mbps≈0.5MB/s≈30 分钟 900MB，1000 人并发就是 4Gbps——这就是直播必须走 CDN 的原因。"
