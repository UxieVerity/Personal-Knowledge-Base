# 直播低延迟与追帧

> **结论：直播延迟 = 「推流端到播放端的全程水位」，播放端能控的只有「播放 buffer 超标就追帧、不足就保流畅」——**追帧 = playbackRate 1.1~1.5× 悄悄快进，回到直播边缘后恢复 1×**。为什么不能无限缓冲：直播的价值是「近实时」，buffer 里的存量 = 你落后主播的时间——点播存量是资产、直播存量是负债。实测依据：buffered 与 currentTime 的读数方法见 [[MSE最小播放器-验证demo]]，主时钟锚定「直播边缘」的语义见 [[音画同步策略]] §5。**

> 可运行验证：追帧触发的全部输入（buffered/currentTime/playbackRate）都可从 [[MSE最小播放器-验证demo]] 面板直接读；端到端延迟的组成拆解见 [[直播CDN分发链路]]。

## 1. 背景：延迟从哪来

端到端延迟的组成（播放端只控最后一段）：

```
推流编码 GOP/B帧 ──→ 源站转封装 ──→ CDN 分发/边缘缓存 ──→ 播放端 buffer ──→ 解码渲染
   ~1-2s              ~0.1s           ~1-3s                ←播放端可调→        ~0.1s
```

| 段 | 典型延迟 | 播放端能否控 |
| --- | --- | --- |
| 推流端（编码/GOP） | 1~2s（含 B 帧重排） | ❌（可要求推流参数） |
| 协议分发（HLS/FLV） | HLS 10s+ / FLV 2~5s / WebRTC <1s | ❌（选型决定，见 [[直播协议延迟对比]]） |
| **播放端 buffer** | 1~10s | ✅ **本篇主场** |
| 解码渲染 | <0.2s | ❌ |

播放端 buffer 是延迟链里**唯一完全可控**的一段，也是波动最大的段（网络抖动全部积累在这里）。

## 2. 定义/原理：追帧的状态机

```
直播边缘（live edge） = buffered.end(最后区间) - 安全距离(0.5~2s)

if currentTime < liveEdge - 追帧阈值(如 5s):
    playbackRate = 1.2~1.5   // 超标：悄悄快进
elif currentTime > liveEdge:
    等待/暂停下载             // 超前：贴太近会卡
else:
    playbackRate = 1.0       // 带内：正常
```

| 状态 | 判据 | 动作 | 听感 |
| --- | --- | --- | --- |
| 正常带内 | 落后 < 5s | 1× | 正常 |
| 轻度落后 | 落后 5~15s | 1.1~1.2× | 几乎无感（preservesPitch=true） |
| 重度落后 | 落后 > 15s | **丢帧追**（直接 seek 到 liveEdge 最近关键帧）或提示刷新 | 画面跳变 |
| 贴边 | 距 buffered.end < 0.5s | 先降档（ABR）保流畅 | 清晰度下降 |

**为什么阈值分级而不是一路倍速**：1.5× 以上听感明显劣化；落后超过一个量级说明网络持续不给力，硬追不如 seek（[[Seek实现与关键帧对齐]]）+ 降档。

## 3. 实测

### 3.1 「存量=负债」的量化（buffered 读数）

> 🔗 读数方法：demo 面板 buffered 与 currentTime（[[MSE最小播放器-验证demo]] §3），直播流等效观测：

```
落后量 = buffered.end(current区间) - currentTime
例：buffered=[t-8.2, t] 且 currentTime=t-8.2 → 落后 8.2s → 触发 1.2× 追帧
   1.2× 追帧每秒追回 0.2s → 8.2s 落后需 ~41s 追平（无感化过程）
```

**playbackRate 实测边界**：Chrome 允许 0.0625~16，但 >2× 声音明显失真（preservesPitch 变调算法开始救不过来）；<0.5× 拖沓感明显。**可用追帧窗口就是 1.1~1.5×**——一次追帧能消化的落后量有限，重度落后必须 seek。

### 3.2 为什么「暂停不追」的直播会越落越远

网络恢复后下载速度 > 消费速度，buffer 只会涨不会自己缩：

| 不追帧 | 追帧 |
| --- | --- |
| 落后 5s → 10s → 20s 持续累积 | 落后 5s → 1.2× 追回 → 稳定在带内 |

**追赶是被动策略失效后的主动修复**——只要消费速度恒 1×，存量单调涨；唯一能把 currentTime 拉向 live edge 的就是 >1 的消费速度或 seek。

### 3.3 B 帧与 GOP 对延迟的编码层贡献（上游实测）

- B 帧重排延迟：实测 `codecpar->delay=2`（[[I帧P帧B帧与GOP]] §3.4），直播推流常 `-bf 0` 省 2~3 帧 (~70ms)。
- GOP 越短新观众首开越快（[[I帧P帧B帧与GOP]] §3.2），但压缩率降 10% 左右——**直播延迟是全链路合谋，播放器追帧只是最后一环**。

## 4. 为什么这么设计？（背后取舍）

**为什么直播播放器不设计成「永远贴住 live edge」？**
- 贴边 = buffer 趋零 = 任何网络抖动直接卡顿。安全距离（0.5~2s）就是「延迟换流畅」的固定税；追帧机制的存在意义是**让这笔税长期保持在最低水平**（水位回落后恢复 1×）。

**为什么不无限加大 buffer 保流畅（点播思路）？**
- 直播的消费场景是「看正在发生的」：落后 60s 的「直播」在产品上已经不是直播（弹幕/竞猜/连麦全错位）。**延迟超标 = 功能性错误**，比卡顿更不可接受——这就是直播策略与点播策略的根本分叉（[[播放器缓冲策略]] §5 的「同一 buffer 两种语义」）。

**为什么重拾延迟用丢帧（seek）而不是无限倍速？**
- 倍速追帧的代价随倍率非线性上升（1.2× 无感 → 1.5× 可感 → 2×+ 破坏体验）；落后量超过 15s 时，倍速追平需要分钟级，用户早已感知「这不是直播」。**seek 是 O(1) 的延迟修复**（直接跳到边缘），代价是画面跳一次——落后越大，seek 越划算（和 ABR 切档的 hysteresis 一个思路：小扰动连续修复、大扰动离散跳变）。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 一般直播 | liveEdge = end−1s；落后 5s 起 1.2×，15s+ 走 seek |
| 强实时（竞拍/连麦） | buffer 1~2s + WebRTC 协议（见 [[直播协议延迟对比]]） |
| 追帧听感 | `video.preservesPitch = true`（默认 true，确认没被关） |
| 落后治理优先级 | 追帧 → ABR 降档 → seek → 提示刷新 |
| 观测 | 面板常驻显示「落后量」= buffered.end − currentTime |

## 6. 面试速记

> **30 秒版**："直播端到端延迟里播放端 buffer 是唯一可控段：buffered.end − currentTime 就是落后量，超标用 playbackRate 1.1~1.5 倍速悄悄追回（preservesPitch 保音调），15s 以上直接 seek 到直播边缘，追帧窗口外倍速就不划算了。为什么不能无限缓冲：直播的存量是落后时间，是负债不是资产，延迟超标是功能性错误比卡顿严重。为什么不贴边播：buffer 趋零任何抖动直接卡，安全距离是延迟换流畅的固定税，追帧机制让这笔税长期最低。"
