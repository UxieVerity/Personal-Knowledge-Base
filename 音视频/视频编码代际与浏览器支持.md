# 视频编码代际与浏览器支持

> **结论：H264（2003）→ H265（2013）→ AV1（2018）每一代同画质体积省 30%~50%，但代际越新专利/解码负担越重，浏览器支持就越碎。实测本机 Chrome 154：H264/VP9/AV1 全支持（canPlayType=probably、MSE=true），唯独 H265 MSE=false——但 `<video>` 直接播 H265 文件却能硬解播放成功（RTX 3050 NVDEC）。这就是「硬解支持矩阵碎片化」的活标本：同一浏览器内 MSE 层和 video 标签层的结论都可以不一致，自研 SDK 的 isTypeSupport 能力检测必须分通道探测。**

> 可运行验证：ffmpeg 编码对比（§3.1 实测）+ headless Chrome 能力矩阵（§3.2 实测，puppeteer-core 驱动，`canplay-probe*.js` 同目录）。

## 1. 背景：为什么编码标准不断换代

视频编码的核心目标：**同样画质，更少比特**。每代标准通过更精细的块划分、更多预测方向、更好的熵编码把体积往下压。代价是三样：**编码算力暴涨、解码复杂度上升、专利费**。

| 标准 | 年份 | 同画质 vs 上一代 | 专利 | 主推方 |
| --- | --- | --- | --- | --- |
| H264/AVC | 2003 | 基准 | 收费（MPEG LA） | ITU/MPEG |
| H265/HEVC | 2013 | -40% 左右 | **收费更狠、专利池更乱** | ITU/MPEG |
| VP9 | 2013 | ≈H265 水平 | **免费** | Google |
| AV1 | 2018 | 比 H265 再省 ~30% | **免费**（AOMedia 联盟） | Google/Netflix/AMD 等 |

H265 专利池碎片化（HEVC Advance、Velos 等多个池分别收费）直接导致浏览器厂商观望多年——这是 Chrome 桌面版长期不对 H265 开放 MSE 的根本原因，也是 AV1 诞生的推手。

## 2. 定义/原理：浏览器支持的三层探测面

浏览器里「能不能播某编码」有**三层入口，结论可能不一致**（实测证据见 §3.2）：

1. `<video>.canPlayType(mime)` —— video 标签整文件播放能力
2. `MediaSource.isTypeSupported(mime)` —— MSE 分段喂流能力（直播/自研播放器的主通道）
3. `VideoDecoder.isConfigSupported(config)` —— WebCodecs 帧级解码能力

三层背后都是「平台解码器 + 浏览器策略」，但策略开关不同：canPlayType 走平台媒体管线，MSE 走 Chrome 自家 demuxer 管线 + 白名单，WebCodecs 单独一套。**桌面 Chrome 的 H265 支持长期 = 「平台有硬解就放行 video 标签，但 MSE 默认不开」**，版本间行为还随 flags 漂移——能力检测必须三层各测。

## 3. 实测

### 3.1 编码代际的体积与速度（ffmpeg 实测）

> 🔗 环境：FFmpeg 9.0，合成源 testsrc2，preset=medium。机器不同绝对值有差异，相对倍率稳定。

同画质等体积对比（1080p，找 H265 的 CRF 使体积 ≈ H264 crf28，再比 SSIM）：

| 编码 | 体积 (B) | SSIM All | 编码耗时 (medium) |
| --- | --- | --- | --- |
| H264 crf28 | 1,521,424 | 0.9876 | 1337 ms |
| H265 crf31.5（等体积） | 1,466,451 | 0.9876 | 3744 ms（**2.8× 慢**） |

解码耗时（同机 ffmpeg 软解，120 帧 1080p）：

| 流 | 软解 | NVDEC 硬解 (RTX 3050) |
| --- | --- | --- |
| H264 | ~247 ms (speed 28.9×) | ~460 ms* |
| H265 | ~336 ms (speed 12.5×) | ~383 ms* |

> *ffmpeg CLI 整体耗时含启动开销，NVDEC 数值不作解码速度精确对比，仅证明**两条流本机 GPU 都能硬解**（exit=0）。

**结论三条**：① H265 等画质比 H264 省体积，但在低分辨率合成源上优势缩水甚至反转（见 [[编码与封装的区别]] §3.2），分辨率越高越兑现；② H265 编码贵 3~4×，推流端/转码端成本敏感场景普遍仍用 H264；③ H265 软解比 H264 慢 ~35%，是 WASM 软解方案的性能天花板约束（见 [[WASM软解H265管线]]）。

### 3.2 本机 Chrome 154 能力矩阵（headless Chrome + puppeteer-core 实测）

> 🔗 `canplay-probe*.js`：headless Chrome 154.0.8037.93（Windows 11，RTX 3050）。**canPlayType 返回 maybe/probably 只是「判断依据的强度」，空串才是确定的不支持。**

| 探测面 | H264 (avc1) | H265 (hvc1) | VP9 | AV1 (av01) |
| --- | --- | --- | --- | --- |
| `canPlayType` | `probably` | `probably` | `probably` | `probably` |
| MSE `isTypeSupported` | `true` | **`false`** | true | true |
| `<video>` 实播 H265 文件 | — | **成功**（currentTime 正常走，无 error） | — | — |

与 H265 强相关的追加实测（MSE 通道）：

| 尝试 | 结果 |
| --- | --- |
| `MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L93.B0"')`（默认 flags） | `false` |
| 同上 + `--enable-features=PlatformHEVCDecoderSupport` | 仍 `false` |
| 加 `--enable-experimental-web-platform-features` | 仍 `false` |

⚠️ **版本差异警告**：Chrome 107+ 起 H265 支持逐步放开（video 标签硬解 → MSE 视平台），且 headless/fullscreen、Windows HEVC 扩展是否安装都会影响结果。**上面的 false 只代表本机 Chrome 154 默认 flags 的实测快照，不代表所有用户**——这正是能力检测（isTypeSupport）必须运行时做而不能按 UA 表硬编码的原因，也正是自研 SDK 第一层 `isTypeSupport()` 存在的意义。

### 3.3 MSE 喂 H265 实测（等浏览器策略放开后怎么接）

在 MSE 可用的前提下（如 Edge/部分平台/未来 Chrome），fMP4-H265 的正确喂法已验证：

```
MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L93.B0, mp4a.40.2"') → true 时：
  addSourceBuffer → appendBuffer(fMP4 分片) → buffered 覆盖 4.07s → video 正常播放 ✅
```

三个实测踩坑（对 H264 同样适用，见 [[MSE最小播放器-验证demo]]）：

| 坑 | 实测报错 |
| --- | --- |
| codecs 只写视频编码，音频轨没声明 | `CHUNK_DEMUXER_ERROR_APPEND_FAILED: audio object type 0x40 does not match what is specified in the mimetype` |
| fMP4 没有 `default_base_moof` | `TFHD base-data-offset not allowed by MSE`（ffmpeg 加 `-movflags +default_base_moof` 解决） |
| tag 写 `hev1` vs `hvc1` | 参数集在sample内(sample)外(vps/sps/pps in hvcc)的封装差异，两端约定必须一致 |

## 4. 为什么这么设计？（背后取舍）

**为什么 Chrome 对 H265 如此拧巴（video 行、MSE 不行）？**
- 专利风险控制：H265 专利池收费对象是「分发解码器的商业软件」，Chrome MSE 管线里内嵌软件解码路径会放大专利敞口；video 标签走 OS 平台硬解（Windows Media Foundation / macOS VideoToolbox），解码器是微软/苹果装的，Google 不分发 → 专利风险转移。**支持矩阵碎片化不是技术问题，是法律问题的技术投影。**
- 推论：**有硬解能力的设备上 H265 才是「免费」的**——这就是自研 SDK `isTypeSupport → 硬解 H265 走 MSE，否则 WASM 软解` 这条选型链的第一性原理（见 [[硬解与软解的选型]]）。

**为什么 AV1 免费还能更省？**
- AOMedia 联盟成员（Google/Netflix/Apple/Intel/ARM…）交叉授权自己的相关专利，凑成一个专利池内免费的标准，用联盟体量对冲专利费；Netflix/YouTube 已大规模用 AV1 分发，省下的带宽就是钱。

**为什么 canPlayType 设计成 maybe/probably/空 三态而不是布尔？**
- `canPlayType` 只检查浏览器自己的静态知识（容器+codec 串白名单），不实际初始化解码器；「支持声明但不保证能解」的中间态就落在 maybe。规范原文就是「return probably if confident, maybe if possible」。这就是它**只能当初筛、不能当终审**的原因，终审要靠实际喂流（MSE append 或 WebCodecs configure）。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 播放器选编码 | 能力检测链：`MSE.isTypeSupported(h265)` → 硬解走 MSE；false → WASM 软解；H264 永远兜底 |
| 兼容性测试 | 别只信 canPlayType，用真实 appendBuffer/实播验证（本篇 §3.2 的不一致就是证据） |
| 转码出片 | Web 分发默认 H264（兼容性天花板）+ 高价值流量出 AV1/VP9（WebM）；H265 走 App 内嵌或确认平台硬解 |
| 直播推流 | H264（编码快、硬解普遍、CDN 链路最成熟），见 [[直播协议延迟对比]] |

## 6. 面试速记

> **30 秒版**："H265 同画质比 H264 省 30~40% 但编码慢 3 倍、专利池乱；VP9/AV1 免费是 Google 为绕专利推的，AV1 比 H265 再省 30%。实测本机 Chrome 154 最有意思的一点：MSE 层 isTypeSupported(hvc1)=false，但 video 标签直接播 H265 文件硬解成功——同一浏览器三层探测面结论不一致，所以播放器选路必须运行时逐层能力检测，这就是我们 SDK isTypeSupport 的第一层。"
