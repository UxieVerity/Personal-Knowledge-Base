# 视频编码代际与浏览器支持

> **结论：H264（2003）→ H265（2013）→ AV1（2018）每一代同画质体积省 30%~50%，但代际越新专利/解码负担越重，浏览器支持就越碎。实测本机 Chrome 154：H264/VP9/AV1 全支持；H265 在正常启动（GPU 可用）时 video 标签与 MSE 双双可用（isTypeSupported=true、硬解播放成功，RTX 3050 NVDEC），但 `--disable-gpu` 软渲染环境下双双关闭——Chrome 107+ 的 MSE H265 放行是「运行时探测平台硬解」而非静态白名单。同一浏览器结论仍会随 flags/环境漂移（WebCodecs 通道实测不可见），自研 SDK 的 isTypeSupport 必须运行时逐通道探测。**

> 可运行验证：ffmpeg 编码对比（§3.1 实测）+ headless Chrome 能力矩阵（§3.2 实测，puppeteer-core 驱动，`canplay-probe*.js` 同目录）。

## 1. 背景：为什么编码标准不断换代

视频编码的核心目标：**同样画质，更少比特**。每代标准通过更精细的块划分、更多预测方向、更好的熵编码把体积往下压。代价是三样：**编码算力暴涨、解码复杂度上升、专利费**。

| 标准 | 年份 | 同画质 vs 上一代 | 专利 | 主推方 |
| --- | --- | --- | --- | --- |
| H264/AVC | 2003 | 基准 | 收费（MPEG LA） | ITU/MPEG |
| H265/HEVC | 2013 | -40% 左右 | **收费更狠、专利池更乱** | ITU/MPEG |
| VP9 | 2013 | ≈H265 水平 | **免费** | Google |
| AV1 | 2018 | 比 H265 再省 ~30% | **免费**（AOMedia 联盟） | Google/Netflix/AMD 等 |

H265 专利池碎片化（HEVC Advance、Velos 等多个池分别收费）直接导致浏览器厂商观望多年——这是 Chrome 桌面版长期不对 H265 开放 MSE 的根本原因，也是 AV1 诞生的推手。

## 2. 定义/原理：浏览器支持的三层探测面

浏览器里「能不能播某编码」有**三层入口，结论可能不一致**（实测证据见 §3.2）：

1. `<video>.canPlayType(mime)` —— video 标签整文件播放能力
2. `MediaSource.isTypeSupported(mime)` —— MSE 分段喂流能力（直播/自研播放器的主通道）
3. `VideoDecoder.isConfigSupported(config)` —— WebCodecs 帧级解码能力

三层背后都是「平台解码器 + 浏览器策略」，但策略开关不同：canPlayType 走平台媒体管线，MSE 走 Chrome 自家 demuxer 管线 + 平台硬解运行时探测（复测修正见 §3.2），WebCodecs 单独一套。**Chrome 107+ 的 H265 MSE 放行 = 「运行时探测到平台硬解即放行」，但结论会随启动 flags/环境漂移**——能力检测必须三层各测、且在真实目标环境测。

## 3. 实测

### 3.1 编码代际的体积与速度（ffmpeg 实测）

> 🔗 环境：FFmpeg 9.0，合成源 testsrc2，preset=medium。机器不同绝对值有差异，相对倍率稳定。

同画质等体积对比（1080p，找 H265 的 CRF 使体积 ≈ H264 crf28，再比 SSIM）：

| 编码                | 体积 (B)    | SSIM All | 编码耗时 (medium)       |
| ----------------- | --------- | -------- | ------------------- |
| H264 crf28        | 1,521,424 | 0.9876   | 1337 ms             |
| H265 crf31.5（等体积） | 1,466,451 | 0.9876   | 3744 ms（**2.8× 慢**） |

解码耗时（同机 ffmpeg 软解，120 帧 1080p）：

| 流 | 软解 | NVDEC 硬解 (RTX 3050) |
| --- | --- | --- |
| H264 | ~247 ms (speed 28.9×) | ~460 ms* |
| H265 | ~336 ms (speed 12.5×) | ~383 ms* |

> *ffmpeg CLI 整体耗时含启动开销，NVDEC 数值不作解码速度精确对比，仅证明**两条流本机 GPU 都能硬解**（exit=0）。

**结论三条**：① H265 等画质比 H264 省体积，但在低分辨率合成源上优势缩水甚至反转（见 [[编码与封装的区别]] §3.2），分辨率越高越兑现；② H265 编码贵 3~4×，推流端/转码端成本敏感场景普遍仍用 H264；③ H265 软解比 H264 慢 ~35%，是 WASM 软解方案的性能天花板约束（见 [[WASM软解H265管线]]）。

### 3.1b VP9/AV1 的编码速度与 Chrome 支持版本（补充实测）

> 🔗 同机同源实测（FFmpeg 9.0，640×360 2s 片段，恒质量模式）：**「AV1 很慢」的说法只对参考编码器 libaom 成立，现代编码器 SVT-AV1 与 x265 同档**。

| 编码器 | 耗时 | vs H264 | 体积 | 备注 |
| --- | --- | --- | --- | --- |
| libx264 (H264) | 177 ms | 1.0× | 105,380 | 基准 |
| libx265 (H265) | 409 ms | **2.3×** | 137,781 | |
| **libvpx-vp9 (VP9)** | 1,592 ms | **9.0×** | 223,617 | Google 官方编码器，单线程架构拖累 |
| **libsvtav1 (AV1)** | 420 ms | **2.4×** | 222,250 | Intel 出的现代实现，preset 6 |
| libaom-av1（AV1 参考） | 53,656 ms | **303×** | 143,333 | 参考级质量，仅研究用 |

1080p 复测同型（2s，恒质量）：x264 1082ms / x265 1640ms（**1.5×**）/ VP9 10,768ms（**10.0×**）/ SVT-AV1 1170ms（**1.1×**，preset 8）——倍率与 360p 一致，结论稳定。

三条读数：① **VP9 是四大编码里编码最慢的主力**（libvpx 工程老、并行化差）——比 AV1 的现代编码器还慢 4×；② **AV1 编码速度已不是瓶颈**（SVT-AV1 ≈ x265），「AV1 太慢」的历史印象来自 libaom 参考实现；③ 解码侧四编码几乎无差（89~95ms，同机软解 640×360）——**新代际的成本集中在编码端，解码端已拉平**，这是「AV1 解码普及快、编码只在服务端做」的经济基础。

Chrome 支持版本（历史节点）：

| 编码 | Chrome 支持 | 节点 | 备注 |
| --- | --- | --- | --- |
| VP9 | **Chrome 29**（2013） | VP9 标准化同年 | WebM 生态，YouTube 多年主力 |
| AV1（软解） | **Chrome 70**（2018-10） | AV1 规范定稿同年 | Desktop x86-64，Main profile 0，仅解码；Chrome 67~69 藏在 flag 后 |
| AV1（硬解依赖） | 视芯片 | — | 硬解需 2022+ 硬件（RTX 30 系/Intel Arc/Apple M3/Snapdragon 8 Gen 1+）；无硬解时 4K 软解耗 CPU 明显 |
| Safari | AV1 需 **Safari 17**（2023） | — | 且实际硬解依赖 M3/A17+，AV1 在苹果生态普及最晚 |

**本机复测**（Chrome 154，无 disable-gpu 正常启动）：VP9/AV1 的 canPlayType 与 MSE isTypeSupported 均为 probably/true——**2026 年的 Chrome 里 VP9/AV1 的 MSE 通道不存在 H265 那样的策略障碍**（AV1 免专利，无敞口顾虑），唯一约束是硬件解码能力决定 4K 功耗。

### 3.2 本机 Chrome 154 能力矩阵（headless Chrome + puppeteer-core 实测）

> 🔗 `canplay-probe*.js`、`h265-env-matrix.js`：Chrome 154.0.8037.93（Windows 11，RTX 3050）。**canPlayType 返回 maybe/probably 只是「判断依据的强度」，空串才是确定的不支持。**

初测（headless + `--disable-gpu` 启动）：

| 探测面 | H264 (avc1) | H265 (hvc1) | VP9 | AV1 (av01) |
| --- | --- | --- | --- | --- |
| `canPlayType` | `probably` | `probably` | `probably` | `probably` |
| MSE `isTypeSupported` | `true` | **`false`** | true | true |
| `<video>` 实播 H265 文件 | — | **成功**（currentTime 正常走，无 error） | — | — |

#### 复测修正：false 的真凶是 `--disable-gpu`，不是「MSE 策略默认不开」

初测的 MSE=false 结论**不成立**——它被测量环境污染了。四环境对照实测（`h265-env-matrix.js`）：

| 环境 | GPU | MSE hvc1 | canPlayType |
| --- | --- | --- | --- |
| A 有头 + 默认 flags | RTX 3050（真硬解可用） | **`true`** | `probably` |
| B 有头 + `--disable-gpu` | Microsoft Basic Render Driver（软渲染） | `false` | （空） |
| C headless=new + 默认 flags | RTX 3050 | **`true`** | `probably` |
| D headless=new + `--disable-gpu` | 软渲染 | `false` | （空） |

复现最小变量：`--disable-gpu`（±swiftshader）单加即让 MSE 与 canPlayType **双双转 false/空**——与「MSE 层有没有单独白名单」无关。

**修正后的机制理解**：Chrome 107+ 的 H265 MSE 放行的判定链是「平台硬解可用性运行时探测」（`--disable-gpu` 杀掉 GPU init → 平台解码器不可用 → isTypeSupported=false），**不是静态白名单开关**。用户在 chrome://settings 开「使用硬件加速」= 有头正常启动 = MSE 直接可用——这与「MSE 只在有硬解时放行 H265」的设计（专利敞口控制：有硬解就不需要内嵌软解）自洽。

⚠️ **测量方法论教训**：headless/puppeteer 默认 flags 里的 `--disable-gpu`（工具兼容习惯）会系统性压低平台解码能力——**能力探测类实验必须对照「无 disable-gpu 的有头/新版 headless」**。下表结论以 A/C 组为准；其余各篇引用本节时按修正后口径理解。

**不变的结论**：三层探测面（canPlayType / MSE / WebCodecs）在不同 flags、不同平台、不同版本下结论仍可不一致（本机 WebCodecs 探测即不可见），isTypeSupport 运行时逐通道检测的必要性不降反升。

### 3.3 MSE 喂 H265 实测（等浏览器策略放开后怎么接）

在 MSE 可用的前提下（如 Edge/部分平台/未来 Chrome），fMP4-H265 的正确喂法已验证：

```
MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L93.B0, mp4a.40.2"') → true 时：
  addSourceBuffer → appendBuffer(fMP4 分片) → buffered 覆盖 4.07s → video 正常播放 ✅
```

三个实测踩坑（对 H264 同样适用，见 [[MSE最小播放器-验证demo]]）：

| 坑 | 实测报错 |
| --- | --- |
| codecs 只写视频编码，音频轨没声明 | `CHUNK_DEMUXER_ERROR_APPEND_FAILED: audio object type 0x40 does not match what is specified in the mimetype` |
| fMP4 没有 `default_base_moof` | `TFHD base-data-offset not allowed by MSE`（ffmpeg 加 `-movflags +default_base_moof` 解决） |
| tag 写 `hev1` vs `hvc1` | 参数集在sample内(sample)外(vps/sps/pps in hvcc)的封装差异，两端约定必须一致 |

## 4. 为什么这么设计？（背后取舍）

**为什么 Chrome 对 H265 如此拧巴（video 行、MSE 不行）？**
- 专利风险控制：H265 专利池收费对象是「分发解码器的商业软件」，Chrome MSE 管线里内嵌软件解码路径会放大专利敞口；走 OS 平台硬解（Windows Media Foundation / macOS VideoToolbox），解码器是微软/苹果装的，Google 不分发 → 专利风险转移。**MSE 对 H265 的放行条件「平台有硬解」正是这条边界的运行时体现**（复测修正：正常启动即 MSE 可用，见 §3.2）。**支持矩阵碎片化不是技术问题，是法律问题的技术投影。**
- 推论：**有硬解能力的设备上 H265 才是「免费」的**——这就是自研 SDK `isTypeSupport → 硬解 H265 走 MSE，否则 WASM 软解` 这条选型链的第一性原理（见 [[硬解与软解的选型]]）。

**为什么 AV1 免费还能更省？**
- AOMedia 联盟成员（Google/Netflix/Apple/Intel/ARM…）交叉授权自己的相关专利，凑成一个专利池内免费的标准，用联盟体量对冲专利费；Netflix/YouTube 已大规模用 AV1 分发，省下的带宽就是钱。

**为什么 canPlayType 设计成 maybe/probably/空 三态而不是布尔？**
- `canPlayType` 只检查浏览器自己的静态知识（容器+codec 串白名单），不实际初始化解码器；「支持声明但不保证能解」的中间态就落在 maybe。规范原文就是「return probably if confident, maybe if possible」。这就是它**只能当初筛、不能当终审**的原因，终审要靠实际喂流（MSE append 或 WebCodecs configure）。

## 5. 规避 / 实践

| 场景 | 手段 |
| --- | --- |
| 播放器选编码 | 能力检测链：`MSE.isTypeSupported(h265)` → 硬解走 MSE；false → WASM 软解；H264 永远兜底 |
| 兼容性测试 | 别只信 canPlayType，用真实 appendBuffer/实播验证（本篇 §3.2 的不一致就是证据） |
| 转码出片 | Web 分发默认 H264（兼容性天花板）+ 高价值流量出 AV1/VP9（WebM）；H265 走 App 内嵌或确认平台硬解 |
| 直播推流 | H264（编码快、硬解普遍、CDN 链路最成熟），见 [[直播协议延迟对比]] |

## 6. 面试速记

> **30 秒版**："H265 同画质比 H264 省 30~40% 但编码慢 3 倍、专利池乱；VP9/AV1 免费是 Google 为绕专利推的，AV1 比 H265 再省 30%。实测本机 Chrome 154 最有意思的一点：MSE 层 isTypeSupported(hvc1)=false，但 video 标签直接播 H265 文件硬解成功——同一浏览器三层探测面结论不一致，所以播放器选路必须运行时逐层能力检测，这就是我们 SDK isTypeSupport 的第一层。"
