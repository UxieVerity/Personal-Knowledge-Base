# 05 · Prompt Cache：为什么缓存价格能便宜到 1/10

> **结论先行**：大模型 API 里那个「命中缓存」价格，背后就是 **Prompt Cache（前缀缓存）**。它**不是新黑科技**，只是把上期讲的 KV Cache **从「一次请求之内」延长到「多次请求之间」**：把相同前缀算出的每一层 K/V 存起来，下次请求直接复用。能这么干，靠的还是 Transformer 那条最朴素的规矩——**只能看前面，不能看后面**（因果掩码），所以「前缀一字不差 ⇒ 这段前缀每层的 K/V 完全相同」。也因此**只有前缀能命中**：中间改一个 token，从它往后全部作废。对 Agent 开发者，这是**直接决定账单**的一条工程纪律。

## 一、现象：缓存命中价为什么这么便宜

大模型 API 定价里，除输入价、输出价外还有一个**命中缓存价**，常常只有正常输入价的 **1/10**。为什么能这么便宜？因为命中的那段**根本不用重算**——直接拿现成的 K/V 用。

## 二、先回到 KV Cache（一句话版）

因果（掩码）注意力规定：每个 token 只能看自己和**前面**的内容，看不到后面 ⇒ 新 token 出现**不改变历史 token 的计算结果** ⇒ 把每层历史 token 的 **K、V** 存下来，新 token 只拿自己的 Q 去查这些历史 KV。这就是 KV Cache，**用空间换时间**。详见 [[04-KV-Cache到底是什么]]。

## 三、KV Cache 的边界：只活在「这一次请求」里

**场景**：轩辕做了个 AI 小助手，专门回答养鹦鹉的问题。每次调用都先塞**一大段系统提示词** + **几千字饲养手册**，最后才是用户问题。

一次请求的生命周期：

| 阶段 | 做什么 |
| ---- | ---- |
| **prefill（预填充）** | 把全部输入 token 完整跑一遍，算出每层的 K 和 V |
| **decode（解码）** | 一个 token 一个 token 往外生成答案（KV Cache 主要在这里发挥作用） |

> ⚠️ **这份 KV Cache 只活在这一个请求里**。回答完「能不能吃苹果」，请求结束，这些 K/V **就被释放掉了**。

几秒钟后同一个用户又问「虎皮鹦鹉掉毛怎么办」：系统提示词一模一样、几千字手册一模一样，**只有最后的问题变了**——可模型又得从第一个 token 开始把几千字重新算一遍。**又是一种重复计算。**

## 四、凭什么说「每次算出来都一样」

因为因果注意力下：**一个 token 的 K 和 V，只取决于「它自己」以及「它前面所有的 token」**。后面跟着什么内容，完全影响不到它。

所以：

- **开头部分一字不差 ⇒ 这一段每层的 K/V 一定完全相同** → 可以复用；
- 反过来，**中间有一个 token 变了**（比如手册第 100 个 token 改了一个字）→ 第 100 个 token 的 K/V 变了 → 第 101 个 token 做注意力时会看到这个变化，结果也跟着变 → 一路传下去 → **从第 100 个 token 往后，所有缓存全部作废**。

> 🎯 **只能命中「从第一个 token 开始完全相同」的那一段——这一段就叫前缀（prefix）。**

把相同前缀的 KV Cache **跨请求**保存下来、下次直接复用，就是 **Prompt Cache**，也叫**前缀缓存**。

## 五、KV Cache vs Prompt Cache

**联系**：缓存的是同一种东西——**每一层历史 token 的 K 和 V**。Prompt Cache 存的不是你那段文字本身，而是这段文字算出来的 K/V。

**三点区别**：

| 维度 | KV Cache | Prompt Cache（前缀缓存） |
| ---- | ---- | ---- |
| **作用范围** | 一次请求**内部**（生成第 8 个 token 时复用前 7 个的结果） | **请求之间**（这次请求复用上次请求的开头） |
| **省在哪** | 主要省 **decode**，让模型往外吐字更快 | 主要省 **prefill**，前缀越长省得越多，用户感受是**首字更快出来** |
| **谁管 / 怎么收费** | 推理引擎内部的事，用户基本感知不到 | 要在服务器上存一段时间，涉及存多久、存在哪、命中怎么算钱 → 各家做成**明码标价的功能** |

> 💡 一句话：**KV Cache 是「这一句里面别重复算」，Prompt Cache 是「这一次和上一次别重复算」。**

## 六、Agent 开发者必看：为什么你的账单会很痛

一个 Agent 跑起来是这样的：

| 轮次 | 动作 |
| ---- | ---- |
| 1 | 用户：「帮我查一下明天的天气适不适合带鹦鹉出门」→ 调模型 |
| 2 | 模型决定调用天气工具 → 工具返回 → 结果**追加**到上下文 → 再调模型 |
| 3 | 模型：「还要查一下鹦鹉怕不怕冷」→ 又调一次工具 → 追加 → 再调模型 |
| … | 每调一次工具就是**一次全新的请求** |

**每一次请求都要重新发一遍**：系统提示词 + 几十个工具的定义 + 前面所有对话 + 所有工具结果。一个任务几十轮下来，上下文越滚越长，而**绝大部分输入 token 其实上一轮已经发过了**。

> 每轮都能命中缓存 ⇒ **只需要为最后新增的那一小段付全价**。所以做 Agent 开发，**一定要想办法让前缀稳住**。

### 6.1 四条实战经验

#### ① 拼出来靠前的部分要保持不变

调 API 时，工具定义、系统提示词、历史消息是请求 JSON 里的**不同字段**——JSON 里谁写在前谁写在后**其实无所谓**，模型根本不认 JSON。

服务端收到请求后会按**自家固定的模板**把这些东西拼成一条完整 token 序列再送进模型，**缓存比对的就是这条拼好的序列的前缀**。

> Anthropic 文档明确写：拼接顺序是 **工具 → 系统提示词 → 消息**。其他家模板细节略有不同，但思路差不多。

**所以重点不是你怎么排列字段，而是拼出来以后靠前的那部分每次都要一模一样。**

- ❌ 系统提示词里塞**每次都在变**的东西：用户 ID、随机数、时间戳……
- 💥 一改，后面的缓存**全部作废**。

#### ② 工具定义不要动

以 Anthropic 为例，工具定义**拼在最前面**，是整个前缀的**地基**。改一下就导致后面系统提示词和历史消息的缓存**全部失效**。

常见踩坑：

- 有的框架**每次请求都动态增删工具**；
- 或者把工具列表从一个**无序集合**里取出，导致**工具先后顺序时不时变一下**。

对人来说还是同一批工具，**可拼出来的 token 序列已经完全不一样了**——对缓存就是一个全新的前缀。

> ✅ 工具列表尽量一开始就定好，每次生成出来的内容保持完全一致。

#### ③ 历史只追加，不修改（血泪教训）

作者的亲身经历：嫌上下文太长浪费，想到「把很久之前那些超长的工具参数和结果**截断**只留开头」，又担心影响效果，于是决定**最近几轮不裁剪**、只截断很久之前的。

**问题在哪**：「最近几轮」是一个**滑动窗口**——每多交互一轮，窗口就往后挪一格，原来「不裁剪」的那一轮就掉进了要被裁剪的范围，内容被截断 ⇒ **从这个位置往后前缀全变了** ⇒ 缓存一轮接一轮地失效。

> 作者后来盯着账单里的**缓存命中率**才发现问题。把裁剪**取消掉**后，命中率瞬间上去了；更反直觉的是——**不裁剪后上下文明明更长，但因为绝大部分命中缓存，实际花的钱反而降下来了**。

✅ 历史消息**尽量只往后追加**。要补充新指令，就**追加一条新消息**，而不是回头改前面的内容。

#### ④ 上下文压缩要想清楚代价

上下文太长时很多 Agent 会做压缩：把前面几十轮总结成一小段摘要，替换掉原来那段。

**代价**：从被替换的位置开始前缀就变了 ⇒ **压缩之后的第一次请求基本要重新写一遍缓存**。

✅ 压缩不能太频繁，最好**攒到一定长度再做一次大的压缩**；压完以后新的前缀尽量保持稳定，让后面几次继续命中。

### 6.2 还有两种隐形杀手

- **中途切换模型**（不同模型的缓存不通用）；
- **切换推理强度等参数**——在很多厂商那里也会导致缓存失效。

## 七、全片总结

1. KV Cache 只活在**一次请求**里，请求结束就扔，下次相同开头还得重算；
2. 于是把**相同前缀的 KV 跨请求**保存下来 → Prompt Cache；
3. **为什么只能缓存前缀**：因果注意力下，一个 token 的 K/V 只取决于它和它前面的内容，前面任何一个 token 变了，后面全部作废；
4. Agent 每调一次工具就是一次新请求，上下文越滚越长 → **让前缀稳住**：靠前部分不变、工具定义别乱动、历史只追加不修改、别做滑动窗口式裁剪、压缩别太频繁；
5. **上下文短一点不一定更省钱，前缀稳住了长一点反而更便宜**；
6. Prompt Cache 不是新黑科技，就是把 KV Cache 从一次请求延长到了多次请求之间——靠的还是 Transformer 那条最朴素的规矩：**只能看前面，不能看后面**。

## 自查清单（贴在你的 Agent 代码旁边）

- [ ] 系统提示词是不是**纯静态**？（无时间戳 / 用户 ID / 随机数）
- [ ] 工具定义是否**稳定且顺序固定**？
- [ ] 历史是否**只追加**？有没有滑动窗口裁剪 / 回改？
- [ ] 压缩策略是否**低频、成块**，压完保持稳定？
- [ ] 有没有在会话中途**切模型 / 切推理强度**？
- [ ] 有没有在监控**缓存命中率**（而不只是总 token 数）？
