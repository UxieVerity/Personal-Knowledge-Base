# 06 · 长上下文六件套：MHA / MQA / GQA / MLA / DSA / CSA 到底在省什么

> **结论先行**：这几个缩写之所以吓人，是因为没按「**它在省哪个方向的成本**」来归类。一旦按方向归类，它们就是一条顺理成章的优化链：**KV Cache**（算过的别重算）→ 缓存太大 → **MQA / GQA**（少存几套，砍 KV 的**份数**）→ 每个 token 还是太宽 → **MLA**（把每个 token 压窄，**横着压**）→ 历史太长 → **DSA**（别全看，先初筛再精算）→ 初筛候选还是 100 万 → **CSA**（把历史压短，**竖着压**，再挑着看）。**每一次优化都是拿一点精度换算力**——这也解释了为什么「宣称百万上下文，用到五六十万就开始降智」。

## 一、先算一笔账：注意力到底有多贵

每个 token 都要拿自己的 Q 和**所有 token** 的 K 匹配一遍：

| token 数 | 两两匹配次数 |
| ---- | ---- |
| 10 | 10 × 10 = 100 |
| 100 | 100 × 100 = 1 万 |
| 1 000 000 | 1 000 000² = **1 万亿** |

> 数量涨 10 倍，计算量涨 **100 倍**。而且这还只是**一层、一个头**的账——模型有几十层，每层还有几十个头。真要老老实实算，GPU 都得干冒烟。

## 二、前置知识：prefill 与 decode 是两个阶段

从你发问题到模型开口，中间是两段完全不同的活：

| 阶段 | 含义 | 特点 |
| ---- | ---- | ---- |
| **prefill（预填充）** | 所有输入 token **一起**冲进 Transformer，每层用**这一层自己的参数**给每个 token 算这一层的 QKV（32 层就有 32 套，第二层的输入是第一层加工后的结果） | 一口气读完 → **可并行** |
| **decode（解码）** | 第一个 token 吐出来后，继续预测第二、第三…个 | 第二个 token 写什么**得等第一个写出来才知道** → **只能串行** |

> 📖 **prefill 是模型在读题，decode 是模型在一个字一个字写答案。读题可以一口气读完，答案只能一个字一个字来。**

## 三、第一招：KV Cache（第 0 层优化）

prefill 时把每层 K/V 存起来，decode 时只算新 token，直接查缓存。**第一笔浪费省掉了。**

**但新问题**：每生成一个 token，缓存就往后长一截，而且**每层都有一份、每层还有多个头**。上下文 10 万、100 万时，显存里要存的历史 KV 大得吓人。

**麻烦不只是放不下**：decode 时每写一个 token，都得把历史 KV 从显存读一遍——**GPU 往往不是算不过来，而是大部分时间花在搬数据上**（memory-bound）。

> 于是优化的三个方向出现了：① **少存几套** ② **每份小一点** ③ **别全看**。

## 四、方向一：少存几套 —— MHA / MQA / GQA

### 4.1 MHA：每人一套资料库（基线）

32 个头 → 32 个 Q、32 个 K、32 个 V。**为什么需要 32 个 Q**：一句话里的关系太多（指代、修饰、动作），多个提问角度很有价值。

> 比喻：32 个观察员，有人问「这只鹦鹉是谁养的」，有人问「羽毛什么颜色」，有人问「什么品种」——**MHA 给每个观察员都配了一整套自己的资料库**。豪华，但太占地方。

### 4.2 MQA：全公司共用一个助理

**32 个 Q 保留，K 和 V 只留一套。**

```
MHA:  Q1 Q2 ... Q32   K1 K2 ... K32   V1 V2 ... V32
MQA:  Q1 Q2 ... Q32            K            V      ← 只有一套
```

> ⚠️ 共用 KV ≠ 所有头结果一样。每个头的 **Q 不同、问的问题不同，算出的注意力权重也就不同**。

**代价**：原来每个头都能按自己的方式组织资料，现在所有人都得读同一份共享的——**砍得太狠，模型表达能力难免受影响**。

> 比喻：公司降本增效，原来 32 人每人一个专属助理，现在全公司只留一个。省钱是真省，可 32 个人排队找一个助理，谁都用得不顺手。

### 4.3 GQA：按小组裁员

在「每人一套」和「全员共享」之间取折中：**几个头一组，组内共用一套 KV**（比如 32 个头分 8 组，每 4 个头共用一个资料库）。

| 方案 | KV 份数（32 头举例） |
| ---- | ---- |
| MHA | 32 套 |
| GQA | 8 套（每组 1 套） |
| MQA | 1 套 |

> 🔑 MQA 和 GQA 砍的是**同一个东西：KV 的份数**。

## 五、方向二：每份小一点 —— MLA（多头潜在注意力）

100 万 token 下，就算从 32 套砍到 8 套，**每个 token 还是得存自己那一份**，总量还是很大。那就换个思路：**让每一份本身变小**。

### 5.1 关键洞察：几十份 K/V 同源

32 个头的 K 和 V **全都是从同一个 token 向量变出来的**。看起来是几十份独立数据，其实**源头只有一个**，每个头只是用自己的方式把同一份信息重新加工了一遍 → **大量重复内容，真正独立的信息没有看上去那么多**。

> 比喻：把一份原稿复印了几十份，每份只换了排版。你不需要存几十份复印件——**存一份原稿 + 记住几十种排版方法**就够了。

### 5.2 怎么做：压缩 → 存 latent → 用时各自展开

| 步骤 | 操作 |
| ---- | ---- |
| 压缩 | 用一个**训练出来的线性变换**，把 token 向量压成一个很短的向量 **latent（潜在表示）** |
| 存储 | 缓存里只存这个短向量（从几千上万个数字 → 几百个数字），每个 token 一小份 |
| 展开 | 用时再用一组训练出来的线性变换，把 latent 重新展开成**各个头各自需要的 K/V** |

> 🎯 **每个头都有自己专属的展开方式**：大家存的是同一份精简笔记，但每个头展开出来的 K/V **各不相同**。

**这和 MQA 的本质区别**：MQA 是所有头被迫读取**同一份 K/V**，结果只能雷同；MLA 是**共用同一个源头**，每个头仍可按自己的方式解读。

### 5.3 压缩会不会丢信息

理论上会——压成更短的向量，容量变小，不可能零损耗。但和 MQA 的一刀切有根本区别：**压缩和展开用的两组线性变换不是人工设计的，而是跟着模型一起训练出来的**。模型从头训练时就知道自己的缓存只有这么大，于是**自己学着把最有用的信息放进短向量、把重复没用的舍掉**。

> 📄 据 DeepSeek 论文的实验，MLA 在实际效果上**并不比传统 MHA 差太多**，压小了效果还能保持得不错。

> ⚠️ 真实 MLA 比这个简化描述复杂得多，理解思路即可。

## 六、方向三：别全看 —— DSA（DeepSeek Sparse Attention）

上下文 100 万，就算每个 token 都瘦得像根牙签，那也是 **100 万根牙签**。能不能让 K/V 本身**少一点被看**？

**人的做法**：「轩辕小时候养的是什么？」——你不会把前面几十万字每个字重读一遍，而是**先快速扫一遍找到相关几处，再精读那几处**。

**DSA 的做法**：别对 100 万个历史位置都做昂贵的精确注意力，**先用一个便宜的办法给所有历史位置快速打分，只挑分数最高的 top-k，真正昂贵的注意力只在这些候选里算**。

> 先初筛，再精算。

### 6.1 indexer：轻量级检索器

负责初筛的组件叫 **indexer**。它面临一个关键疑问：**训练数据千变万化，虎皮鹦鹉今天在第 3821 个 token，明天在第 80 万个，检索器怎么训练？**

> 🔑 **位置是随机的，但「什么内容和当前问题相关」不是随机的。** 普通注意力学的也不是「永远看前面第五个 token」，而是「什么样的 Q 和什么样的 K 更匹配」。**indexer 学的同样是相关性，不是位置。**

### 6.2 indexer 不需要很准

- 它只负责**筛候选**，不负责给正确答案；
- 真正重要的 token 只有几十个，它捞回来 2000 个、混进一堆没用的也没关系——**后面的正式注意力会在这 2000 个里重新计算**；
- 所以对 indexer 最重要的指标是 **召回率**：**宁可多抓几个，也不要漏掉关键的**。

## 七、方向三·续：CSA（Compressed Sparse Attention，压缩后再稀疏）

新问题：为了从 100 万里挑 top-k，**indexer 自己的候选不还是 100 万吗**？初筛虽然比精算便宜很多，可 100 万终究还是 100 万。

**解法：先让候选变小。** 把**连续的几个 token 合并成一个**——比如每 4 个位置经一个训练出来的压缩过程融合成一个更浓缩的表示，叫 **compress entry**：

```
100 万 token  --4:1 合并-->  25 万个 compress entry  --indexer 挑 top-k-->  精算
```

> 砍两刀：**第一刀先把历史压短，第二刀从压缩后的历史里挑着看** → 先压缩再稀疏 = **CSA**。

### 7.1 MLA vs CSA：最容易搞混的一对

两边都有「压缩」，但**压的方向完全不一样**。把历史缓存想成一张大表格：**横着**是每个历史位置要存多少信息，**竖着**是一共有多少个历史位置。

| 方法 | 压哪个方向 | 效果 | 一句话 |
| ---- | ---- | ---- | ---- |
| **MLA** | **横着压** | 每个 token 原来很宽，现在压窄 | 把缓存**压窄** |
| **CSA** | **竖着压** | 原来 100 万行，多个位置合并成一行，行数变少 | 把历史**压短** |

### 7.2 四个压成一个，不会丢吗

当然会。所以很自然的思路是——**分段保真**：

| 距离 | 策略 |
| ---- | ---- |
| 离当前 token **很远**的内容 | 看压缩后的摘要就行 |
| 离当前 token **很近**的内容 | 保留更精细的原始信息 |

> 📖 就像读一本很厚的书：几百页以前只剩个大概，**刚刚读过的最近几页细节还清清楚楚**。长上下文注意力的优化越来越像人「翻书找东西」的过程——**先翻目录再精读，远处记摘要，近处仔细看**。

## 八、把整条链串起来（这条最重要）

| # | 遇到的问题 | 技术 | 省的是 |
| ---- | ---- | ---- | ---- |
| 0 | 每生成一个 token，历史 KV 都重算 | **KV Cache** | 算过的别重算 |
| 1 | 缓存越来越大（层 × 头 × token） | **MQA / GQA** | KV 的**份数**（32 套 → 1 套 / 8 套） |
| 2 | 套数少了，但每个 token 存的信息还是很多 | **MLA** | 每份的**宽度**（横着压，存 latent） |
| 3 | 每个 token 都很瘦了，但历史有 100 万个 | **DSA** | 别全看（indexer 初筛 + top-k 精算） |
| 4 | 初筛的候选还是 100 万 | **CSA** | 历史的**长度**（竖着压，多个位置合一） |

> ✅ 今天的大模型能处理几十万上百万 token 却**没被注意力成本压垮**，靠的不是某一个单独的技术，而是**一整套技术、每个方向都省一点**。

## 九、回答片头的问题：为什么会「降智」

「宣称支持百万上下文，用到五六十万就开始降智」——原因不止一个：

1. **训练数据里真正很长的文本本来就少**；
2. **这些省钱的办法大多不是白省的**：压缩会丢信息，挑着看可能把真正重要的信息漏在外面；
3. **上下文越长，需要压缩的越多、需要筛选的越多，漏掉关键信息的概率也就越大**。

> 💰 **省下来的每一份算力，背后都是拿一点精度换的。** 就像公司降本增效，砍得越狠，业务出问题的风险也越大。

## 十、回头看 2017

Transformer 刚出来时，注意力最大的优势就是**让所有 token 直接建立联系**，不用像 RNN 那样一个个传话。可当上下文从几百个 token 一路涨到几十万、上百万之后，**「所有 token 都能看到其他 token」这个最大的优势，反过来变成了最大的成本**。

所以这些年注意力技术的演进，一直在两头之间找平衡：**既要保住注意力强大的信息检索能力，又要想尽办法把计算、显存、带宽的成本压下来**。而且这条路远远没走完——今天是 100 万 token，如果以后到 1000 万甚至更长，注意力还会是今天这个样子吗？

## 缩写速查卡

| 缩写 | 全称 | 一句话 |
| ---- | ---- | ---- |
| MHA | Multi-Head Attention | 每个头一套 K/V（基线） |
| MQA | Multi-Query Attention | 所有头共用**一套** K/V |
| GQA | Grouped-Query Attention | 每**组**头共用一套 K/V |
| MLA | Multi-head Latent Attention | 只存压缩后的 **latent**，用时按头展开 |
| DSA | DeepSeek Sparse Attention | **indexer 初筛 + top-k 精算** |
| CSA | Compressed Sparse Attention | 先把历史**竖着压短**，再稀疏挑选 |
