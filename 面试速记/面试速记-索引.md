## 🎯 主线一：滚动 / 渲染 / 事件机制

面试官最爱从"滚动性能"切入，这条线从底层到应用一次讲清：

```
事件循环 → Update Rendering 阶段 → scroll/wheel 事件时机 → passive →
强制同步布局 → dialog 锁滚动（实战应用）
```

**30 秒主线速记：**

| 环节                  | 一句话                                                | 详细                        |
| ------------------- | -------------------------------------------------- | ------------------------- |
| 事件循环                | 宏任务 → 微任务 → 渲染 → rIC，渲染可跳过                         | [[浏览器事件循环(EventLoop)]]    |
| Update Rendering 顺序 | resize/scroll → 动画 → rAF → 样式/布局 → RO → IO → Paint | [[Update Rendering 阶段详解]] |
| scroll 时机           | **滚动后**通知，不可取消，passive 无效                          | [[验证scroll是滚动前还是后]]       |
| wheel/touchmove 时机  | **滚动前**事件，可取消，passive 有效                           | [[验证scroll是滚动前还是后]]       |
| passive             | 承诺不 preventDefault → 浏览器不等 JS 提前滚动                 | [[scroll中的强制同步布局]]        |
| 强制同步布局              | 布局脏时读几何 → 强制重排；不脏则命中缓存                             | [[scroll中的强制同步布局]]        |
| dialog 锁滚动          | 桌面 overflow:hidden；移动端 touchmove+passive:false     | [[dialog阻止背景滚动-方案对比]]     |

## 🎯 主线二：网络链路（URL → 页面渲染）

面试官从"输入 URL 后发生了什么"切入，网络段一次讲清：

```
DNS 解析 → TCP 三次握手 → TLS 握手 → HTTP 请求/响应 → 断开连接（FIN/RST）
```

**30 秒主线速记：**

| 环节 | 一句话 | 详细 |
| --- | --- | --- |
| DNS 解析 | 域名 → IP，走 UDP 53，本地命中 ~0.03ms | [[从浏览器输入网址到页面完整展示全过程]]（§2/§4） |
| TCP 三次握手 | 确认双方收发能力 + 协商 ISN，**1 RTT** | [[TCP 三次握手（建立连接）+ 四次挥手（断开连接）]] |
| TLS 握手 | TLS1.2 需 **2-RTT**，TLS1.3 只要 **1-RTT**（0-RTT 恢复） | [[TLS12和TLS13的区别]] |
| HTTP 请求 | H1 串行 → H2 多路复用 → H3 独立流（队头阻塞演进） | [[HTTP1和HTTP2、HTTP3 的区别]] |
| 断开连接 | FIN 优雅关闭（四次挥手）/ RST 异常断开 | [[TCP FIN 和 RST：正常关闭 vs 异常断开]] |

> **连接建立往返次数（高频背记）**：H1+TLS1.2 首访 **3 RTT** → H2+TLS1.3 **2 RTT** → H3(QUIC) **1 RTT**（重连 0-RTT）。

## 🎯 主线三：音视频（自研播放器 + WASM 软解 H265）

简历两个 🔥 项目（自研播放引擎、WASM 软解）的理论底座，面试官从「播放器怎么设计的」切入：

```
编码/封装 → I/P/B 帧 GOP → video 标签 → MSE → WebCodecs → WASM 软解 →
播放器五层（拉流/demux/解码/渲染/同步）→ 缓冲水位 → 直播协议选型 → WebRTC
```

**30 秒主线速记：**

| 环节 | 一句话 | 详细 |
| --- | --- | --- |
| 编码 vs 封装 | 编码是压缩算法、封装是箱子，多对多；remux 实测 MD5 不变 | [[编码与封装的区别]] |
| 编码代际 | H265 省 30-40% 但编码慢 3 倍、专利乱；MSE 与 video 标签结论可不一致 | [[视频编码代际与浏览器支持]] |
| I/P/B 帧 GOP | B 帧重排有延迟；GOP 越长压缩越好但首开/Seek 越伤 | [[I帧P帧B帧与GOP]] |
| 播放三层 | video 整文件喂 → MSE 分段喂 → WebCodecs 逐帧喂，控制粒度逐层细 | [[video标签与canPlayType]] · [[MSE核心机制]] · [[WebCodecs与MSE的边界]] |
| 音画同步 | AudioContext 硬件钟做主轴（单调连续），视频丢帧/等帧追它 | [[WebAudio与音画同步时钟]] |
| 播放器五层 | 拉流→demux→解码→渲染→同步，层间只传带时间戳的数据，可独立替换 | [[播放器架构分层]] |
| 缓冲水位 | 点播大水位防卡、直播小水位追帧（存量是负债） | [[播放器缓冲策略]] · [[直播低延迟与追帧]] |
| WASM 软解 | MSE 不放行 H265（专利）→ Worker 解码、帧池零拷贝、WebGL 吃 YUV | [[WASM软解H265管线]] |
| 直播协议 | 延迟-成本-规模三角：HLS 10s+/FLV 2-5s/WebRTC <1s | [[直播协议延迟对比]] |

> **背记数字**：H265 等画质比 H264 省体积但软解慢 ~35%；appendBuffer 毫秒级；AudioContext 时钟 2s 漂移 <2ms；GOP 1s→10s 体积降 ~10%；CDN 1000 人 × 4Mbps = 4Gbps。
