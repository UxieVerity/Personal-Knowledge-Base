# 传输层协议 TCP / UDP / QUIC · 面试速记

> **速记定位**：面试被问到「TCP 和 UDP 的区别 / QUIC 是什么 / 为什么 HTTP/3 用 UDP」时，30 秒答完。详细见 [[TCP与UDP与QUIC的区别]]。

---

## 1. 一句话主线

> **TCP 可靠有序但串行（有队头阻塞）、UDP 最快但不可靠（无连接）、QUIC 想兼得两者——在 UDP 上自建可靠传输 + 独立流，消除队头阻塞，成为 HTTP/3 的传输层。**

- **UDP** =「尽力而为」：发出去不管，最快最轻
- **TCP** =「确保到达」：可靠有序，但一个包丢全等
- **QUIC** =「确保到达且互不拖累」：丢包只重传单流

## 2. 三协议对比（速记表）

| 维度 | TCP | UDP | QUIC |
| --- | --- | --- | --- |
| 连接 | 面向连接（三次握手） | **无连接**（直接发） | 面向连接（握手含 TLS1.3） |
| 可靠性 | ✅ 可靠（确认+重传） | ❌ 不可靠 | ✅ 可靠（独立流级重传） |
| 有序性 | ✅ 有序 | ❌ 无序 | ✅ 每流有序 |
| 队头阻塞 | ✅ **有**（一个包丢全等） | ❌ 无 | ❌ **无**（流独立） |
| 握手往返 | 1 RTT | **0 RTT** | 1 RTT（重连 0-RTT） |
| 头部开销 | 20 字节 | **8 字节** | 较大（含 TLS 状态） |
| 拥塞控制 | ✅ 内核内置 | ❌ 无 | ✅ 用户态实现（更灵活） |
| 典型应用 | HTTP、邮件、文件 | DNS、视频、语音、游戏 | **HTTP/3**、WebTransport |

## 3. 为什么 TCP 有队头阻塞，UDP 没有

> TCP 保证**有序交付**：接收方按序号组装，**一个包丢了，后续所有包（无论属于哪个请求）都等在缓冲区等重传**。UDP 不管顺序，丢包就丢，所以没这问题——但应用层得自己处理乱序/丢失。

## 4. QUIC 怎么做到「可靠 + 不阻塞」

- 在 UDP 之上把连接拆成**多个独立流**：每流独立编号、独立确认、独立重传
- **一个流丢包只重传那个流，其他流照常**——这就是消除队头阻塞
- 取舍：TCP 是「一个丢、全体等」，QUIC 是「一个丢、单流等」

## 5. 为什么 QUIC 用 UDP 而不是改 TCP（高频追问）

> 改 TCP 要**升级全球操作系统内核**（TCP 栈在内核），太慢。QUIC 在 UDP 之上**用户态**实现可靠传输——不动内核，任何支持 UDP 的系统都能跑。代价：用户态拥塞控制更复杂，且要过 NAT/中间设备的坑（部分网络限速/阻断 UDP）。

## 6. 场景选择（速答）

| 场景 | 选哪个 | 原因 |
| --- | --- | --- |
| Web 页面/API | TCP（H1/H2）或 QUIC（H3） | 需要可靠 + 快 |
| 视频/语音/直播 | **UDP**（WebRTC/SRT） | 实时性 > 完整性，丢帧可接受 |
| 在线游戏 | **UDP**（或 QUIC） | 低延迟优先 |
| DNS 查询 | **UDP 53**（大响应 TCP 回退） | 单次查询，快 |
| 弱网/移动（跨洋） | **QUIC**（HTTP/3） | 独立流 + 0-RTT + 连接迁移 |

## 7. 高频追问点

- **QUIC 连接迁移**：用 **Connection ID** 标识连接而非 IP+端口 → WiFi 切 4G 不断；TCP 靠 IP+端口，IP 一变直接断开
- **实测锚点**：TCP 串行 16 请求 = 762ms（队头阻塞证据）；DNS UDP 53 localhost 命中 ~0.03ms
- **与上层联动**：HTTP/1.1、HTTP/2 走 TCP 受队头阻塞影响；HTTP/3 走 QUIC；TLS1.3 内置进 QUIC 握手
