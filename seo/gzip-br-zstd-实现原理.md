# gzip、br（Brotli）、zstd 压缩算法实现原理

> **结论：gzip / Brotli / zstd 本质都是「两段式」无损压缩——第一段用 LZ 类算法找重复（把重复片段替换成「指回之前位置的引用」），第二段用熵编码（Huffman/ANS/FSE）把符号压得更短。三者的差异在「窗口大小」「字典」「熵编码器」三个维度：gzip 最老最兼容（LZ77 + 32KB 窗口 + Huffman，1992），Brotli 为 Web 文本优化（内置静态字典 + 大窗口 + Huffman，2015），zstd 速度优先（大窗口 + FSE 熵编码 + 可选字典，2016）。** 实测锚点：同一 126KB JS，gzip 压到 6.6KB（省 94.8%）、br 3.1KB（97.6%）、zstd 4.2KB（96.7%）；字典机制实测单个 114B JSON 从 94B 压到 **11B（省 88.3%）**；窗口实测重复距离 >32KB 时 gzip 复用不了、br/zstd 仍能压。

> 可运行验证：[[gzip-br-zstd-验证脚本.js]] —— Node 内置 zlib 实测三算法压缩比/速度、窗口大小、字典机制、压缩级别权衡

---

## 1. 背景：为什么文本能被压这么狠

- **无损压缩的前提 = 数据有冗余（redundancy）**：文本（JS/CSS/HTML/JSON）里有大量**重复的子串**和**不均衡的符号分布**（`e` 远多于 `z`、`function` 远多于 `=>`）。
- 压缩就是把这两种冗余去掉：
  - **重复子串** → 用「引用」替代（长度 + 距离），这是 LZ 家族做的事。
  - **不均衡分布** → 高频符号用短编码、低频符号用长编码，这是熵编码做的事。
- 已经**不可压缩**的内容（图片/视频/随机数据）没有冗余 → 再压无收益（实测 Part 1 随机数据 gzip/br/zstd 全部 ~0%）。

```
原始文本 → [第一段: LZ 找重复] → 符号流 → [第二段: 熵编码] → 压缩字节流
             (LZ77/LZSS)              (Huffman/ANS/FSE)
```

## 2. 第一段：LZ 类算法（找重复）

### 2.1 LZ77 核心思想

> **结论：LZ77 用「滑动窗口 + 字典引用」压缩——维护一个向前看的窗口，发现「当前字符串在过去出现过」就输出一个 `(距离, 长度)` 引用，而不是重复输出原文。**

```
输入:  abcdefgabcdxyz
              ↑↑↑↑
          "abcd" 在 7 个字符前出现过 → 输出引用 (dist=7, len=4)，而不是再写一遍 abcd
```

- **窗口（Window）**：LZ 能「回看多远」= 窗口大小。窗口内才找得到重复，窗口外复用不了。
- **关键参数**：`(dist, len)` 引用 + 字面量（literal）交替。压缩率取决于「引用覆盖了多大比例」。

### 2.2 三者的窗口差异（实测重点）

| 算法 | 窗口大小 | 含义 |
| --- | --- | --- |
| gzip (DEFLATE) | **固定 32KB** | 重复距离 >32KB 就复用不了 |
| Brotli | 16KB ~ 16MB（可选） | 大窗口能找到更远的重复 |
| zstd | 1KB ~ 128MB（可选） | 窗口最大，长距离重复也能压 |

> 实测（Part 2）：构造「40KB 前缀 + 40KB 相同后缀」（重复距离 40KB > gzip 窗口）——gzip 压到 155B（只利用了窗口内的短重复）、br 22B、zstd 29B。**大窗口让「长距离重复」也能被复用**，这正是 br/zstd 对「大文件」压缩率优于 gzip 的机制之一。

## 3. 第二段：熵编码（把符号压短）

> **结论：LZ 之后的数据流仍然有符号分布不均——高频出现的符号（如 `e`、空格、`function`）值得用更短的码。熵编码就是「按频率分配码长」：高频短码、低频长码。**

### 3.1 Huffman 编码（gzip / br 用）

- **思想**：构造哈夫曼树，出现频率越高的符号码长越短。`e`（频率 12%）用 3 bit，`z`（频率 0.1%）用 10 bit。
- **gzip**：静态 Huffman（预置固定码表）或动态 Huffman（随数据建表，表也要存）。
- **Brotli**：Huffman 的一种变体，配合它的「上下文建模」——**根据前一个字符预测下一个字符的分布**，选不同的 Huffman 树（context modeling），压缩率更高。

### 3.2 FSE / ANS（zstd 用，更快）

- **zstd 的熵编码器是 FSE（Finite State Entropy）**，是 ANS（Asymmetric Numeral Systems）的一种实现。
- **为什么更快**：Huffman 一次编码一个符号（bit 级操作），ANS/FSE 用**数学变换**把多个符号编码进一个整数，吞吐更高、解压也快。
- **代价**：实现复杂（专利/复杂度门槛高），所以 br 没用 FSE（当时 FSE 有专利顾虑），zstd 用 FSE。

## 4. 字典：Brotli 的杀手锏 vs zstd 的可选

> **结论：字典 = 预先把「这类数据的典型样本」喂给压缩器，压缩时直接引用字典里的重复 → 小文件也能压得很小。Brotli 内置一个 120KB 的静态 Web 字典（常见 HTML/JS/CSS 的 token），zstd 支持自定义/训练字典。**

### 4.1 为什么小文件需要字典

- LZ 的窗口机制对**小文件**很吃亏：文件太小，窗口里「过去的重复」太少，无处引用。
- 字典提供「文件之外的历史」——压缩器可以把字典内容当作窗口的前缀，`(dist, len)` 直接引用字典里的常见 token。

### 4.2 Brotli 的静态字典（实测 Part 3 验证机制）

- Brotli 内置约 **120KB 静态字典**（RFC 7932 附录），预置了 Web 常见字符串：`<div`、`function`、`class`、`https://` 等。
- 实测（Part 3，用 zlib 原生 deflate 字典验证同机制）：单个 114B JSON，无字典 94B → 带字典 **11B（省 88.3%）**。字典让「小而相似」的输入压缩率暴增。
- **这就是为什么 br 对「小 HTML/JS」压缩率明显优于 gzip**——gzip 没有 Web 字典。

### 4.3 zstd 的可选字典

- zstd 支持 `ZSTD_compress_usingDict`（任意参考字节）和 **trained dictionary**（用大量样本训练出最优字典）。
- 典型场景：服务器对「结构相似的一批小 JSON 响应」训练一个字典 → 每个响应都压得很小。
- ⚠️ **Node 内置 zstd 封装未暴露字典/级别 API**（实测 dict 选项无效、level 各级别输出相同），真实 zstd 字典需 `zstd` npm 包（node-gyp 编译）或原生 CLI。

## 5. 三算法对比总表

| 维度 | gzip (DEFLATE) | Brotli (br) | zstd |
| --- | --- | --- | --- |
| 发布 | 1992 (RFC 1952) | 2015 (RFC 7932) | 2016 (RFC 8878) |
| 作者/背景 | Jean-loup Gailly (gzip) | Google | Meta (Yann Collet) |
| 第一段（找重复） | LZ77 | 自定义 LZ77 | LZ77 变体 |
| 窗口大小 | **固定 32KB** | 16KB~16MB | 1KB~128MB |
| 字典 | ❌ 无 | ✅ **内置 120KB Web 静态字典** | ✅ 可选自定义/训练字典 |
| 第二段（熵编码） | Huffman | Huffman（+上下文建模） | **FSE (ANS)** |
| 速度 | 中 | **慢**（高复杂度） | **快** |
| 压缩率 | 最低 | **最高**（小文本尤其） | 高（接近 br） |
| 浏览器支持 | ✅ 全 | ✅ 全（Safari 15+） | ⚠️ Chrome 实验支持 |
| 适用 | 兼容优先、老系统 | 静态 Web 资源 | 动态响应、大数据、需速度 |

### 实测数据（Node zlib，同一 126KB JS bundle）

| 算法 | 级别 | 压缩后 | 节省 | 耗时 |
| --- | --- | --- | --- | --- |
| gzip | 6 | 6,621B | 94.8% | 1.4ms |
| br | 5 | 3,063B | 97.6% | 2.1ms |
| zstd | 3 | 4,179B | 96.7% | 0.9ms |

> **读法**：压缩率 br 最高、gzip 最低；速度 zstd 最快、br 最慢。zstd 是「速度/压缩率」平衡最好的一档。

## 6. 压缩级别：不是越高越好（实测）

> **结论：级别越高压缩率越高但越慢，且到高端有「收益递减甚至反噬」——Brotli 级别 10-11 是 text mode 高复杂度，压缩率不升反降、耗时暴增。**

实测（Brotli 0~11，Node 真实生效，162KB 自然语言）：

| 级别 | 压缩后 | 节省 | 耗时 |
| --- | --- | --- | --- |
| 0 | 10,310B | 93.6% | 0.5ms |
| 1 | 3,906B | 97.6% | 0.7ms |
| 4 | 2,952B | 98.2% | 0.9ms |
| 6 | 3,073B | 98.1% | 2.7ms |
| 9 | 2,595B | 98.4% | 7.1ms |
| 11 | 3,183B | 98.0% | **352.1ms** |

> **读法**：lvl 1→9 压缩率从 97.6% 爬到 98.4%（收益 0.8pp）但耗时从 0.7ms 涨到 7ms（10×）；lvl 11 耗时 352ms（50×）压缩率反而**下降**。所以 Web 实践：静态资源用 br lvl 5-9（一次压反复用），动态响应用低级别（快）。zstd 的 1~22 同理，默认 3 已很均衡。

## 7. 为什么这么设计？（背后取舍）

- **为什么 gzip 窗口固定 32KB**：1992 年内存珍贵，窗口越大内存占用越高（且要存查询表）。32KB 是当年「压缩率/内存」的折中。今天看是短板，但**兼容性**让 gzip 无法改（改了就不是 gzip）。
- **为什么 Brotli 内置静态字典**：Web 文本的 token 高度重复（`<div`、`class`、`function` 到处都是），字典把这些「文件外的高频词」变成免费引用 → 小文件压缩率远超 gzip。代价：**字典是固定的**，对非 Web 数据无效。
- **为什么 zstd 用 FSE 不用 Huffman**：FSE/ANS 编码/解码吞吐更高（一次处理多符号），满足 zstd「速度优先」的定位。代价：实现复杂、有专利顾虑（Brotli 当年因此避开）。
- **为什么三者的熵编码器不同**：Huffman 简单通用但慢、FSE/ANS 快但复杂。取舍 = **实现简单度 vs 吞吐**。
- **为什么 br 压缩最慢**：它可选大窗口 + 上下文建模 + 高压缩级别，算法最复杂。但 Web 静态资源「一次压缩、反复下发」，慢的代价被摊薄 → 值得用高压缩率换 CPU。
- **为什么 zstd 适合动态内容**：压缩快 → 每次请求现压也不心疼；解压也快 → 客户端/服务器开销低。这是它作为「新一代通用压缩」定位的原因。

## 8. 面试速记

- **一句话**：三者都是「LZ 找重复 + 熵编码」，区别在窗口、字典、熵编码器——gzip 最老兼容（LZ77+32KB+Huffman）、br 为 Web 优化（内置 120KB 静态字典+大窗口+Huffman+上下文建模）、zstd 速度优先（大窗口+FSE）。
- **为什么 br 比 gzip 小 20~30%**：静态字典（小文件）+ 大窗口（长重复）+ 上下文建模 Huffman。
- **为什么 zstd 最快**：FSE 熵编码器吞吐高 + 低级别压缩就够。
- **级别不是越高越好**：br lvl 11 耗时 50× 压缩率反降，静态用 5-9、动态用低级别。
- **字典怎么用**：给小而相似的数据（一批小 JSON）训练字典 → 压缩率暴增（实测 88%）。
