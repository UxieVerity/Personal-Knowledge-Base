# 网络层优化（SEO/性能：网络链）

> **结论：网络层优化的目标 = 把「TTFB（首字节）+ 资源下载总耗时」压到最低。核心手段五件套——① CDN（边缘缓存 + 就近分发，减少回源 RTT）、② 压缩（gzip/br 减少传输字节）、③ 缓存（命中=0 请求）、④ 云服务商 DNS（智能解析/Anycast/DoH 加速 DNS 与调度）、⑤ HTTP 版本升级（H2/H3 解决并发）。** 实测锚点：同一份前端 bundle，gzip 压缩省 **94%** 传输字节、br 再省 **57%**（比 gzip）；CDN 边缘缓存命中后源站 **0 回源**，3 次请求只回源 1 次；智能 DNS 按地域把用户导向不同 IP（广州/上海/海外各连最近节点），普通 DNS 全挤源站；H1 串行 16 资源 **762ms** → H2 单连多路复用 **60ms**（≈12.7×）；缓存命中二次访问 **0 网络请求**。网络层优化是「面试中最好拿分的部分」——每一招都有明确指标可量化。

> 可运行验证：[[CDN与压缩-验证脚本.js]]（gzip vs br 压缩比、Accept-Encoding 协商、CDN 边缘命中 vs 回源）；[[云服务商DNS-验证脚本.js]]（智能解析/TTL/DoH 实测）；[[HTTP1vsHTTP2-验证脚本.js]]（H1 串行 vs 6 连接 vs H2 多路复用 vs H3 独立流）；[[重定向与缓存-验证脚本.js]]（301 跟随、缓存命中 0 请求、no-cache→304、no-store 全量）；[[DNS解析路径-验证脚本.js]]（DNS 命中 vs 网络查询、GFW 分析）

## 1. 背景：网络链在哪里、瓶颈是什么

```
[前置逻辑]          [网络请求链]                                [渲染链]
缓存查找 → DNS → TCP → TLS → HTTP请求 → HTTP响应 → (进入渲染)
   ↑        │      │      │       │         │
   └─命中=0  │      │      │       │         └→ 3xx 回到前置逻辑
            │      │      │       └→ 重定向每跳=+1 RTT
            │      │      │
            │      │      └→ TLS1.2 2RTT / TLS1.3 1RTT
            │      └→ 1 RTT
            └→ 10~100ms（未命中）
```

- **网络链的性能瓶颈在「延迟 + 带宽」两个维度**：
  - **延迟**：DNS、TCP、TLS、服务器处理、网络 RTT 叠加决定 TTFB → 用云 DNS 加速解析、CDN 就近分发、缓存、0-RTT、连接预热解决。
  - **带宽/传输字节**：资源体积越大下载越慢 → 用 gzip/br 压缩、tree-shaking、代码分割解决。
- **网络链优化的本质**：能省的 RTT 省掉（缓存、CDN、云 DNS 智能调度、0-RTT、复用连接），能并行的并行（H2 多路复用），能变小的变小（压缩），能跳过的跳过（减少重定向）。
- **与渲染链的关系**：网络层决定了「HTML 什么时候到」，渲染层决定「到了之后什么时候画出来」。两段独立优化、互不替代。

## 2. 缓存：命中 = 0 网络请求（收益最大）

> **结论：缓存是网络层性价比最高的优化——命中新鲜副本时，整个网络链（DNS/TCP/TLS/请求/响应）全部短路，0 网络请求、0 RTT。** 实测二次访问 `/new`（`max-age=60`）时服务器完全没收到请求；`no-cache` 虽每次校验，但 304 只回 0B 响应体，省带宽不省请求。

### 2.1 缓存查找顺序

```
Service Worker(Cache API) → 内存缓存(最快) → 磁盘缓存(持久) → 网络
              ↑ 命中即短路，不发网络请求
```

### 2.2 强缓存 vs 协商缓存

| 维度 | 强缓存 | 协商缓存（条件请求） |
| --- | --- | --- |
| 触发 | 新鲜期内（`max-age` 未过期） | 过期后 / `no-cache` |
| 是否发请求 | **否，0 网络请求** | 是，但只带校验头 |
| 响应 | 直接本地读 | 服务器回 **304**（0B）或 **200**（变了） |
| 关键头 | `Cache-Control: max-age`、`Expires` | `ETag/If-None-Match`、`Last-Modified/If-Modified-Since` |

### 2.3 最优策略（面试常问「缓存怎么配」）

| 资源类型 | 策略 | 说明 |
| --- | --- | --- |
| 静态资源（JS/CSS/图片） | `Cache-Control: max-age=31536000, immutable` + **hash 文件名** | 内容变→URL 变→天然失效，可永久缓存 |
| HTML | `no-cache` 或 `max-age=0` | 必须每次校验，避免拿到旧页面 |
| 用户数据/接口 | `no-store` 或 `private, no-store` | 不进共享缓存 |
| 未配缓存头 | 浏览器**启发式缓存** `(Date−Last-Modified)×10%` | 「没配却被缓存」的原因，尽量显式配置 |

> ⚠️ **hash 文件名 + 长缓存**是静态资源最优解：把「新鲜度判断」从服务器端（304 校验）转移到 URL 层（内容变 URL 就变），彻底消灭 304。

> 可运行验证：[[重定向与缓存-验证脚本.js]] —— 实测六种缓存语义。

## 3. 云服务商 DNS：智能解析 + 加密 + 就近（网络链第一跳）

> **结论：云服务商 DNS（阿里云 DNS / 腾讯 DNSPod / AWS Route 53 / Cloudflare DNS）用「智能解析 + Anycast + 健康检查 + DoH」替代默认运营商 DNS，是网络链第一跳的优化。** 实测：智能 DNS 按用户地域返回不同 IP（广州→华南节点、上海→华东节点、海外→海外节点），普通 DNS 固定一个 IP 让所有用户都挤源站；DoH 实测国内 Cloudflare 端点不可达（GFW），实际用阿里/腾讯的 DoH。

### 3.1 默认运营商 DNS 有什么问题

| 问题 | 说明 |
| --- | --- |
| 无智能调度 | 只做「域名→IP」一对一，不按用户位置就近返回 |
| 明文可劫持 | UDP 53 明文 → 运营商/攻击者可 DNS 劫持（插广告）、污染（假 IP） |
| 无健康检查 | 源站挂了 DNS 不感知，用户一直连坏的 |
| TTL 不可控 | 缓存太久 → 故障转移慢 |

### 3.2 云服务商 DNS 的四个能力（面试背这四点）

1. **智能解析（GSLB/GeoDNS）**：按「来源地域 + 运营商」返回不同 IP，把用户导向最近的服务器/CDN 节点。这是 CDN 路由的前提（CDN 依赖智能 DNS 做第一跳）。实测：同一域名，广州用户→120.196.0.1、上海→101.226.0.1、海外→8.8.8.1。
2. **Anycast 就近解析**：DNS 解析服务器本身全球多机房广播同一 IP（阿里 223.5.5.5、腾讯 119.29.29.29），BGP 自动把用户路由到最近机房——解析请求本身也快。
3. **健康检查 + 自动切换**：定时探测源站（HTTP/TCP），挂了自动把解析切到备用 IP。**故障转移时间 ≈ 最坏 TTL**：TTL=60 → 最多 1 分钟切完；TTL=1 周 → 最坏一周才切（灾难）。所以关键域名用短 TTL + 云 DNS 健康检查。
4. **DoH / DoT 加密**：DNS 查询走 HTTPS:443（DoH）或 TLS:853（DoT），防运营商劫持/污染/窥探。传统 DNS UDP:53 明文。

### 3.3 TTL 与故障转移（面试高频）

| TTL | 缓存失效 | 最坏故障转移时间 | 适用 |
| --- | --- | --- | --- |
| 60s | 1 分钟 | ≤1 分钟 | 频繁变更/负载均衡（A/B、灰度） |
| 600s（默认） | 10 分钟 | ≤10 分钟 | 常规 |
| 86400（1天） | 1 天 | ≤1 天 | 稳定记录 |
| 604800（1周） | 7 天 | ≤7 天 | 静态（但故障转移灾难） |

> 结论：**TTL 是「查询频率」与「更新/故障转移速度」的取舍**——想切换快就短 TTL（代价是查询多、依赖 DNS 服务稳定性）；想省查询就长 TTL（代价是故障转移慢）。

### 3.4 DoH 实测与国内现状

- **实测**：脚本用 Cloudflare 1.1.1.1 的 DoH 端点（cloudflare-dns.com）查询 `www.baidu.com`/`www.github.com` → **网络不可达**（GFW 封锁），符合 [[DNS解析路径-验证脚本.js]] 里「能解析但连不上」的结论。
- **国内实践**：用**阿里 223.5.5.5（dns.alidns.com/resolve）** 或 **腾讯 DNSPod 119.29.29.29** 的 DoH——既是加密、又能就近、还不会被墙。
- **DoH 的意义**：运营商只见「你在访问 223.5.5.5 的 443」，看不到你查了哪个域名 → 防 DNS 劫持（不再被运营商插广告/跳转到错误页）。

> 可运行验证：[[云服务商DNS-验证脚本.js]] —— 智能解析/TTL 模拟 + 真实 DoH 查询（含国内被墙降级）。

## 4. CDN：边缘缓存 + 就近分发（收益最大之二）

> **结论：CDN（Content Delivery Network，内容分发网络）把内容缓存到离用户最近的边缘节点，用户请求打到边缘而非源站——省掉「用户→源站」的长距离 RTT，源站压力骤降。** 实测：同一资源 3 次请求，只有第 1 次回源，后 2 次全部命中 CDN 边缘缓存（源站收到请求数 = 1）。

### 4.1 CDN 是什么、解决什么问题

- **本质**：在全球/全国部署一组「边缘节点」，把源站内容（静态资源、可缓存的动态内容）缓存到节点上。用户访问时由**智能 DNS / GSLB（全局负载均衡）** 把请求路由到**最近的节点**。
- **解决的问题**：
  - **跨地域延迟**：用户到源站可能要跨省/跨国（几百 ms），到边缘节点只有几 ms~几十 ms。
  - **源站压力**：边缘命中 → 源站 0 请求，扛住突发流量/秒杀。
  - **带宽成本**：流量走 CDN 比走源站带宽便宜。
  - **附带能力**：DDoS 防护、WAF、TLS 卸载（边缘终结证书）、边缘计算（可编程 CDN/Edge Function）。

### 4.2 CDN 请求流程（命中 vs 回源）

```
用户请求 → 智能 DNS 解析到最近边缘节点
            ↓
  ① 边缘节点查本地缓存
      ├─ 命中新鲜 → 直接返回（源站 0 请求）     ← 用户延迟 = 到边缘的 RTT
      └─ miss / 过期 → 回源取内容，写缓存，返回  ← 首次延迟 = 到边缘 RTT + 到源站 RTT
```

- **回源（origin fetch）**：边缘节点缓存中没有/过期时，向源站请求原始内容，拿到后**按响应头的缓存策略**写入边缘缓存。
- **命中率**：`(总请求 − 回源请求) / 总请求`。越高越好——静态资源理想 95%+。

### 4.3 关键：CDN 缓存与浏览器缓存的区别

| 维度 | 浏览器缓存 | CDN 边缘缓存 |
| --- | --- | --- |
| 位置 | 用户本地 | 边缘节点 |
| 谁受益 | 单个用户（再次访问） | 所有访问该节点的用户（首次也快） |
| 控制头 | `Cache-Control`（浏览器读） | **`Cache-Control: public`** + `s-maxage`（CDN 读） |
| 失效 | URL 变 / 手动清 | 主动刷新（CDN 控制台 Purge）/ TTL 到期 |

> **关键区分 `public` vs `private`**：`public` 才允许 CDN/共享代理缓存；`private` 只允许浏览器缓存（如带用户信息的响应）。想走 CDN 必须 `public`（或 `s-maxage` 专门给 CDN 设的缓存时长）。

### 4.4 实践要点

- **静态资源全量上 CDN**：JS/CSS/图片/字体，配 hash 文件名 + `public, max-age=31536000, immutable` → 永久缓存、几乎不回源。
- **动态内容选择性缓存**：可缓存接口配 `public, s-maxage=60`（CDN 缓存 60s，源站 60s 只被打一次）；个性化内容 `private`/`no-store`。
- **回源策略**：CDN 回源时带上 `X-Forwarded-For`（真实用户 IP）、`Via`（代理链）。源站要能识别 CDN 回源，避免回源也走 CDN 死循环。
- **热点/秒杀**：把可预测的峰值内容预热（Purge/预热到边缘），避免首波回源打爆源站。
- **与云 DNS 联动**：CDN 的 CNAME 记录托管在云 DNS 上，智能 DNS 决定「用户去哪个边缘节点」——云 DNS 是 CDN 的第一跳。

## 5. 压缩：gzip / br 减少传输字节

> **结论：压缩是「一配就见效、零改代码」的优化——浏览器声明支持，服务器把文本资源压缩后再传，传输字节大降。** 实测同一前端 bundle：gzip 把 127KB 压到 7.4KB（省 **94%**），br 压到 3.2KB（比 gzip **再小 57%**）。**br（Brotli）通常比 gzip 小 20~30%**，是现代浏览器的首选编码。

### 5.1 压缩原理（为什么文本能压这么狠）

- 文本类资源（JS/CSS/HTML/JSON）**冗余度极高**：关键字、结构、重复片段到处都是。
- **gzip（DEFLATE）**：LZ77 找重复 + Huffman 编码，经典算法，兼容性最好。
- **br（Brotli，RFC 7932）**：Google 2015 年推出，内置**静态字典**（预置了常见 HTML/JS/CSS 的 token），对 web 文本压缩率更高，且可更高压缩级别。
- 已经**不可压缩**的内容（已压缩的图片/视频、随机数据）再压无收益，反而浪费 CPU。

### 5.2 Accept-Encoding 协商（怎么决定用 gzip 还是 br）

```
浏览器请求头:  Accept-Encoding: gzip, deflate, br   （声明支持哪些编码，br 优先级最高）
服务器响应头:  Content-Encoding: br                 （实际用了哪种编码，浏览器据此解压）
              Vary: Accept-Encoding                 （告诉 CDN/代理：不同编码要分别缓存！）
```

- **流程**：浏览器在请求头声明支持哪些编码 → 服务器选一个（通常 br 优先，降级 gzip）→ 压缩后加 `Content-Encoding` 返回 → 浏览器解压后使用。
- **Vary: Accept-Encoding 必配**：否则 CDN 缓存了 br 版本，发给不支持 br 的老浏览器就乱码。配了它 CDN 才会按编码分别缓存。

### 5.3 实测：不同内容的压缩率（Node zlib）

| 内容 | 原始 | gzip | br | br/gzip |
| --- | --- | --- | --- | --- |
| 前端 bundle（结构代码） | 127,049B | 7,440B（省 94%） | 3,182B（省 97.5%） | 43% |
| JSON（接口数据） | 130,781B | 10,590B | 4,684B | 44% |
| HTML | 21,073B | 185B | 72B | 39% |
| 纯随机文本（不可压缩） | 20,000B | 12,088B | 11,920B | 99% |

> 结论：**文本类 br 普遍比 gzip 小 20~30%（甚至更多）；随机数据/已压缩内容两者都无收益** → 压缩只对「有冗余的文本」有效，图片/视频不要二次压缩。

### 5.4 实践要点

- **默认开 br**：现代浏览器（Chrome/Edge/Firefox/Safari 15+）都支持 br。服务器配置 `brotli on;`（nginx）即可。
- **优先压缩大文本**：JS/CSS/HTML/JSON/SVG；图片视频本就压缩过，别压（浪费 CPU）。
- **压缩级别权衡**：br 级别 1-11，级别越高越小但越慢（CPU）。静态资源用高等级（一次压、反复用），动态响应用低等级。
- **与 CDN 配合**：CDN 通常自动做 br/gzip 协商 + 缓存，源站只需保证 `Vary: Accept-Encoding` 正确。

## 6. HTTP 版本升级：并发与队头阻塞

> **结论：HTTP/2 用 1 条连接 + 多路复用做到比 HTTP/1.1 的 6 条连接还快——实测 16 资源 H1 串行 762ms → H2 60ms（12.7×）。** 若仍卡在 H1，再好的缓存也只是减少请求次数，无法解决单连接串行的并发瓶颈。

| 模型 | TCP 连接数 | 16 资源总耗时 | 结论 |
| --- | --- | --- | --- |
| HTTP/1.1 单连接 | 1 | 761.6ms | 队头阻塞：严格串行 |
| HTTP/1.1 6 连接 | 6 | 153.9ms | 浏览器上限，缓解 |
| HTTP/2 多路复用 | **1** | **59.5ms** | 1 连接全并行 |
| HTTP/3 QUIC | 1 | 46ms（丢包最慢流） | 连 TCP 层 HOL 也消除 |

- **为什么快**：H1 一条连接一次一个请求（文本协议无法区分帧属于谁）；H2 二进制分帧 + Stream ID，1 连接 N 流并行；H3 用 QUIC/UDP 把流独立，丢包只拖慢单流。
- **实践要点**：
  - 启用 H2/H3 需 **TLS**（ALPN 协商），HTTPS 是前提。
  - 域名收敛：HTTP/1.1 时代「域名分片」榨干 6 连接，H2 时代**有害**（分片反而多连接、多 TLS 握手），应收敛到单域。
  - 资源合并（CSS/JS 打包）在 H2 下收益变小，但小文件太多仍有效率问题（每个请求有头开销），适度合并 + `http2-push` 已废弃少用。
- **面试一句**：H1→H2 靠「二进制分帧+多路复用」消灭应用层 HOL，H2→H3 靠「QUIC 独立流」消灭 TCP 层 HOL。

> 可运行验证：[[HTTP1vsHTTP2-验证脚本.js]] —— 三模型 + 丢包对比实测。

## 7. 减少重定向（纯开销）

> **结论：重定向是网络层的纯负资产——每跳一次 = 多 1 个完整 RTT + 多 1 次请求响应，浏览器还要限跳 20 次防死循环。** 优化 = 减少跳数、避免链式重定向、把重定向逻辑前移到 CDN 边缘。

- **常见来源**：`http://`→`https://`、`www`↔非 www、`/` 缺失、旧链接 → 新路径、地域/设备跳转。
- **度量**：打开 DevTools Network，看 waterfall 里有没有多余灰色跳转条目；`Performance` 里 `redirectCount`（Navigation Timing 的 `redirectCount` 字段）。
- **对策**：
  - 一次跳转到达（避免 /a→/b→/c 链式）；
  - 能配 CDN 301 就别让源站 302 每次算；
  - 新老域名并存期后**删除**旧跳转（避免永久依赖）；
  - `www` 与根域在 DNS 阶段统一（两条 A 记录指向同 IP，或 CDN 上 301）。
- **状态码要点**：301/308 可被缓存（永久）、302/303/307 默认不缓存（临时）；308/307 保留 POST 请求体、301/302 会丢。

> 详见 [[从浏览器输入网址到页面完整展示全过程]] §3.1（状态码语义表）。

## 8. 连接预热：dns-prefetch / preconnect / preload

> **结论：把「未来才需要的连接」提前到当前空闲时段建立——dns-prefetch 提前解析 DNS、preconnect 提前建好 TCP+TLS、preload 提前下载关键资源。** 网络层优化中「用空闲带宽换未来延迟」的标准手法。

| 手段 | 提前做的事 | 省掉的 RTT | 用法 |
| --- | --- | --- | --- |
| `dns-prefetch` | DNS 解析 | ~1 个 DNS RTT | `<link rel="dns-prefetch" href="//api.x.com">` |
| `preconnect` | DNS + TCP + TLS | DNS+TCP+TLS 全部 | `<link rel="preconnect" href="https://api.x.com" crossorigin>` |
| `preload` | 下载资源本身 | 请求+下载时间 | `<link rel="preload" as="script" href="x.js">` |
| `prefetch` | 下载**未来导航**资源 | 下次导航的时间 | `<link rel="prefetch" href="next-page.html">` |

- **preconnect 优先级**：只对「首屏必用 + 跨源」的少数域名用（每个 preconnect 都占用浏览器连接预算，过多反而挤占主资源）。
- **preload vs 浏览器自动发现**：preload 强制优先下载，适合「首屏关键但藏在 CSS/JS 深处」的资源（如字体、首屏图）。

## 10. 为什么这么设计？（背后取舍）

- **缓存先于网络**：本地读 μs 级 vs 网络几十 ms RTT，「速度 > 新鲜度」→ 用新鲜期 + 协商校验换取极速命中，接受「最终一致性」。
- **TTL 是「快 vs 稳」的取舍**：短 TTL 故障转移快但要频繁查询（依赖 DNS 可用性），长 TTL 省查询但故障转移慢。云 DNS 用「健康检查」在两者间兜底。
- **DoH 用「加密」换「防劫持」**：DNS 走 HTTPS 防运营商劫持，但多了 TLS 握手 + 依赖 DoH 服务器可用（国内 Cloudflare 被墙就是例子）。取舍：**隐私安全 > 极简**。
- **CDN 用「分布式缓存」换「就近」**：把内容复制到全世界边缘节点，用**存储换延迟**。代价是缓存一致性变难（更新要 Purge）、首访必回源。取舍：**就近 RTT > 全局一致**。
- **public vs private**：CDN 是「陌生人的缓存」，只有 `public` 才敢存；`private` 是「只给你一个人的缓存」。取舍：**共享效率 vs 隐私安全**。
- **压缩用「CPU 换带宽」**：压缩省传输字节，但多花服务器 CPU。br 比 gzip 更小但更耗 CPU。取舍：**带宽成本 > 计算成本**（静态资源一次压、反复用，CPU 摊薄）。
- **no-cache 不是不缓存**：历史命名混乱。它要「每次确认」而非「每次全量」——省响应体、不省请求。取舍：一致性 > 省流量。
- **Vary: Accept-Encoding 为什么重要**：同一资源因客户端能力有多个编码版本，缓存必须知道「按编码区分」否则串版本。取舍：**正确性 > 缓存简单**。
- **H2 多路复用为何不直接上**：H2 需 TLS/ALPN，且引入 TCP 层 HOL（丢包时共享连接全停）。取舍：应用层并发 > 传输层鲁棒性；H3 再用 QUIC 把鲁棒性补回来。
- **静态资源永久缓存 + hash**：把「要不要重新下载」的判断权从服务器交给 URL——内容变 URL 就变，天然失效。取舍：多一次构建产物 → 换零 304 请求。
- **域名分片为何消失**：H1 时代为突破 6 连接限制主动分片，H2 单连接多路复用后分片只剩反作用（多握手、多连接）。取舍：协议演进让旧优化失效，优化需随协议更新。

## 11. 规避 / 实践清单

| 问题 | 手段 | 对应节点 |
| --- | --- | --- |
| TTFB 高 / 跨地域慢 | **CDN 就近分发**、H2/H3、服务端缓存、边缘计算 | 网络链 |
| DNS 解析慢/被劫持 | **云服务商 DNS**（智能解析 + DoH）、短 TTL + 健康检查 | DNS 层 |
| 故障切换慢 | 云 DNS 健康检查 + 短 TTL（≤60s） | DNS 层 |
| 静态资源下载慢 | **gzip/br 压缩** + CDN + hash 文件名长缓存 | 传输/网络链 |
| 源站压力大 | CDN 边缘缓存（`public`/`s-maxage`） | 网络链 |
| 静态资源反复下载 | hash 文件名 + 长缓存 + immutable | 前置逻辑 |
| 页面/接口被缓存 | `no-store` / `private` | 前置逻辑 |
| 每次都 304 | 长缓存，把可变的塞进 URL | 前置逻辑 |
| 重定向拖首屏 | 减少跳数、CDN 层 301、删除旧跳转 | 前置逻辑 |
| H1 并发差 | 升级 H2/H3、收敛域名（去掉分片） | HTTP 层 |
| 弱网丢包卡 | HTTP/3 (QUIC) | HTTP 层 |
| 跨源首屏连接慢 | `preconnect` + `dns-prefetch` | 连接层 |
| 首屏关键资源晚到 | `<link rel="preload">` | 请求层 |
| 老浏览器拿到 br 乱码 | 正确协商 + `Vary: Accept-Encoding` | 传输层 |
