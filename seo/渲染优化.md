# 渲染优化（SEO/性能：渲染链）

> **结论：渲染优化的目标 = 把「HTML 到达之后到首屏（FCP/LCP）呈现」的时间压到最低。核心手段 = ① 选对渲染模式（SSG/SSR/ISR vs CSR 决定 HTML 里有没有内容）、② 减少渲染阻塞（CSS/JS）、③ 减少布局抖动（CLS）、④ 让关键资源提前（preload/LCP 优先级）。** 实测锚点：`<head>` 里一个 350ms 的 `slow.css` 把 FCP 从 28ms 拖到 **532ms（≈19×）**，把 DOMContentLoaded 从 12ms 拖到 **526ms（≈44×）**——渲染阻塞资源是首屏最大杀手；渲染模式上，SSG 内容就绪 **40ms** vs CSR **160ms**（4×），差的就是「HTML 自带内容 vs 等 JS 跑出内容」。渲染优化是「面试中区分度最高的部分」——它牵扯事件循环、渲染管线、LCP 动态更新、以及服务端/客户端渲染模式取舍。

> 可运行验证：[[导航时序全过程-demo.html]]（本地 HTTP 服务器给 `slow.css`/`slow.png` 注入延迟，逐段拆解 Navigation Timing + Paint Timing，含瀑布图）；[[SSR-SSG-ISR-验证脚本.js]]（Node 模拟四种渲染模式的 TTFB 与内容就绪时间）；[[Update Rendering.html]]（渲染管线每一帧内部顺序）

## 1. 背景：渲染链在哪里、瓶颈是什么

```
(网络链终点 responseStart)  →  [浏览器渲染链]
HTML到达 → 解析HTML → CSSOM → 渲染树 → 布局 → 绘制 → 合成 → 屏幕
             │  遇 <link>css → CSSOM（阻塞渲染）
             │  遇 <script> → 阻塞解析
             └→ DOM + CSSOM 就绪 → 首屏 (FP/FCP) → 最大内容 (LCP)
```

- **渲染链的性能瓶颈在「阻塞 + 内容来源」两个维度**：
  - **阻塞**：HTML/CSS/JS 的解析顺序、渲染阻塞资源，决定 FCP/LCP。
  - **内容来源**：HTML 是**自带内容**（SSR/SSG/ISR）还是**空壳等 JS**（CSR）——决定「首屏有没有内容可渲染」（见 §4）。
- **渲染优化的本质**：能并行的并行（async/defer/preload）、能提前的提前（关键 CSS 内联、构建期生成 HTML）、能减少的减少（避免强制同步布局、防 CLS）。
- **与网络链的关系**：网络层决定 HTML「什么时候到」，渲染层决定「到了之后什么时候画出来」。两段独立优化、互不替代。

> 完整链路图见 [[从浏览器输入网址到页面完整展示全过程]]；每帧内部顺序见 [[Update Rendering 阶段详解]]。

## 2. 渲染阻塞资源：CSS 与 JS（收益最大）

> **结论：`<head>` 里的 CSS 和同步 JS 是首屏两大阻塞源——CSS 阻塞渲染（FCP 前必须拿到 CSSOM），JS 阻塞解析（解析器必须等脚本执行完）。** 实测 `slow.css` 350ms 延迟 → FCP 532ms（19×）、DCL 526ms（44×）、load 651ms（53×）。

### 2.1 阻塞语义表（面试必背）

| 资源/位置 | 阻塞 DOM 解析 | 阻塞渲染(FCP) | 说明 |
| --- | --- | --- | --- |
| `<link>` CSS 在 `<head>` | ❌ | ✅ **阻塞** | 首屏前必须拿到 CSSOM（防 FOUC） |
| 同步 `<script>` | ✅ **阻塞** | ✅ | 可能改 DOM，必须等它执行完 |
| `<script async>` | ⚠️ 下载并行、执行时阻塞 | 视情况 | 执行顺序不保证 |
| `<script defer>` | ❌ | ✅ 阻塞在 DCL 前 | 解析完、DCL 前按序执行 |
| `<img>` | ❌ | ❌（可能成 LCP） | 解码渲染完才上报 LCP |

> **⚠️ CSS 与 JS 交互坑**：`<head>` 的 CSS 会**阻塞其后同步 `<script>` 的执行**（规范：脚本要等前置样式表就绪）。所以 `slow.css` 不只推迟渲染，还把 `domInteractive` 一起拖到 500ms+。面试追问「CSS 阻塞的是解析还是脚本」就从这里答。

### 2.2 实测：渲染阻塞的影响（Chrome 151 headless）

**① 有 vs 无渲染阻塞 CSS**

| 指标 | 基线页(无 slow.css) | 标准页(含 slow.css) | 差距 |
| --- | --- | --- | --- |
| FCP | 28ms | 532ms | **≈19×** |
| DOMContentLoaded | 12ms | 526ms | **≈44×** |
| load | 12ms | 651ms | **≈53×** |

**② 标准页逐阶段耗时**

| 阶段 | 耗时 | 占首屏比例 |
| --- | --- | --- |
| TTFB | ~6ms | 1% |
| 下载 HTML | ~1ms | <1% |
| **HTML解析→DOMInteractive** | **~500ms** | **77%**（被 slow.css 阻塞的脚本等待） |
| FP/FCP | ~532ms | — |
| LCP | ~656ms | —（slow.png 600ms 后到） |

> 结论：**首屏 77% 时间耗在「解析被渲染阻塞 CSS 拖住」**——CSS 不阻塞解析本身，但阻塞其后脚本执行，连带推迟 `domInteractive`。图片 600ms 不阻塞解析（DCL 不推迟），但会成为 LCP。

> 可运行验证：[[导航时序全过程-demo.html]] —— 瀑布图可见 `domParse` 段（红紫）横跨大半时间轴。

### 2.3 对策

- **关键 CSS 内联**：首屏需要的 CSS 内联进 `<head>`（省一次请求 + 避免阻塞等待），非关键 CSS 用 `media` 拆分/异步加载。
- **JS 三选**：`defer`（保序、不阻塞解析）→ 默认；`async`（独立、不保序）→ 第三方统计类；`<script type="module">`（默认 defer 语义）。
- **preload 关键资源**：首屏关键但藏在 CSS/JS 深处的资源（字体、首屏图）用 `<link rel="preload">` 强制提前。
- **CSS `@import` 别用**：`@import` 是串行下载（比 `<link>` 多一次往返），H1 下更是灾难。

## 3. 首屏指标：FCP 与 LCP（度量 + 优化）

| 指标 | 全称 | 含义 | 优化重点 |
| --- | --- | --- | --- |
| **FP** | First Paint | 第一次绘制像素 | 最小渲染 |
| **FCP** | First Contentful Paint | 第一个内容（文字/图/画布）渲染 | 关键 CSS + 减少阻塞 |
| **LCP** | Largest Contentful Paint | **最大内容**块渲染，核心体验 | 首屏图/大标题优先级 |
| **CLS** | Cumulative Layout Shift | 布局抖动累计分 | 图片占位、字体度量 |

> **⚠️ LCP 是动态更新的**：最大内容可能变（图片后到会替换文字），以「最后一次上报」为准。所以「优化 LCP」= 让最大元素（往往是首屏大图/大标题）**尽快被渲染且稳定不被替换**。

- **LCP 常见元素**：`<img>`、`<image>`、`background-image`、大段文本块、`<video>` poster。
- **LCP 优化手段**：
  - 首屏图 `fetchpriority="high"` + `preload` + 适当尺寸（别加载 2× 的大图）；
  - 大标题/首屏文本别藏在 JS 里异步渲染（会让 LCP 推迟到 JS 执行完）；
  - 首屏外的图 `loading="lazy"`（不抢 LCP 资源优先级）。

## 4. 渲染模式：SSG / SSR / ISR / CSR（内容从哪来，面试高频）

> **结论：SSR/SSG/ISR 的核心差异 = 「HTML 在哪生成、何时生成」。SSG 构建期生成（最快），SSR 请求时在服务器生成（内容新鲜但 TTFB 慢），ISR 是 SSG + 按需重建（兼得快与新），CSR 让 JS 在客户端生成（HTML 空壳，首屏最慢、SEO 最差）。** 实测：SSG 内容就绪 **40ms** vs SSR/ISR **70ms** vs CSR **160ms**（4×）。

### 4.1 四种模式一句话

| 模式 | 全称 | HTML 谁生成 | 生成时机 | 一句话 |
| --- | --- | --- | --- | --- |
| **CSR** | Client-Side Rendering | 客户端 JS | 请求后，JS 下载+执行 | HTML 空壳，内容全靠 JS 跑出来 |
| **SSR** | Server-Side Rendering | 服务器 | **每次请求时** | 服务端现渲染，内容新鲜，TTFB 慢 |
| **SSG** | Static Site Generation | 构建期 | **构建时** | 一次生成静态 HTML，读文件最快 |
| **ISR** | Incremental Static Regeneration | 构建期 + 按需重建 | 构建时 + 过期重建 | SSG + 定期/按需更新，兼得快与新 |

### 4.2 实测：四种模式的时间线（Node 模拟）

参数：服务端渲染 30ms、客户端 JS 120ms、网络 RTT 20ms。

| 模式 | HTML 谁生成 | 生成时机 | TTFB | 内容就绪(FCP) |
| --- | --- | --- | --- | --- |
| **SSG** | 构建期 | 构建时 | 20ms | **40ms** |
| **ISR** | 构建期/重建 | 构建时+按需 | 50ms（冷缓存） | **70ms**（冷缓存重建） |
| **SSR** | 服务器 | 请求时 | 50ms | **70ms** |
| **CSR** | 客户端 | 请求后 JS | 20ms | **160ms** |

> 结论：**TTFB 上 SSG 最快（读文件）、SSR 最慢（请求时渲染）、CSR 也快（空壳）；但「内容就绪」SSG/SSR/ISR 都远快于 CSR（40/70/70 vs 160ms）**——因为前三种的内容就在 HTML 里，浏览器拿到即可渲染；CSR 必须等 JS 下载执行完才生成 DOM，之前屏幕空白。

> 可运行验证：[[SSR-SSG-ISR-验证脚本.js]] —— Node 模拟四种模式的 TTFB/内容就绪 + ISR 过期重建对比。

### 4.3 ISR 增量再生：命中 vs 重建（实测）

| 访问 | 状态 | 额外耗时 |
| --- | --- | --- |
| 第 1 次（冷缓存） | ISR 过期重建 | +30ms（构建） |
| 第 2 次（60s 内） | ISR 缓存命中 | +0ms |
| 第 3 次（>60s） | ISR 过期重建 | +30ms |

> 结论：**ISR = 平时走 SSG 的读文件速度，过期后下一次访问触发重建**。用「按需重建」换「内容不永久陈旧」——适合内容会变但不要求实时的页面（博客、商品详情）。

### 4.4 怎么选（面试决策框架）

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 内容基本不变（文档/博客/官网） | **SSG** | 最快 + 最便宜（静态托管） |
| 内容会变但非实时（商品/文章列表） | **ISR** | 快 + 能更新 |
| 个性化/实时数据（用户中心/行情） | **SSR**（或 CSR+骨架） | 每次拿最新，但贵、TTFB 慢 |
| 纯应用/后台（内部工具） | **CSR** | 无需 SEO，省服务端成本 |
| SEO 敏感（营销页/内容站） | SSG/SSR | HTML 自带内容，爬虫可抓 |

- **SEO 关键**：CSR 空壳 HTML 爬虫抓不到内容（除非用渲染服务/预渲染），SSG/SSR/ISR 的 HTML 有完整内容 → 对 SEO 是刚需。
- **SSR 的坑**：服务端渲染 = 每个请求都跑渲染函数 → TTFB 慢 + 服务器 CPU 贵；配合 CDN 缓存 `s-maxage` 可缓解（见 [[网络层优化]] §3）。
- **水合（hydration）**：SSR/SSG 返回的 HTML 已有内容，浏览器还要下载 JS「水合」——把静态 HTML 绑定为可交互应用。水合前页面「能看不能点」。SSR 不是「首屏就交互」，而是「首屏就有内容」。
- **流式 SSR（Streaming SSR）**：把 HTML 分块流式返回，首块（头部+骨架）先到、慢的内容块后到，TTFB 更小、FCP 更早。

## 5. 布局抖动 CLS：视觉稳定性

> **结论：CLS 衡量「元素位置在页面生命周期内突然移动」的程度。** 抖动来自「元素先渲染、后因资源/字体到达而被迫挪位」——图片没占位、字体 swap、广告/弹窗插入、JS 改布局。

- **CLS 计分**：位移距离 × 影响区域，0~1，<0.1 为良好。
- **常见诱因与对策**：

| 诱因 | 对策 |
| --- | --- |
| 图片无尺寸 | `width/height` 占位（或 `aspect-ratio`），防加载后撑开 |
| 字体加载抖动 | `font-display: swap`（先回退字体、后替换，避免文字隐藏）或 `optional` |
| 动态插入广告/弹窗 | 预留容器、定位用 `transform` 而非改布局 |
| 首屏后异步改布局 | 避免在 `load` 后往视口上方插内容 |
| 动画引起位移 | 动画只用 `transform/opacity`（不触发布局/绘制） |

> **动画原则**：能用 `transform`/`opacity` 就别动 `width/height/top/left`——前者只走合成（compositor），后者触发重排+重绘。见 [[Update Rendering 阶段详解]] 的合成/绘制分层。

## 6. 减少主线程负担：避免强制同步布局（FSL）

> **结论：强制同步布局（Forced Synchronous Layout）是「读几何属性时，浏览器被迫中断当前队列、立即做一次布局」——在滚动/动画循环里反复触发会卡帧。** 优化 = 读写分离：先批量读、再批量写，或先用缓存值。

- **触发**：在「布局尚未完成」的时机读 `offsetHeight/scrollTop/getBoundingClientRect()` 等几何值。
- **实测场景**：scroll 事件里每帧读 `scrollTop` + 写样式 → 强制重排；见 [[scroll中的强制同步布局]]。
- **对策**：
  - 读几何前先把待写的样式写完（读写分离）；
  - 用 rAF 批量读（布局稳定后读）；
  - 几何只读不改的用 `content-visibility: auto` 跳过屏外渲染。

> 可运行验证：[[scroll中的强制同步布局-demo.html]]。

## 7. 渲染优化的分层策略（面试框架）

从「投入产出比」看渲染优化，面试可这样分层回答：

| 层级 | 手段 | 目标 |
| --- | --- | --- |
| L0 选对渲染模式 | SSG/SSR/ISR vs CSR（HTML 有无内容） | 首屏有内容 + SEO |
| L1 减少阻塞 | 关键 CSS 内联、defer/async、preload | FCP 提前 |
| L2 度量与优先级 | 首屏图 `fetchpriority="high"`、`loading="lazy"` 屏外 | LCP 提前 |
| L3 视觉稳定 | 图片占位、`font-display: swap`、transform 动画 | CLS 降低 |
| L4 主线程 | 读写分离、rAF 批量、`content-visibility` | 卡顿减少/INP 降低 |
| L5 渲染管线认知 | 知道哪一步触发布局/绘制/合成，选对属性 | 长期可维护 |

## 8. 为什么这么设计？（背后取舍）

- **SSG 快但旧**：构建期生成 → 请求时读文件（≈0 渲染），最快最便宜；但内容更新要重新构建。取舍：**速度 > 新鲜度**。
- **SSR 新但慢**：每次请求现渲染 → 内容永远最新，但 TTFB = 渲染耗时，服务器 CPU 贵。取舍：**新鲜度 > 速度**。
- **ISR 是折中**：SSG 的速度 + 定期重建的新鲜度。用「过期后下一次访问触发重建」换「内容不永久陈旧」。取舍：**大部分时候快 + 偶尔慢**。
- **CSR 为什么仍是主流**：交互复杂应用（后台、编辑器）内容与用户强相关，服务端渲染无意义且贵；且 CSR 开发简单、部署便宜。取舍：**开发效率 > 首屏/SEO**。
- **CSS 阻塞渲染**：首屏必须保证样式一致（避免 FOUC 无样式闪烁）。浏览器宁可在 CSSOM 就绪前不画，也不愿画了再闪。取舍：**首屏正确性 > 首屏速度**。
- **JS 阻塞解析**：脚本可能 `document.write`/改 DOM，解析器无法预知，只能停下等它执行完。取舍：**确定性 > 并行性**。这也是 `defer`/`async`/`module` 存在的意义——把「确定性」主动让渡给开发者。
- **图片不阻塞解析**：图片与 DOM 结构无关，浏览器只需留出占位。取舍：**并行下载 > 渲染完整性**；代价是图片晚到会触发 CLS，由 `width/height` 占位解决。
- **LCP 动态更新**：浏览器无法预知「哪个是最大内容」，只能边走边比。取舍：**准确反映真实首屏 > 上报稳定**。
- **font-display 默认是 block（不显示）**：怕文字「闪」，却造成文字不可见；`swap` 换成「先回退、后替换」，视觉损失换可用性。取舍：**可用性 > 完美字体**。

## 9. 规避 / 实践清单

| 问题 | 手段 | 对应节点 |
| --- | --- | --- |
| 首屏没内容/SEO 差 | 换 SSG/SSR/ISR（HTML 自带内容） | 渲染模式 |
| 内容变了却还是旧页 | ISR 重建周期调短 / SSR | 渲染模式 |
| SSR TTFB 慢 | CDN 缓存 `s-maxage`、流式 SSR、边缘渲染 | 渲染模式 |
| 首屏被 CSS 拖 | 关键 CSS 内联、`media` 拆分、preload | 阻塞 |
| 首屏被 JS 拖 | `defer`/`async`/`module`、body 底部 | 阻塞 |
| LCP 是首屏大图 | `fetchpriority="high"` + preload + 合理尺寸 | 度量 |
| 图片导致抖动 | `width/height`/`aspect-ratio` 占位 | CLS |
| 字体导致文字跳 | `font-display: swap` | CLS |
| 滚动卡顿 | 读写分离、rAF 批量、避免 FSL | 主线程 |
| 动画掉帧 | 只用 `transform/opacity` | 合成 |
| 屏外内容白算 | `content-visibility: auto` | 主线程 |
