# 防抖（Debounce）

> **结论：防抖 = 事件触发后，重置计时器，只在「停止触发一段时间后」执行一次回调。** 高频触发（输入、滚动、resize）只会让计时器不断重置，**真正执行的永远只有"最后一次触发"**。核心就一行：`clearTimeout(timer); timer = setTimeout(fn, delay)`。可选 `immediate`（leading）让**第一次立即执行**。防抖与节流的分工：**防抖管"停止后执行一次"，节流管"固定间隔最多执行一次"**——搜索联想用防抖，滚动位置上报用节流。
>
> 可运行验证：[[防抖-验证脚本.js]]（Node 真实 setTimeout 时序：trailing/leading/冷却后重触发/无防抖对比/this 绑定/cancel）· [[debounce两种写法对比-验证脚本.js]]（面试陷阱：if 在外 vs if 在内，leading 模式天壤之别）

## 1. 背景：为什么需要防抖

- 事件天然高频：`input` 每敲一个字、`scroll`/`resize` 每帧都可能触发几十次。
- 高频回调的代价：每次触发都可能发请求 / 做重计算 / 操作 DOM → **请求轰炸、掉帧卡顿**。
- 直觉解法：**等用户"停下来"再执行**——这就是防抖。

> 为什么这么设计：防抖的本质是**"用时间换稳定"**。用户连续操作是噪声，真正有意义的是"最后那一下"（最后一次输入的字、滚轮停住的位置）。与其每次触发都干活，不如把活推迟到触发停止后一次性做完。

## 2. 标准实现（面试手写版）

```js
function debounce(fn, delay = 300, immediate = false) {
  let timer = null;
  function debounced(...args) {
    const ctx = this;                         // ① 先存 this（调用时是触发者）
    if (immediate && !timer) fn.apply(ctx, args);  // ② leading：无计时器=冷却完 → 立即执行
    clearTimeout(timer);                      // ③ 核心：每次都重置
    timer = setTimeout(() => {
      if (!immediate) fn.apply(ctx, args);    // ④ trailing：计时结束执行最后一次
      timer = null;                           // ⑤ 清状态，让 leading 下轮生效
    }, delay);
  }
  debounced.cancel = () => { clearTimeout(timer); timer = null; };
  return debounced;
}
```

| 行 | 作用 | 面试要点 |
| ---- | ---- | ---- |
| ③ `clearTimeout + setTimeout` | **防抖的灵魂**：每次触发重置倒计时 | 倒计时永远从最后一次触发重新计 |
| ② `immediate && !timer` | leading 版：冷却完成后第一次触发**立即执行** | `!timer` 判断"当前是否在冷却期" |
| ① `const ctx = this` | 保存调用者 this | 定时器回调里 this 会变 `undefined`（非严格）/window，必须提前存 |
| `...args` | 透传参数 | 最后一次调用的参数生效（`[A2]`） |
| `cancel()` | 手动取消未执行的回调 | 组件卸载时 `debounced.cancel()` 防"更新已卸载组件" |

```
[A2] 执行参数 [[5]]            ← 只有最后一次的参数生效
[B1] leading 连发 5 次 → 执行 1 次（期望 1）

```

## 4. trailing vs leading（两种触发时机）

| 模式 | 执行时机 | 典型场景 | 参数取谁的 |
| ---- | ---- | ---- | ---- |
| **trailing**（默认） | **最后一次触发后** delay | 搜索输入联想（等用户停手再请求） | 最后一次 `[A2]` |
| **leading**（`immediate: true`） | **第一次触发立即执行**，冷却期内其余忽略 | 按钮防连点（首次立刻响应） | 第一次 `[B2]` |

> 面试加分：**说清"防抖不是只执行一次"**（实测 `[C1]`：冷却结束后再触发，照样再执行）——这是新手最常见的误解。

## 5. 防抖 vs 节流

| 维度 | 防抖 debounce | 节流 throttle |
| ---- | ---- | ---- |
| 执行时机 | **停止触发后** delay 执行一次 | **固定间隔**最多执行一次（不管触发了多少次） |
| 连续输入 1s | 只执行最后一次后那 1 次 | 按间隔执行多次（如 200ms 一次 → 5 次） |
| 适用 | 搜索联想 / 窗口 resize / 表单校验 | 滚动位置上报 / 拖拽 / 游戏帧率控制 |
| 一句话 | "等你停下来" | "固定节奏干活" |

## 5.5 面试陷阱：两种写法的区别（实测）

> **结论：`if (!immediate)` 在外 vs 在内，trailing 下没区别，leading 下天壤之别——外置写法在 leading 模式每次触发都执行（bug），内置写法才正确。** 根源：**`timer = null` 必须无条件执行**（它是冷却结束标记），外置写法把 `timer = null` 关进了 `!immediate` 的笼子，leading 模式永远拿不到标记 → `!timer` 恒 true → 每次都执行。

```js
// 写法A：if 在外（❌ leading bug）
if (!immediate) {
  timer = setTimeout(() => {
    fn.apply(ctx, args);   // 无条件执行
    timer = null;          // ← 被关进笼子，leading 模式永远执行不到
  }, delay);
}

// 写法B：if 在内（✅ 标准）
timer = setTimeout(() => {
  if (!immediate) fn.apply(ctx, args);   // 只决定执行
  timer = null;                          // ← 无条件置 null = 冷却标记
}, delay);
```

实测（debounce两种写法对比-验证脚本.js）：
```
[A1] 写法A trailing → 1 次（正常）
[A2] 写法A leading → 5 次（❌ 每次触发都执行，bug！）
[B1] 写法B trailing → 1 次（正常）
[B2] 写法B leading → 1 次（✅ 只执行第一次）
[C]  写法B leading 冷却后重触发 → [1,2]（✅ 每轮暂停后都能再立即执行）
```

**为什么写法A leading 崩**：leading 下 `if (!immediate)` 为 false → **不创建定时器** → `timer` 永远是 null → `immediate && !timer` 恒为 true → 每次都执行。**没有定时器，就没有「冷却结束」的标记**，leading 变成「每次都执行」。

**为什么写法B 对**：定时器**始终创建**（冷却期存在），回调里 `if (!immediate)` 只决定「执行不执行 func」，而 **`timer = null` 无条件跑**——这就是冷却结束标记，leading 下一轮能据此重新立即执行（实测 C）。

> **面试话术**：「两种写法 trailing 等价；leading 下 if 在外是陷阱——`timer = null` 必须无条件执行，它是冷却结束的标记。if 的位置决定『要不要执行』，不决定『要不要创建定时器』。」

## 6. 高频追问速答

| 问题                  | 一句话答案                                                     |
| ------------------- | --------------------------------------------------------- |
| 防抖核心代码是？            | `clearTimeout(timer); timer = setTimeout(fn, delay)`      |
| 防抖里 this 为什么可能丢？    | 定时器回调的 this 指向变了（严格模式 `undefined`），所以要 `const ctx = this` |
| leading 版如何判断"冷却完"？ | `immediate && !timer`——timer 为 null 说明没有待执行的定时器=冷却结束      |
| 防抖和节流怎么选？           | 要"最后一次结果"用防抖，要"持续有响应"用节流                                  |
| 防抖会造成内存问题吗？         | 回调闭包持有大对象时要注意；组件卸载记得 `cancel()`                           |

## 7. 面试速记（30 秒版）

> **防抖：触发 → 重置计时器 → 停止后 delay 执行一次（最后一次的参数）。** 灵魂一行 `clearTimeout + setTimeout`。两个版本：**trailing**（尾执行，等用户停手）vs **leading**（首执行，`immediate && !timer` 立即响应，防连点）。要点：**先存 `this`**（定时器回调丢 this）、透传 `...args`、暴露 `cancel()`。**陷阱**：`if (!immediate)` 必须放回调**内**（`timer = null` 无条件执行 = 冷却标记；放外则 leading 每次触发都执行）。和节流的区别：**防抖"停后执行一次"，节流"固定间隔一次"**——搜索联想用防抖，滚动上报用节流。
