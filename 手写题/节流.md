# 节流（Throttle）

> **结论：节流 = 固定时间间隔内，最多只执行一次回调。** 不管触发了多少次，都保证**每 delay 毫秒至多执行一次**——高频事件被"降频"而不是"延后"。两种实现：**时间戳版**（leading：第一次立即执行，之后按间隔触发）和**定时器版**（trailing：冷却期内忽略，只在一次触发后 delay 执行）。与防抖的分工：**防抖管"停止后执行一次"，节流管"固定间隔最多一次"**——搜索联想用防抖，滚动/拖拽/窗口 resize 上报用节流。
>
> 可运行验证：[[节流-验证脚本.js]]（Node 真实 setTimeout 时序：时间戳版/定时器版/防抖对比/冷却期忽略/this 绑定/cancel）

---

## 1. 背景：防抖的"缺陷"和节流的"补位"

- 防抖的问题：如果用户**一直不停**（持续输入、持续滚动），回调就**永远不执行**——"等用户停下来"这个前提不成立。
- 节流解决：**不管多频繁，固定间隔就执行一次** → 即使事件不停，也有稳定的响应节奏。

> 为什么这么设计：**防抖是"结果敏感"（只要最后的结果），节流是"过程敏感"（要保持持续的进度）。** 拖拽一个元素，你要的是一路平滑更新（每隔一段就落一次位置），不是停下来才算——这就是节流的场景。

## 2. 标准实现（面试手写版）

### 2.1 时间戳版（leading：第一次立即执行）

```js
function throttle(fn, delay = 300) {
  let last = 0;                    // 上次执行时刻
  return function (...args) {
    const now = Date.now();
    const ctx = this;
    if (now - last >= delay) {     // 距离上次执行已超过间隔 → 执行
      last = now;
      fn.apply(ctx, args);
    }
  };
}
```

### 2.2 定时器版（trailing：冷却期忽略，结束后执行最后一次）

```js
function throttleTimer(fn, delay = 300) {
  let timer = null;
  return function (...args) {
    const ctx = this;
    if (timer) return;             // 已有计时器 → 冷却期，忽略本次触发
    timer = setTimeout(() => {
      fn.apply(ctx, args);
      timer = null;                // 执行完释放，允许下次触发
    }, delay);
  };
}
```

| 版本 | 触发时机 | 特点 | 适用 |
| ---- | ---- | ---- | ---- |
| **时间戳版** | 第一次立即执行，之后每间隔执行 | 响应快、不拖尾 | 滚动监听、拖拽（要即时反馈） |
| **定时器版** | 每次触发后 delay 执行一次，冷却期忽略 | 尾执行、不丢最后一次 | 上报统计（攒一段一起发） |

> 面试加分：**先说"节流两种实现，区别在 leading/trailing"**，再补一句"正式库（lodash）支持 leading+trailing 组合（trailing 补齐最后一次）"——显得你不仅背代码，还懂取舍。

## 3. 实测数据（节流-验证脚本.js）

```
[A1] 时间戳版：每 20ms 触发 5 次，delay=60ms → 执行 3 次（立即第1次 + 间隔后）
[A2] 执行时刻 [3, 67, 128]ms          ← 间隔 ≈ delay（60ms）
[C1] 同样 5 次连发：防抖 1 次 | 节流 3 次   ← 分工差异直接可见
[D1] 冷却期内触发 [2,3] 被忽略 → 执行 [1,4]  ← 节流"降频"而非"延后"
[E1] this 正确指向 obj.n=1
[F1] cancel() 后执行 0 次
```

- `[A2]`：两次执行间隔约 60ms（≈delay）→ 节流保证了**固定节奏**。
- `[D1]`：第 2、3 次触发落在冷却期被忽略，冷却结束后第 4 次执行 → 中间触发直接丢弃（不是延后）。
- `[C1]`：防抖 1 次 vs 节流 3 次——**这是面试必答的分工**。

## 4. 防抖 vs 节流（最终对比）

| 维度 | 防抖 debounce | 节流 throttle |
| ---- | ---- | ---- |
| 执行时机 | **停止触发后** delay 执行一次 | **固定间隔**最多执行一次 |
| 持续触发时 | 一直不执行（等停手） | 按间隔持续执行 |
| 核心代码 | `clearTimeout + setTimeout` | `now - last >= delay` 或 `if (timer) return` |
| 适用 | 搜索联想 / 表单校验 / resize 收尾 | 滚动位置 / 拖拽 / 游戏帧率 / 上报 |
| 一句话 | "等你停下来" | "固定节奏干活" |

> 实战组合：**"leading 节流 + trailing 防抖"**（lodash `throttle` 默认两者都带）——既保证首触发即时，又不丢最后一次，是滚动上报的标准姿势。

## 5. 高频追问速答

| 问题 | 一句话答案 |
| ---- | ---- |
| 节流核心思路？ | 记录上次执行时间，间隔未到就忽略；或冷却期内有计时器就忽略 |
| 时间戳版 vs 定时器版？ | 时间戳=leading 立即执行；定时器=trailing 尾执行；lodash 可组合 |
| 节流和防抖怎么选？ | 要"最后结果"→防抖；要"持续响应/固定节奏"→节流 |
| 节流会丢事件吗？ | 会——冷却期内的中间触发被丢弃，这正是"降频"的目的 |
| 手写注意什么？ | 存 `this`、透传 `...args`、暴露 `cancel`、定时器版记得 `timer=null` 释放 |

## 6. 面试速记（30 秒版）

> **节流：固定间隔最多执行一次，把高频事件"降频"。** 两种实现——**时间戳版**（`now-last>=delay` 才执行，leading 立即响应）和**定时器版**（`if(timer)return` 冷却期忽略，trailing 尾执行）。要点：存 `this`、透传参数、定时器版执行后 `timer=null`。和防抖的区别一句话：**防抖"停后执行一次"，节流"固定间隔一次"**——搜索联想防抖，滚动/拖拽节流。正式库支持 leading+trailing 组合（trailing 补最后一次）。
