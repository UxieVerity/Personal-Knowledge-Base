# 数组乱序（洗牌 Shuffle）

> **结论：正确洗牌 = Fisher-Yates 算法（从后往前，每个位置与 [0, i] 随机下标交换），O(n) 且均匀。** 面试错误答案：**`arr.sort(() => Math.random() - 0.5)`**——比较函数被要求满足全序（传递性），随机返回值破坏排序算法假设，导致结果**非均匀**（实测元素落在中间位置概率偏高、两端偏低）。两个必答点：① Fisher-Yates 为什么均匀——每个元素在每个位置的概率严格 1/n（组合数推导）；② 注意**别改原数组**（先 `slice()` 副本）。

> 可运行验证：[[数组乱序-验证脚本.js]]（Node 实测：正确性 / 10 万次均匀性统计 Fisher-Yates vs sort 随机版对比 / 性能）

---

## 1. 背景：什么时候需要洗牌

- 随机打乱列表：抽奖、题目乱序、卡片/瀑布流随机
- 游戏：发牌、出招随机
- 音视频/推荐：随机播放列表（播放引擎里也用到）

> 为什么这么设计：**"随机"≠"均匀"**。`Math.random()` 每次独立均匀，但把随机数塞进 sort 比较函数，排序算法（V8 的 TimSort/插入排序）会系统性偏置——这不是"看起来乱"就够，面试考的是**你知道随机排列的数学要求和 O(n) 的交换式洗牌**。

## 2. 标准实现（面试手写版）

### 2.1 Fisher-Yates（正确版，背这个）

```js
function shuffle(arr) {
  const a = arr.slice();                              // ① 副本，不改原数组
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));    // ② [0, i] 随机下标
    [a[i], a[j]] = [a[j], a[i]];                      // ③ 交换
  }
  return a;
}
```

| 行 | 作用 | 面试要点 |
| ---- | ---- | ---- |
| `arr.slice()` | 副本 | 洗牌应返回新数组，不破坏原数组 |
| `i > 0` 从后往前 | 每个位置只参与一次 | 已处理的尾部不再动 → 保证均匀 |
| `Math.floor(random() * (i + 1))` | [0, i] 整数 | **含 i**（含当前位，允许原地不动），不是 `(i)` |
| 解构交换 | 交换 | 不引入临时变量 |

> 为什么均匀：第 i 步元素被选中的概率是 1/(i+1)，且后续步骤不会再把已固定的尾部位置打乱——**每个元素落在每个位置的概率严格 1/n**（n=5 时每个位置 20%）。

### 2.2 错误做法（必答的坑）

```js
const shuffleBad = arr => arr.slice().sort(() => Math.random() - 0.5);
```

- **错在哪**：sort 的比较函数必须满足**全序**（a<b 且 b<c 则 a<c）。返回随机值 → 比较结果自相矛盾（a 比 b 小、b 比 c 小、但 a 又比 c 大），排序算法（V8 TimSort）在这种输入下产生**系统性偏差**。
- **实测**：10 万次，元素 3 落在位置 0~4 的概率 = **16.4% / 16.4% / 17.1% / 22.2% / 27.9%**（理论 20%）——中间偏后位置概率被抬高，不均匀。
- 性能也差：O(n log n) 且比较函数每次调用都有随机开销（实测 32ms vs Fisher-Yates 1.5ms）。

### 2.3 偏置的根因：二分插入排序的插入点分布（进阶深挖）

> 面试大杀器：**"sort 随机版为什么不均匀"**，能讲到下面这层，直接碾压大多数候选人。实验：30 万次，5 元素 `[1,2,3,4,5]`，每个原始元素落在每个最终位置的概率（行=原始元素，列=最终位置，理论全 20%）：

```
        位置0   位置1   位置2   位置3   位置4
元素1 | 24.4% | 24.6% | 19.6% | 17.3% | 14.1%   ← 往前偏
元素2 | 24.8% | 24.6% | 19.5% | 17.1% | 14.1%   ← 往前偏
元素3 | 16.5% | 16.4% | 17.3% | 21.8% | 28.0%   ← 往后偏
元素4 | 22.0% | 21.9% | 18.6% | 18.7% | 18.8%   ← 轻微
元素5 | 12.4% | 12.6% | 25.0% | 25.0% | 25.0%   ← 强烈往后偏
```

**规律**：越靠前的元素越容易留在前面，越靠后的元素越容易被推向后面——**有方向的系统性偏差，不是随机乱**。

**机制三步链（背下来）：**

1. **V8 对 ≤10 个元素的数组走 TimSort 的二分插入排序**（BinaryInsertionSort）。
2. **随机比较器让二分查找的插入点分布天然偏右**。对长度 4 的有序前缀插新元素（落点 0~4），100 万次实测：

   ```
   落点0: 12.5% | 落点1: 12.5% | 落点2: 25% | 落点3: 25% | 落点4: 25%
   ```

   落点 3、4（右侧）是落点 0、1（左侧）的 **2 倍**。原因：越靠右的位置需要"连续选右"的次数越少（落点 4 只需连续 3 次选右，概率 1/8 的路径；落点 0 需要更苛刻的判定组合）——**二分查找的路径组合数天然偏向右侧**。
3. **偏右的插入点 × 依次插入 = 累积偏置**。第 i 个元素大概率插到有序前缀右侧 → 先插入的被推向右、后插入的越插越靠后 → **原始顺序靠前的留在左边，靠后的被挤到右边**。

> **验证闭环**：V8 内置 sort 的概率矩阵（上面 A 表）和手写二分插入排序 + 随机比较器的矩阵**逐格几乎一致**——石锤：偏置就来自二分插入排序本身，与 V8 其他细节无关。**不是 V8 的 bug，是"把随机数当比较器"这个用法在数学上就不成立。**

> 面试一句话：**"随机比较器破坏 sort 的全序假设 → 对短数组 V8 走二分插入排序 → 二分查找插入点天然偏右（实测右侧是左侧 2 倍）→ 依次插入累积，原始靠前元素留前、靠后元素挤后。任何排序实现都救不了它，因为问题是数学层面的。"**

### 2.4 更深一层：二分查找判定树为什么"左深右浅"（可精确推导）

> 面试终极形态：**面试官追问"为什么插入点会偏右"，把二分查找的判定树结构展开**。这层讲出来 = 全栈级别的知其所以然。

**二分查找 = 走一棵判定树**。区间 `[lo, hi)`，每次 `mid = (lo+hi)>>1`，按比较结果去左/去右。**每个落点对应一条根到叶的路径，路径长度 = 比较次数 = 树深度。每层概率 1/2，所以路径越短概率越高。**

关键细节：V8 插入排序的二分查找**去左保留 mid、去右跳过 mid**：

```js
if (比较) hi = mid;       // 去左：mid 仍可能是落点 → 左侧所有落点都保留，要一路走到底
else      lo = mid + 1;   // 去右：mid 被跳过 → 右侧部分落点被"提前排除"，路径更短
```

**n=4 的判定树**（区间 `[0,4)`，mid=2）：

```
              [0,4)  ← 根，mid=2
            ↙        ↘
         [0,2)      [3,4)     ← 第一层
        ↙    ↘         ↘
    [0,1)  [2,2)     [4,4)    ← 第二层
     ↙ ↘     ↙         ↘
  [0,0)[1,1) [2,2)   [4,4)    ← 第三层（叶）
   落0   落1  落2      落4
```

实测（10 万次）落点与深度：

```
落点 | 实测概率 | 平均深度
 0   | 12.4% | 3.00 层   ← 最深：一路走左到区间 [0,0)
 1   | 12.4% | 3.00 层
 2   | 25.2% | 2.00 层   ← 浅：第一层 mid=2 就命中
 3   | 25.1% | 2.00 层
 4   | 24.9% | 2.00 层   ← 浅：第一层选右就到
左侧合计 24.8% | 右侧合计 75.2%   ← 右侧占 3/4
```

**结论：右侧叶子浅（2 层），左侧叶子深（3 层）→ 右侧路径概率高（每层 1/2，浅路径概率大）→ 插入点分布天然偏右。**

> **精确定义（防止说岔）**：深度不直接等于概率，而是**路径长度 = 比较次数，每多一层比较就乘一次 1/2**——一条深度 d 的路径概率 = `(1/2)^d`。所以右侧 2 层落点单点概率 25%（`(1/2)²`），左侧 3 层落点单点概率 12.5%（`(1/2)³`）。**不是"树深所以概率低"，是"路径短所以概率高"。**

**为什么左深右浅（直觉 + 数学）：**
- **去右只跳一个 mid**：`lo = mid+1` 把 mid 排除，右侧落点不用深入；**去左保留 mid**：`hi = mid`，左侧所有落点都在区间里，必须比较到区间空（`[lo,hi)` 长 0）为止——所以左侧落点必须走到底。
- 数学上：n=4 时 2 层路径 3 条 + 3 层路径 2 条，各概率 `(1/2)^深度` → 2 层合计 3/4、3 层合计 1/4，实测 75.2% / 24.8% 完全吻合。
- **这个"左深右浅"是二分查找本身的性质**，跟排序、跟洗牌无关——随机比较器只是把它的概率暴露了出来。

> 面试一句话：**"偏置根源是二分查找判定树左深右浅——去左保留 mid 要一路走到底，去右跳过 mid 路径更短；路径短概率高，插入点偏右。这跟排序无关，是二分查找本身的性质。"**

## 4. 高频追问速答

| 问题                    | 一句话答案                                         |
| --------------------- | --------------------------------------------- |
| 洗牌怎么写？                | Fisher-Yates：从后往前，每位置与 [0,i] 随机下标交换，O(n)      |
| 为什么不用 sort+random？    | 比较函数破坏全序假设 → V8 TimSort 系统性偏置，非均匀（实测中间位置概率偏高） |
| 为什么 Fisher-Yates 均匀？  | 每步固定一个尾部位置且不回头，每个元素每个位置概率严格 1/n               |
| 要洗原数组还是返回新的？          | 看需求；手写默认返回副本（slice），面试提一句副作用                  |
| `Math.random()` 够随机吗？ | 够用于洗牌（均匀）；加密场景才需要 `crypto.getRandomValues`    |

## 5. 面试速记（30 秒版）

> **洗牌 = Fisher-Yates**：`slice()` 副本 → 从后往前 → 每位置与 `[0,i]` 随机下标交换 → O(n) 均匀。**坑：`sort(() => Math.random()-0.5)` 是错的**——比较函数破坏全序，V8 对短数组走二分插入排序，**二分查找插入点天然偏右（实测右侧落点是左侧 2 倍）→ 依次插入累积** → 原始靠前元素留前、靠后元素挤后（实测位置概率 12%~28% vs 理论 20%），还慢 20 倍。**均匀的原因**：每步固定尾部、不回头，每个元素每个位置概率严格 1/n。
